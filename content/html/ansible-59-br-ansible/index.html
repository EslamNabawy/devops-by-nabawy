Chapter 01

🤖 Intro — مقدمة ونظرة عامة

🟢 6 MIN

Ansible هي أداة Automation مفتوحة المصدر (Open-Source) تُستخدم بشكل أساسي في مجالين:

1️⃣ Configuration Management

إدارة الإعدادات — تثبيت وتحديث البرامج وضبط الملفات على الـ Servers.

2️⃣ Infrastructure Provisioning

بناء وتجهيز البنية التحتية — إنشاء الـ Servers والموارد السحابية.

TASK [أهم مميزات Ansible الأساسية]the four pillars

1.1Agentless — بدون عميل

  • 📦 لا تحتاج لتثبيت أي برامج أو Agents على الـ Managed Nodes المستهدفة.
  • 🔌 الاتصال يتم عبر بروتوكول SSH (في أنظمة Linux) أو WinRM/SSH (في أنظمة Windows).
  • 🐍 المتطلب الوحيد على Servers الـ Linux هو وجود بيئة Python.

1.2Simple Syntax — صيغة بسيطة

تُكتب جميع الإعدادات وسيناريوهات التشغيل بلغة YAML — وهي لغة قراءة وكتابة بسيطة جدًا وسهلة التعلم والتنفيذ. لا أقواس معقدة ولا فاصيل منقوطة؛ فقط مسافات وترتيب.

1.3Declarative Approach — الأسلوب التوصيفي

تحدد في ملف الـ YAML الـ Desired State (الحالة المطلوبة) — مثل: «أريد تثبيت Apache وGit» — ويقوم Ansible بتنفيذ الـ Steps اللازمة للوصول لهذه الحالة بنفسه. ويدعم أيضًا الـ Imperative Approach عند استخدام الـ Ad-hoc Commands.

1.4Idempotency — التكرار الآمن ♻️

تعني أن تنفيذ نفس الـ Script عدة مرات متتالية لن يغيّر شيئًا إلا إذا كانت هناك حاجة فعلية للتغيير.

EXAMPLEإذا طلبت من Ansible تثبيت Apache وكان البرنامج مثبتًا بالفعل بنفس الإصدار → لن يعيد تثبيته ولن يحدث أي تغيير على الـ Server. ستظهر الحالة ok. غير مثبت؟ يثبته → changed.
AgentlessSimple YAMLDeclarativeIdempotent

Chapter 02

🏗️ Architecture — معمارية Ansible

🟢 5 MIN

تتكون معمارية Ansible من مكوّنين رئيسيين — بساطة متعمدة هي سر قوتها.

Architecture — المكوّنان والقناة بينهما
Control NodeLaptop / Linux Server — عليه Ansible
━━━ SSH Connection ──►
Managed NodeUbuntu / CentOS / DB

القناة: Public/Private Key Pair — الاتصال مؤمَّن بلا Passwords.

2.1Control Node — عقدة التحكم

الجهاز أو الـ Server الذي يتم تثبيت Ansible عليه، ومن خلاله يقوم مهندس الـ DevOps بتشغيل الأوامر وكتيبات التشغيل (Playbooks). يمكن أن يكون Laptop شخصيًا أو Linux Server في معمل أو Cloud.

2.2Managed Nodes (Targets) — العقد المُدارة

الـ Servers المستهدفة بتطبيق التغييرات والإعدادات. تتلقى الـ Instructions عبر SSH وتنفذها بدون الحاجة لتثبيت Agents عليها — لهذا نسمي المعمارية Agentless.

KEY IDEAلاحظ ما لا يوجد: لا Database مركزية، لا Daemon يعمل باستمرار على الـ Targets، لا Agent يُحدَّث. Ansible يتصل عند الحاجة، ينفّذ، ثم يرحل. العبء على الـ Managed Nodes = صفر.
TASK [خريطة المكونات]component map
المكوّنما هو؟ماذا يُثبَّت عليه؟دوره
Control NodeLaptop / Linux ServerAnsible (وحده)تشغيل الأوامر والـ Playbooks
Managed NodesUbuntu / CentOS / DB…لا شيء — Python فقطاستقبال أوامر SSH وتنفيذها
WATCH OUTخطأ شائع عند المبتدئين: محاولة تثبيت Ansible على الـ Managed Nodes «احتياطًا». لا تفعل — هي لا تحتاجه إطلاقًا. الـ Control Node هو المكان الوحيد للتثبيت (سنعود له في فصل الـ Installation).
🎓 EXAMسؤال المقابلة: «صِف معمارية Ansible؟» → مكوّنان: Control Node (عليه Ansible، منه التشغيل) + Managed Nodes (تستقبل عبر SSH بلا Agents)، والقناة بينهما Key Pair. بساطة معمارية = سهولة تشغيل.

⚖️ Comparison — مقارنة طرق إدارة الـ Servers

🟡 6 MIN

تخيل أنك مهندس تدير 3 سيرفرات Linux مختلفة التوزيعات — Ubuntu، CentOS، Alpine — وتريد تثبيت Nginx عليها. ثلاث طرق أمامك، والفارق بينها فلسفة كاملة:

وجه المقارنة🖐️ Manual📜 Bash Scripts▶️ Ansible
آلية العملالدخول عبر SSH لكل Server وتنفيذ الأوامر يدويًا.كتابة Script Bash يتعرف على الـ OS وينفذ الأوامر.كتابة ملف YAML بسيط يُعرّف الـ Desired State للجميع.
السرعة والجهدبطيئة وتكثر فيها الأخطاء.تتطلب خبرة عالية في الـ Scripting.سريعة، مركزية، وSimple Syntax.
Idempotencyغير متوفرة — تدخل يدوي للتأكد.غير متوفرة تلقائيًا — شروط تُكتب يدويًا.مدعومة تلقائيًا ✓
دعم التوزيعاتتتطلب معرفة أوامر كل توزيعة (apt, yum, apk).تتطلب كتابة if/else لكل OS.الـ Modules تتكفل تلقائيًا ✓
ASIDE · المفارقةلاحظ أن Bash Scripts أذكى من Manual لكنها تتراكم: كل توزيعة جديدة = فرع if/else جديد، وكل تحديث = مراجعة كل السكربتات. Ansible يقلب المعادلة: أنت لا تكتب كيف التنفيذ — أنت تكتب ماذا تريد، وهو يعرف الـ How لكل توزيعة داخل الـ Modules.
TASK [قراءة الجدول عمليًا]reading the table

بمعايير حقيقية: لتثبيت Nginx يدويًا على الأنف الثلاثة ستحتاج 3 جلسات SSH و3 أوامر مختلفة (apt install / yum install / apk add) وتحققًا يدويًا من كل واحد. بـ Bash: Script واحد لكن بشروط تشعبية لكل Package Manager. بـ Ansible: Task واحدة — package: name=nginx state=present — تعمل على الثلاثة، وتتحقق الـ Idempotency تلقائيًا في كل Run قادم.

🎓 EXAMاحفظ أزواج المقارنة: Manual = بطء + أخطاء + لا Idempotency · Bash = مركزي لكن Scripting ثقيل + شروط يدوية · Ansible = YAML مركزي + Idempotency تلقائية + Modules تتكفل بالتوزيعات. هذه المقارنة نفسها سؤال مقابلة متكرر.

Chapter 04

🌍 Use Cases — مجالات الاستخدام الرئيسية

🟢 5 MIN

ثلاثة ميادين رئيسية تشغل فيها Ansible اليوم — الأول هو الأشهر والأهم، والثاني يحمل نقاشًا معروفًا في المجال.

4.1Configuration Management — إدارة الإعدادات

الاستخدام الأشهر والأهم: تثبيت وتحديث الـ Packages، ضبط الـ Files، وتحديث الـ Servers من مكان واحد — سواء كانت الـ Servers في Datacenter محلي أو على الـ Cloud. مئات الـ Servers، Command واحدة.

4.2Infrastructure Provisioning — بناء البنية التحتية

إنشاء وتدمير الموارد السحابية (EC2, S3, Containers) عبر الـ APIs للخدمات السحابية (AWS, Azure, GCP).

ASIDE · تنويه من المجاليُفضّل كثيرون استخدام Terraform للـ Provisioning (بناء الـ Infrastructure)، واستخدام Ansible للـ Configuration Management (إدارة ما داخل الـ Servers). فصل الاختصاص: الـ Contractor يبني، والفني يجهّز من الداخل. 🏗️🔧

4.3Network Automation — أتمتة الشبكات

ضبط وإدارة الـ Routers، الـ Switches، والـ Firewalls برمجيًا عبر بروتوكولات الأتمتة — بدل الدخول لكل جهاز شبكة يدويًا عبر واجهته.

⚙️ Installation — التثبيت وإعداد البيئة

🟢 5 MIN

يتم تثبيت Ansible فقط على الـ Control Node — قاعدة لا استثناء لها. اختر طريقك حسب نظامك:

🍎 macOS — Homebrew

$ brew install ansible

🐧 Ubuntu / Debian — apt

$ sudo apt update && sudo apt install ansible -y

🐍 Any OS — Python Pip

$ pip3 install ansible

🪟 Windows — WSL

استخدم بيئة WSL (Windows Subsystem for Linux) لتشغيل Ubuntu داخل Windows وتثبيت Ansible عليه بشكل طبيعي — ثم طبّق أمر Ubuntu أعلاه.

TASK [التحقق من التثبيت]verify installation
$ ansible --version ansible [core 2.16.3] config file = /etc/ansible/ansible.cfg python version = 3.10.12

رقم الـ Version ظهر = التثبيت نجح وأنت جاهز.

Chapter 06 · PLAY

🔐 SSH Keys — إعداد الاتصال الآمن بدون Password

🟠 8 MIN

لكي تتمكن الـ Control Node من الاتصال بالـ Managed Nodes وتنفيذ الـ Instructions تلقائيًا، يُفضَّل إعداد الاتصال عبر مفاتيح الـ SSH — الـ Public/Private Key Pair.

Play — ثلاث Steps واكتمل الاتصال
1️⃣ ssh-keygenأنشئ الـ Key Pair
──►
2️⃣ ssh-copy-idارفع الـ Public Key
──►
3️⃣ Testبلا Password ✅

6.1إنشاء الـ Key Pair على الـ Control Node

$ ssh-keygen -t rsa -b 4096

سيتم إنشاء ملفين في المجلد ~/.ssh/:

🔑 id_rsa — Private Key

الـ Private Key — يُحفظ بسريّة تامة على الـ Control Node ولا يُشارك مع أي أحد أبدًا.

🗝️ id_rsa.pub — Public Key

الـ Public Key — هو الذي يتم رفعه إلى الـ Managed Nodes. قفله لا يفتح شيئًا.

6.2نسخ الـ Public Key إلى الـ Managed Node

$ ssh-copy-id -i ~/.ssh/id_rsa.pub ubuntu@<MANAGED_NODE_IP>

6.3اختبار الاتصال بدون كلمة سر

$ ssh ubuntu@<MANAGED_NODE_IP> Welcome to Ubuntu 22.04 LTS … # logged in — no password asked ✅ $ exit
DEBUG · AWS EC2في حالة استخدام أجهزة AWS EC2، يتم استخدام ملف الـ Private Key بصيغة .pem المُقدَّم من AWS لتنسيق الاتصال الأول — والـ User غالبًا ubuntu أو ec2-user حسب الـ OS.
WATCH OUTخطآن شائعان: نسخ id_rsa (الـ Private) بدل id_rsa.pub (الـ Public) للسيرفر = لن يعمل الاتصال. ونسخ الـ Private عبر قنوات غير آمنة = ثغرة أمنية كاملة. الـ Public يسافر، الـ Private لا يتحرك أبدًا.
🎓 EXAMالتسلسل الحرفي: ssh-keygen -t rsa -b 4096 ← ssh-copy-id -i ~/.ssh/id_rsa.pub ubuntu@IP ← اختبار ssh ubuntu@IP. ومن هذه اللحظة تصبح كل أوامر Ansible القادمة صامتة تمامًا — لا Password بينك وبين الأتمتة.

🧩 Modules — وحدات التنفيذ

🟡 6 MIN

تعتمد جميع مهام Ansible على الـ Modules — وهي أدوات برمجية جاهزة تؤدي وظائف محددة. أنت لا تكتب Scripts، أنت تستدعي Modules وتعطيها الـ State المطلوبة.

TASK [أشهر الـ Modules الأساسية]core modules
Moduleوظيفته
apt / yumلإدارة وتثبيت وتحديث وحذف الـ Packages (حسب الـ Distribution).
pingلاختبار الاتصال والـ Readiness بين الـ Control Node والـ Managed Nodes.
serviceلإدارة الـ Services — start, stop, restart.
copyلنسخ الـ Files من الـ Control Node إلى الـ Managed Nodes.
command / shellلتنفيذ أوامر النظام المباشرة على الـ Servers.

الـ Modules بالمئات تغطي كل شيء تقريبًا — ويمكنك دائمًا الرجوع للوثائق الرسمية (Ansible Documentation) لمعرفة الـ Module المناسب وخياراته لكل Task.

TASK [الـ Modules الثلاثة التي ستستخدمها أولًا]start here

ping

أول Module تجرّبه — يثبت أن الاتصال يعمل. الرد الناجح دائمًا: "pong".

apt / yum

قلب إدارة الـ Packages. مع state=present يصبح الأمر Idempotent تلقائيًا.

service

يتحكم بحياة الـ Service: started, stopped, restarted — وenabled عند الـ Boot.

KEY IDEAالـ Module يخفي عنك الـ How: أنت تقول apt: name=nginx state=present — والـ Module يعرف بنفسه هل ينفّذ apt-get install فعليًا أم أن كل شيء موجود فيتجاهل. هذا هو جذر الـ Idempotency.
WATCH OUTcommand وshell قد يكونان فخًا: بهما تستطيع تجاوز كل أناقة Ansible وكتابة أوامر خام غير Idempotent. استخدمهما كملجأ أخير عندما لا يوجد Module مخصص لمهمتك.
🎓 EXAMاحفظ الخمسة الأساسيين بوظائفهم: apt/yum (Packages) · ping (Connectivity) · service (Services) · copy (Files) · command/shell (Direct commands). سؤال «ما الـ Module الذي تستخدمه لـ X؟» — من هذه القائمة تأتي الإجابات.

Chapter 08

🗂️ Inventory — ملف الـ Managed Nodes

🟡 5 MIN

ملف الـ Inventory هو الملف الذي يحتوي على الـ IPs الخاصة بالـ Managed Nodes — مقسّمة إلى Groups (مجموعات) تستهدفها في الأوامر.

TASK [مثال لملف hosts.ini]inventory example
# hosts.ini [web] 192.168.1.101 ansible_user=ubuntu 192.168.1.102 ansible_user=ubuntu [db] 192.168.1.201 ansible_user=ubuntu
DEBUG · تشريح الملف[web] و[db] = أسماء الـ Groups بين أقواس مربعة · الأسطر تحتها = الـ IPs الأعضاء · ansible_user=ubuntu = الـ SSH User المستخدم للاتصال بذلك الـ Server — تُعرَّف مرة هنا بدل تكرارها في كل Command.
TASK [كيف نستهدف؟]targeting
[web] → 2 Servers [db] → 1 Server all → 3 Servers

ansible web … يضرب Servers الويب فقط · ansible all … يضرب الجميع · استهداف بالمجموعة بدل حفظ وحشو الـ IPs يدويًا كل مرة.

KEY IDEAالـ Inventory هو «مصدر الحقيقة» لخريطة بنيتك: أضفت Server؟ سطر واحد في الـ File. غيّرت User؟ تعديل واحد. كل الـ Commands والـ Playbooks القادمة ستُحيل لهذا الملف عبر -i hosts.ini.
WATCH OUTأسماء الـ Groups حساسة تمامًا: [web] ليست [webs] ولا [Web]. خطأ حرف واحد في الاستهداف = «لا توجد Hosts مطابقة» — ورسالة الـ Error لن تنبّهك للـ Typo.
🎓 EXAMالـ Inventory = ملف يحوي IPs الـ Managed Nodes مقسمة إلى Groups · الـ Syntax: [group_name] ثم الأسطر · ansible_user يعرّف الـ SSH User · يُمرَّر دائمًا بـ -i.

Chapter 09

⚡ Ad-hoc Commands — التنفيذ الفوري

🟡 7 MIN

تُستخدم الـ Ad-hoc Commands لتنفيذ مهمة سريعة بدون الحاجة لكتابة Playbook كامل — سطر واحد مباشرة من الـ Terminal. هذا هو الجانب Imperative الذي ذكرناه في الفصل الأول.

TASK [الصيغة العامة]general syntax
ansible <group_or_all> -i <inventory_file> -m <module_name> -a "<module_arguments>"
TASK [الأمثلة العملية الثلاثة]practical examples

1️⃣ فحص الاتصال — ping لكل الـ Servers:

$ ansible all -i hosts.ini -m ping 192.168.1.101 | SUCCESS => { "ping": "pong" } 192.168.1.102 | SUCCESS => { "ping": "pong" } 192.168.1.201 | SUCCESS => { "ping": "pong" }

2️⃣ معرفة الـ Uptime لـ Servers الويب — المجموعة web:

$ ansible web -i hosts.ini -a "uptime"
DEBUGملاحظة ذكية: عند عدم تحديد -m يتم استخدام الـ command Module افتراضيًا — لهذا كتبنا uptime مباشرة في -a دون تحديد Module.

3️⃣ التأكد من تثبيت Nginx على جميع الـ Servers:

$ ansible all -i hosts.ini -m apt -a "name=nginx state=present" --become
KEY IDEA--become = صلاحيات root (مثل sudo) — الـ Installation يحتاجها دائمًا. وstate=present هي لغة الـ Idempotency: «تأكد أنه موجود» — موجود أصلًا؟ لا شيء يحدث إطلاقًا.
WATCH OUTمتى Ad-hoc ومتى Playbook؟ Ad-hoc لمهمة سريعة ولن تتكرر — فحص، Restart، استعلام. أول ما تشعر أن الـ Command سيُعاد لاحقًا أو يُشارك مع الفريق → انقله فورًا إلى Playbook (الفصل القادم).
🎓 EXAMاحفظ الهيكل بالترتيب: Target ← Inventory (-i) ← Module (-m) ← Arguments (-a) ← Become. وسؤال الفهم الكلاسيكي: «لماذا لم نكتب -m command في مثال uptime؟» — لأنه الـ Module الافتراضي.

📜 YAML Basics — أساسيات الصيغة

🟡 7 MIN

تعتمد لغة YAML على الـ Indentation (المسافات البادئة) — ليست لغة برمجة بل طريقة مرتبة لوصف الـ Data. إتقان قواعدها = كتابة Playbooks بلا صداع.

WATCH OUT · القاعدة الأهملا تستخدم Tab أبدًا — استخدم مسافتين (Spaces) دائمًا. خلط Tab مع Spaces هو أكثر سبب لفشل ملفات YAML عند المبتدئين، والـ Error يظهر بعيدًا عن سطره الحقيقي فيصعب تتبعه.
TASK [القاعدة الأولى]document start

تبدأ الملفات دائمًا بثلاث شرطات --- — إعلان بداية الـ YAML Document:

---
TASK [هياكل البيانات الثلاثة]data structures

① Key-Value

name: Ahmed

مفتاح وقيمة — أبسط بنية.

Chapter 11 · PLAY

📖 Playbooks — كتابة وتشغيل

🟠 9 MIN

الـ Playbook هو ملف YAML يحتوي على مجموعة من الـ Plays، وكل Play تحتوي مجموعة من الـ Tasks — لتنفيذ سيناريو Automation كامل على مجموعة Servers محددة. هذا هو قلب Ansية النابض.

Hierarchy — التسلسل الهرمي
Playbooksite.yml
◂ يحتوي
Playshosts · become
◂ تحتوي
Taskssteps
◂ تستدعي
Modulesapt · service
TASK [مثال: Playbook لتثبيت وتشغيل Apache]أنشئ ملف site.yml
--- - name: Install and Start Apache Web Server hosts: web become: yes tasks: - name: Install Apache Package apt: name: apache2 state: present - name: Ensure Apache Service is Running and Enabled service: name: apache2 state: started enabled: yes
TASK [تشغيل الـ Playbook]execute it
$ ansible-playbook -i hosts.ini site.yml PLAY [Install and Start Apache Web Server] TASK [Gathering Facts] ok: [192.168.1.101] TASK [Install Apache Package] changed: [192.168.1.101] TASK [Ensure Apache Service is Running and Enabled] changed: [192.168.1.101] PLAY RECAP 192.168.1.101 : ok=3 changed=2 failed=0
DEBUG · قراءة سطرًا بسطرhosts: web → استهدف Group الـ web من الـ Inventory · become: yes → نفّذ بصلاحيات root · كل Task = Name وصفي + Module + State مطلوبة. لاحظ الصياغة: لا نقول «ثبّت» بل «اجعله present».
PROOFشغّله مرة ثانية الآن. النتيجة: changed=0 وكل الـ Tasks ok — الـ Idempotency حيّة أمام عينيك: الـ State متحققة فلا تغيير. ♻️

Chapter 11·b

🧹 Playbooks — الإزالة وقراءة النتائج

🟡 7 MIN

نفس القوة التي تُثبّت تُزيل — بعكس الـ State فقط. ثم نتقن قراءة مؤشرات النتائج الثلاثة.

TASK [Playbook لإيقاف وحذف Apache]remove playbook
--- - name: Stop and Remove Apache Web Server hosts: web become: yes tasks: - name: Stop Apache Service service: name: apache2 state: stopped - name: Remove Apache Package apt: name: apache2 state: absent
KEY IDEAالترتيب العكسي المنطقي: نوقف الـ Service أولًا ثم نحذف الـ Package — حذف حزمة والـ Service الخاصة بها تعمل = سلوك غير متوقع. وكلمة السر كلها في الـ state: present / absent / started / stopped — أربع Values تحكم العالم.
TASK [مؤشرات النتائج]result indicators
المؤشراللونالمعنى
okأخضرالـ Server في الـ Desired State بالفعل — لم يتطلب تغييرًا.
changedأصفرتم إجراء الـ Change بنجاح على الـ Server.
failedأحمرحدث Error في الـ Task — توقف التنفيذ على ذلك الـ Server.
RESCUED · لو ظهر failedاقرأ اسم الـ Task الأحمر أولًا — يخبرك أي Step فشلت، ثم السطر أسفلها — يخبرك لماذا (شبكة؟ Permissions؟ اسم Package خاطئ؟). 90% من الأعطال تُحل من هذه السطور دون أي بحث خارجي.
🎓 EXAMالفرق الجوهري بين ok وchanged هو جوهر فلسفة Ansible: ok = الـ State متحققة مسبقًا (الـ Idempotency تعمل)، changed = عمل حقيقي تم الآن. وقراءة failed تبدأ من اسم الـ Task + الـ Error Message تحته.

Chapter 12

🎭 Roles & Galaxy — التنظيم والمشاركة

🟡 7 MIN

عندما تكبر مشاريع الـ Automation، يصبح وضع جميع المهام والتعليمات في ملف Playbook واحد صعب الصيانة. تعطينا Ansible Roles هيكلية مجلدات قياسية لتنظيم الـ Project وتجزئته إلى مكونات Modular & Reusable.

TASK [الهيكل التنظيمي للـ Role]role structure
my_role/ ├── tasks/ # main.yml — الـ Tasks الرئيسية ├── handlers/ # الـ Tasks المشروطة (Handlers) ├── templates/ # قوالب Jinja2 ├── files/ # الملفات الثابتة المراد نقلها ├── vars/ # الـ Variables الخاصة بالـ Role ├── defaults/ # الـ Variables الافتراضية └── meta/ # معلومات عن الـ Role والاعتمادات
KEY IDEAالـ Role = Encapsulation — تغليف. بدل Playbook من 200 سطر، تستدعي Role باسمه، وكل من يقرأ الـ Project يفهم الـ Structure فورًا لأن الجميع يعرف هذا الهيكل القياسي.
TASK [منصة Ansible Galaxy]galaxy

مستودع رسمي مفتوح المصدر يُمكّنك من مشاركة وتنزيل الـ Roles والـ Collections الجاهزة المبنية من قبل مجتمع Ansible — لتسريع عمليات الـ Development والأتمتة. بدل بناء Role لـ Apache من الصفر: ابحث في Galaxy، نزّل، وعدّل لاحتياجك.

galaxy.ansible.com Ready-made Roles Collections Community-driven
WATCH OUTمتى تكتب Role بدل Playbook؟ قاعدة عملية: أول Playbook لك = Playbook عادي. عندما يبدأ الملف بالتكرار أو تجد نفس الـ Tasks في Projects متعددة = وقت التجزئة إلى Roles. لا تبدأ بالتعقيد.
🎓 EXAMاجمع رسالة الكتاب كلها في جملة — سؤال الـ Interview الختامي: «ما Ansible؟» → أداة Agentless Automation عبر SSH، بـ YAML Declarative Syntax للـ Desired State، تتسم بالـ Idempotency، تنظم عملها بـ Inventory وPlaybooks وتتوسع بـ Roles وGalaxy.
