CH 01

🪜 The Exposition Ladder

🟢 4 MIN

Three ways to reach a Service, each one delegating to the one below it. Book 01 showed the first two — this chapter frames them as a ladder, because every rung exists to fix the rung beneath.

The ladder — top is for humans, bottom is machinery
⚖️ LoadBalancercloud LB · one public IP
🚪 NodePort30000–32767 on every node
🕸️ ClusterIPinternal virtual IP only

LB forwards to NodePorts · NodePorts forward through kube-proxy DNAT to Pods — each rung hides the one below

RungReachKills it
ClusterIPinside the cluster onlyliterally unreachable from outside
NodePortany node's IP + a high portraw ports, users hate :30080, no LB across nodes, no TLS story
LoadBalancerone cloud IP per Service$$$ per Service — 10 services = 10 LB bills, and still no path routing
🔑
One sentence: the ladder is a delegation chain — LoadBalancer → NodePort → ClusterIP → Pods. NodePort solved reachability but not usability; LoadBalancer solved usability but not your cloud invoice. The next rung up — Ingress — fixes the invoice.

CH 03

💡 The Problem Ingress Solves

🟢 4 MIN
❌ Naive: one LB per Service
cloud LB #1 → web-svc cloud LB #2 → api-svc cloud LB #3 → admin-svc cloud LB #4 → docs-svc $ × 4 · TLS certs × 4 · WAF × 4 · no shared path rules · bill pain
✅ Ingress: one edge, many routes
cloud LB (just 1) └── Ingress controller ├── shop.example.com → web-svc ├── example.com/api → api-svc ├── example.com/admin → admin-svc └── docs.example.com → docs-svc 1 bill · 1 TLS cert · L7 rules as YAML

Ingress is Layer-7 awareness at the edge: it reads the HTTP hostname and path and routes accordingly — something NodePort/LoadBalancer (dumb TCP forwards) fundamentally cannot do.

Apartment update: LoadBalancer built every visitor their own private bridge to one apartment. Ingress hired a front desk: one entrance, a directory, and it reads the address on your letter to send you to the right apartment.
🔑
One sentence: Ingress consolidates N cloud load balancers into one, and upgrades dumb port-forwarding into hostname/path-aware HTTP routing — declared as plain YAML, versioned with your app.

CH 04

🚦 Ingress & IngressClass

🟡 6 MIN · CORE

Two facts before any YAML: (1) an Ingress is just a rulebook — nothing forwards traffic until a controller reads it; (2) ingressClassName declares which controller owns it.

apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: main spec: ingressClassName: nginx # which referee handles this rulebook rules: - host: demo.local http: paths: - path: / pathType: Prefix backend: service: { name: web, port: { number: 80 } }
PieceRoleApartment translation
Ingressthe routing rulebook ( declarative YAML)the front-desk directory
IngressClassnamed type of controller; routes rulebooks to refereeswhich security firm staffs the desk
Ingress Controlleractual reverse proxy watching Ingress objectsthe desk itself
⚠️
The silent trap: kubectl apply an Ingress with no controller installed and you get zero errors — the object is stored, accepted, and does nothing. The classic symptom: Ingress exists, get ingress shows no ADDRESS, curl hangs. Check kubectl get ingressclass first.
# minikube — one command installs ingress-nginx + the "nginx" IngressClass: $ minikube addons enable ingress $ kubectl get pods -n ingress-nginx ingress-nginx-controller-xxxxx  1/1  Running
🔑
Rulebook vs referee: the Ingress object states intent; the controller is the running reverse proxy that enforces it. Kubernetes ships the grammar — you supply the proxy.

CH 05

🛣️ Host & Path Routing

🟡 6 MIN · CORE

The full routing surface: multiple hosts, each with multiple paths, each pointing at its own Service.

spec: ingressClassName: nginx rules: - host: shop.example.com # name-based virtual host http: paths: - path: /api pathType: Prefix backend: { service: { name: api-svc, port: { number: 80 } } } - path: / pathType: Prefix backend: { service: { name: web-svc, port: { number: 80 } } } - host: docs.example.com # second host, same edge http: paths: - path: / pathType: Prefix backend: { service: { name: docs-svc, port: { number: 80 } } }
pathTypeMatches/api/v1?
Prefixpath and everything under it, by segments✅ yes (for /api)
Exactonly the literal path❌ no — only /api itself
ImplementationSpecificcontroller decides (nginx treats it like Prefix + regex support)controller-defined
  • 🧮 Order doesn't matter — nginx sorts by longest-prefix, so /api wins over / no matter where it's listed
  • 🎯 No host field at all = catch-all for every hostname hitting the edge (handy, but easy to shadow specific rules — be deliberate)
💡
Testing locally: map the hostname in /etc/hosts → <minikube-ip> demo.local shop.example.com, then plain curl http://shop.example.com/api. No DNS purchased — the Host header does the routing.
🔑
Mental model: hosts are apartments in the directory, paths are rooms within them. One edge serves the whole building — the request's Host header is the mailman reading the label.

CH 06

🔐 TLS Termination

🟡 5 MIN

"Termination" = the TLS handshake ends at the ingress. Users get HTTPS; your Pods receive plain HTTP on the internal network. One cert, managed once, at the edge.

spec: tls: - hosts: [shop.example.com] secretName: shop-tls # type kubernetes.io/tls (Book 02 · CH 05) rules: - host: shop.example.com http: paths: - path: / pathType: Prefix backend: { service: { name: web-svc, port: { number: 80 } } } # plain HTTP here!
# the secret the edge serves (self-signed for labs — Lab 2 does it live): $ openssl req -x509 -nodes -newkey rsa:2048 -days 365 \ -keyout tls.key -out tls.crt -subj "/CN=shop.example.com" $ kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key
Termination point
🌍 HTTPS 🔒
──►
Ingress🔒 decrypts here
──►
HTTP (plain)
──►
🫛 Pod :80
  • 🔁 Re-encryption (HTTPS all the way to Pods) is possible but controller-specific — check before promising "end-to-end encrypted" in a security review
  • 🎟️ Production certs come from cert-manager (Let's Encrypt automation) — same secretName mechanism, the cert just appears
  • ⚠️ Missing/expired secret named in tls → nginx serves a fake default cert; browsers scream. Diagnose: check the cert issuer, not just the padlock
🔑
One sentence: TLS terminates at the edge — the padlock in the user's bar is the Ingress's certificate; inside the cluster, traffic rides the private network as HTTP unless you deliberately re-encrypt.

CH 07

🧭 Ingress Controllers

🟡 6 MIN · CORE

A controller is a reverse proxy in a Pod + a reconciliation loop: watch Ingress objects → render proxy config → hot-reload. The ingress-nginx controller literally writes an nginx.conf for your rulebook.

Ingress objects (the rulebooks) │ watch ▼ Controller Pod render config → reload proxy │ ▼ nginx/traefik/haproxy the process actually serving :80/:443
ControllerUnderlying proxyKnow it for
ingress-nginxnginxthe de-facto standard; huge annotation ecosystem; minikube addon
Traefiktraefik (Go)CERT-by-default ACME, CRD-native, popular in homelab/k3s
HAProxyhaproxyraw TCP performance pedigree
AWS ALB / GCEmanaged cloud LBIngress provisions real ALB/GLB instead of in-cluster proxy
⚠️
Annotation culture — power and trap: behavior beyond core routing (rewrites, CORS, IP allowlists, timeouts) arrives via per-controller annotations, e.g. nginx.ingress.kubernetes.io/rewrite-target: /. Powerful — but non-portable: swap controllers and those annotations are silently meaningless. K8s-native versions of some of this live in the Gateway API (CH 13).
💡
Which nginx is which? ingress-nginx = community/kubernetes project. nginx-ingress = F5/NGINX Inc's separate product. Same proxy core, different projects, different annotations — a classic interview gotcha.
🔑
One sentence: the controller is the muscle behind the rulebook — pick one, pin its IngressClass, and treat its annotations as vendor glue to be minimized.

🔓 The Default-Allow World

🟡 5 MIN

Book 01 built the flat network: every Pod gets a routable IP and — by default — may talk to every other Pod. Frontend to database, and your-laptop-sidecar to database, all equally welcome.

No NetworkPolicy = zero segmentation
🫛 frontend
──►
🫛 payment-api
──►
🗄️ postgres:5432
💀 any compromised pod same rights!
──►
🗄️ postgresdirect line 😱
AssumptionReality
"Only my Services can reach my Pods"❌ Services are for discovery — Pod-to-Pod by raw IP works regardless
"Namespaces isolate the network"❌ Book 01 · CH 11: namespaces partition names, not traffic — cross-namespace Pod calls flow freely by default

CH 09

🚧 NetworkPolicy — Ingress Rules

🟡 6 MIN · CORE

The grammar in one sentence: "Pods selected by podSelector may receive connections only from allowed sources, only on allowed ports." The instant one policy selects a Pod, default-allow flips to default-deny for that Pod.

apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: allow-frontend-to-api namespace: shop spec: podSelector: # THE TARGET — who is being protected matchLabels: { app: api } policyTypes: [Ingress] ingress: - from: # allowed SOURCES (any of these) - podSelector: # same-namespace pods with… matchLabels: { app: frontend } - namespaceSelector: # …OR all pods from matching namespaces matchLabels: { kubernetes.io/metadata.name: monitoring } ports: - { protocol: TCP, port: 8080 } # …only this port
⚠️
The AND/OR trap (interview favorite): inside one from list item, podSelector + namespaceSelector = AND (pods matching this label in those namespaces). Across separate items = OR (either source). One character of YAML indentation changes the security meaning.
  • ➕ Policies are additive: if two policies select the same Pod, the allowed set is the union — policies can only ever add permission, never subtract
  • 🎯 Empty podSelector: {} = every Pod in the namespace (no matchLabels field at all)
🔑
Carry the four questions: who's protected (podSelector)? who may call (from)? on what ports? and does a second policy union with this one? — that's 90% of every NetworkPolicy review.

CH 10

🚫 Egress + The Default-Deny Playbook

🟡 6 MIN · CORE

Same grammar, opposite direction. And the industry-standard starting posture: deny everything, then allow named flows.

kind: NetworkPolicy metadata: { name: default-deny-all, namespace: shop } spec: podSelector: {} # every pod in shop policyTypes: [Ingress, Egress] ingress: [] # empty = deny ALL inbound egress: [] # empty = deny ALL outbound
⚠️
The classic default-deny self-own: deny-all egress instantly kills DNS — no pod can resolve anything. The very first egress allow in any cluster is DNS:
kind: NetworkPolicy metadata: { name: allow-dns } spec: podSelector: {} policyTypes: [Egress] egress: - to: - namespaceSelector: matchLabels: { kubernetes.io/metadata.name: kube-system } ports: - { protocol: UDP, port: 53 } - { protocol: TCP, port: 53 }

📋 The production playbook

1 · default-deny all
→
2 · allow DNS :53
→
3 · allow app flows frontend→api, api→db
→
4 · allow ingress-ctrl → apps
⚠️
CNI reality check: NetworkPolicy is just an API — the CNI plugin must enforce it. Calico, Cilium, Weave enforce; flannel does not (policies apply silently, block nothing). If policies "don't work", check your CNI before your YAML. Verify with Lab 3, not with hope.
🔑
One sentence: default-deny + explicit allows = the Kubernetes zero-trust baseline — and rule #1 of deny-all egress is allow DNS first or nothing works and everything looks broken.

CH 11

📮 CoreDNS — Discovery Internals

🟡 6 MIN · CORE

Book 01 asserted "every Service gets a DNS name." Here's the machinery: a CoreDNS Deployment in kube-system, fronted by the kube-dns Service — the cluster's phone book.

Pod resolv.conf → nameserver 10.96.0.10 │ query: "v1.default…" ▼ kube-dns Service (ClusterIP, stable — dogfooding!) ▼ CoreDNS Pods watch API Server → build zone in memory ▼ svc.cluster.local zone every Service & Pod IP, auto
# the cluster zone lives in a ConfigMap — the "Corefile": $ kubectl -n kube-system get cm coredns -o yaml Corefile: | .:53 { kubernetes cluster.local # ← serves the cluster zone from the API forward . /etc/resolv.conf # everything else → upstream DNS }
Query formResolvesWorks from
v1same namespacepods in default (search list fills the rest)
v1.devService v1 in ns devanywhere
v1.dev.svc.cluster.localfull FQDNanywhere (always works)
  • 🪄 Zero registration: "create a Service" is the DNS record — CoreDNS watches the API, no sidecar config
  • 🔎 It also serves Pod records (ip-10-244-1-5.default.pod.cluster.local) and SVC/AAAA types — headless Services return Pod IPs directly
🔑
One sentence: CoreDNS is a small API-watching DNS server — the reason service discovery needs no setup, and the reason a broken kube-dns Service makes the entire cluster feel dead.

🔧 dnsPolicy & DNS Debugging

🟡 6 MIN · CORE
dnsPolicyPod uses…When
ClusterFirst defaultCoreDNS (cluster names + forwarded externals)99% of Pods
Defaultthe node's resolv.conf — no cluster names!rare; e.g. heavy external-DNS workloads
ClusterFirstWithHostNetCoreDNS even for hostNetwork PodshostNetwork daemons that still need Service names
Nonewhatever dnsConfig suppliesfull manual control (custom nameservers/search)

🪤 ndots:5 — the sneaky perf tax

# a default pod's resolv.conf: search default.svc.cluster.local svc.cluster.local cluster.local options ndots:5 # any name with <5 dots is tried AS-IS *and* against every search # suffix → "google.com" = 1 + 3 = 4 queries. measure, don't guess.

🩺 The debug ladder (Lab 4 runs it live)

$ kubectl exec dns -- nslookup v1 # 1 · short name (same ns) $ kubectl exec dns -- nslookup v1.dev # 2 · cross-namespace $ kubectl exec dns -- nslookup kubernetes.default # 3 · the built-in canary $ kubectl exec dns -- cat /etc/resolv.conf # 4 · who's my resolver?
  • ✅ FQDN resolves but short name fails → search list/ndots issue, not DNS death
  • ✅ nothing resolves + timeouts → check CoreDNS Pods (-n kube-system) and the kube-dns Service endpoints
🔑
One sentence: ClusterFirst quietly gives every Pod the cluster phone book plus upstream forwarding — and every "DNS is down" incident is solved by the four-command ladder above, in order.

CH 13

🛣️ Gateway API — The Successor

🔵 OVERVIEW

Ingress won the world but shows its age: routing power locked behind vendor annotations, cross-namespace routing unsafe, one blob of YAML mixing infra and app concerns. The Gateway API (SIG-Network, GA since v1.0) is the redesigned successor.

Ingress (2015 model)
  • behavior via per-controller annotations 🩹
  • cross-namespace = footgun territory
  • platform + app concerns in one object
  • not going away — huge installed base
Gateway API
  • native fields — headers, weights, method routing
  • cross-namespace via explicit ReferenceGrant
  • role-split objects (see below)
  • portable: any conforming implementation
# role separation — the headline idea: GatewayClass # platform team: "we run nginx-gateway" Gateway # platform team: listener :443 + TLS cert HTTPRoute # APP team: my host/path → my svc ← attaches to the Gateway # (+ GRPCRoute, TLSRoute… — and app teams never touch LB config)
kind: HTTPRoute metadata: { name: shop } spec: parentRefs: [{ name: edge-gateway }] # bind to the shared Gateway hostnames: [shop.example.com] rules: - matches: [{ path: { type: PathPrefix, value: /api }}] backendRefs: [{ name: api-svc, port: 80, weight: 90 }] - backendRefs: [{ name: web-svc, port: 80 }] # canary: weight 10
💡
Adoption note: needs a Gateway-API controller installed (nginx-gateway, Envoy Gateway, Traefik v3+…). Guidance for new designs: prototype on Ingress today, keep annotations minimal, know your escape hatch is Gateway API — Book 08's GitOps tooling speaks both.
🔑
One sentence: Gateway API keeps Ingress's job but fixes its politics — infrastructure (Gateway) owned by platform teams, routes (HTTPRoute) owned by app teams, with portability and canary weights as first-class citizens.

🔬 Path Routing via Ingress

🟠 15 MIN · HANDS-ON
STEP 1 · Controller + two apps
$ minikube addons enable ingress $ kubectl create deploy v1 --image=hashicorp/http-echo -- -text=hello-v1 $ kubectl create deploy v2 --image=hashicorp/http-echo -- -text=hello-v2 $ kubectl expose deploy v1 --port=5678 && kubectl expose deploy v2 --port=5678 # printf-style echo servers: perfect for proving WHO answered

$ kubectl apply -f - <<EOF apiVersion: networking.k8s.io/v1 kind: Ingress metadata: { name: routes } spec: ingressClassName: nginx rules: - host: demo.local http: paths: - { path: /v1, pathType: Prefix, backend: { service: { name: v1, port: { number: 5678 } } } } - { path: /v2, pathType: Prefix, backend: { service: { name: v2, port: { number: 5678 } } } } EOF

👀 TEST
$ curl demo.local/v1 hello-v1 $ curl demo.local/v2 hello-v2  # path → service, proven $ curl demo.local/v1/extra hello-v1  # Prefix catches subpaths
🔍 PROOF IT'S L7
# same port 80 for both — # only the PATH differed. # A NodePort could never do # this without 2 services # on 2 ports.

🔐 TLS on an Ingress

🟠 10 MIN · HANDS-ON
STEP 1 · Cert + Secret (Book 02 · CH 05 in action)
$ openssl req -x509 -nodes -newkey rsa:2048 -days 365 \ -keyout tls.key -out tls.crt -subj "/CN=demo.local" $ kubectl create secret tls demo-tls --cert=tls.crt --key=tls.key
STEP 2 · Add the tls block to the Lab 1 Ingress
$ kubectl patch ingress routes --type=merge -p \ '{"spec":{"tls":[{"hosts":["demo.local"],"secretName":"demo-tls"}]}}' $ kubectl get ingress routes HOSTS     PORTS     AGE demo.local  80, 443  # 443 appeared
👀 TEST HTTPS
$ curl -k https://demo.local/v1 hello-v1  # works! (-k: self-signed)
🔍 INSPECT THE CERT
$ curl -kv https://demo.local 2>&1 | grep subject subject: CN=demo.local # the EDGE serves your secret — # pods never saw a cert

Proved: termination happens at the Ingress (CH 06) — one self-signed secret, HTTPS at the edge, plain HTTP behind. Teardown: Lab 1 teardown + kubectl delete secret demo-tls.

LAB 3

🚧 Default-Deny → Selective Allow

🟠 12 MIN · HANDS-ON
⚠️
CNI check first: minikube default (bridge/kindnet) does not enforce policies. Restart with Calico, or run this lab on a cluster whose CNI enforces: minikube delete && minikube start --cni=calico.
STEP 1 · Players: a server, a labeled client, an unlabeled client
$ kubectl create deploy v1 --image=hashicorp/http-echo -- -text=hello-v1 $ kubectl expose deploy v1 --port=5678 $ kubectl run client --image=busybox:1.36 --restart=Never -- sleep 9999 $ kubectl run stranger --image=busybox:1.36 --restart=Never -- sleep 9999
STEP 2 · Deny all ingress to v1
$ kubectl apply -f - <<EOF apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: deny-v1 } spec: podSelector: { matchLabels: { app: v1 } } policyTypes: [Ingress] ingress: [] EOF $ kubectl exec client -- wget -qO- -T 3 http://v1:5678 wget: download timed out  # ← BLOCKED. the room has a wall.
STEP 3 · Allow only labeled callers
$ kubectl apply -f - <<EOF apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: allow-labeled } spec: podSelector: { matchLabels: { app: v1 } } ingress: - from: [{ podSelector: { matchLabels: { access: "true" } } }] EOF $ kubectl label pod client access=true $ kubectl exec client -- wget -qO- http://v1:5678   # now labeled hello-v1  # ✅ allowed $ kubectl exec stranger -- wget -qO- -T 3 http://v1:5678 wget: download timed out  # ❌ still denied — labels are the keys

Proved: policy selects the server; pod labels select the callers; union of policies; enforcement is CNI-dependent. Teardown: kubectl delete np deny-v1 allow-labeled && kubectl delete pod client stranger && kubectl delete deploy v1 && kubectl delete svc v1

GLOSS

📚 Glossary

🔵 REFERENCE
Exposition ladder — ClusterIP → NodePort → LoadBalancer; each rung delegates to the one below.
LoadBalancer — Service type; a cloud controller provisions an external LB fronting NodePorts. One per Service = one bill per Service.
MetalLB / minikube tunnel — ways to get LB behavior without a cloud (bare metal / local dev).
Ingress — L7 routing rulebook (host/path → Service); inert without a controller.
IngressClass — named controller type; spec.ingressClassName binds an Ingress to its referee.
Ingress Controller — running reverse proxy (ingress-nginx, Traefik…) that watches Ingress objects and renders live proxy config.
pathType — Prefix (segment + subtree) / Exact (literal) / ImplementationSpecific.
TLS termination — HTTPS ends at the Ingress; Pod traffic is plain HTTP unless re-encrypted deliberately.
Annotation — controller-specific behavior knob (rewrites, CORS…); powerful, non-portable.
NetworkPolicy — namespaced firewall rules: podSelector (target) + ingress/egress (from/to/ports); additive union; CNI-enforced.
Default-deny — posture where a selected Pod receives/sends nothing unless a policy allows it; empty rules array = deny all.
ipBlock / namespaceSelector / podSelector (in from/to) — the three source/destination selector types.
CoreDNS — cluster DNS Deployment in kube-system behind the kube-dns Service; serves svc.cluster.local by watching the API.
FQDN of a Service — <name>.<namespace>.svc.cluster.local; short names rely on the search list.
ndots:5 — resolv.conf option causing search-list expansion; the hidden cost behind "slow external names".
dnsPolicy — ClusterFirst (default) / Default (node's resolver) / ClusterFirstWithHostNet / None + dnsConfig.
Gateway API — GA successor to Ingress: GatewayClass + Gateway (platform-owned) and HTTPRoute (app-owned), portable and cross-namespace-safe via ReferenceGrant.
