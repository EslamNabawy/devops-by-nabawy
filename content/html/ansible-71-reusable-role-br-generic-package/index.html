Section 01

🎯 Task Goal — and the 5 Objectives

🟢 5 MIN

Build a production-style Ansible project using a single generic, reusable role — generic_package — to install and configure any Linux package on target hosts. The project must use correct structure (ansible.cfg, inventory, site.yml, roles/), use roles instead of flat playbook tasks, and be fully idempotent, testable, and reusable.

KEY IDEA · Expected resultAfter ansible-playbook site.yml: nginx is installed, running, enabled at boot, and serves a styled HTML page at http://localhost showing the deployed package, host, service, and port.
TASK [The 5 Objectives]complete = all 5 done
1

Correct project structure

Standard Ansible layout — ansible.cfg (inventory, roles_path, become, ssh key), inventory.ini (web + local groups), site.yml calling the role, legacy flat playbooks kept for comparison, and roles/generic_package/ with tasks, handlers, 3 templates, defaults, vars, meta.

2

Generic role behavior — driven entirely by variables

8 variables control everything: package_name (default nginx) · service_name (defaults to package name) · service_state (started) · service_enabled (true) · package_state (present) · app_port (80) · template_enabled (false) · custom_index_content (fallback page text). Same role call + different vars = nginx, apache2, or anything else — without editing the role.

3

All Ansible concepts used correctly

Variable priority: defaults (lowest) vs vars (high) vs playbook vars vs -e (highest) · Handlers: Restart + Reload — once at end of play, only if notified, ignore_errors so one bad service doesn't abort · Templates: nginx.conf.j2, app.conf.j2 (with if package_name logic), index.html.j2 (styled page) · Idempotency: run twice → second run reports ok, not changed.

4

Deploy proof with nginx

site.yml calls the role with package_name: nginx, service_name: nginx, app_port: 80, template_enabled: false. Nginx installs, starts, stays enabled — and the custom index lands at /var/www/html/index.html plus /var/www/eslam/index.html (eslam.com vhost test in WSL).

5

Verified with the full command loop

All four checks green: ① --syntax-check passes · ② --check --diff dry-run shows expected counts with no real changes · ③ the real run installs and starts everything · ④ curl http://localhost/ returns the styled page from index.html.j2.

Steps 5–7

⚙️ vars Lock · Tasks · Handlers

🟠 8 MIN
5

Write role vars — roles/generic_package/vars/main.yml

High-priority lock — commented out = nothing locked in this lab, so playbook vars win:

--- # package_name: nginx # service_name: nginx
WATCH OUTUncomment those two lines and nothing in the playbook can override them — vars/ beats playbook vars in precedence. That's the lock's power and its danger: use it only when a value must never be tuned.
6

Write role tasks — tasks/main.yml (order matters)

--- - name: Update apt cache (Debian/Ubuntu) apt: update_cache: yes cache_valid_time: 3600 when: ansible_os_family == "Debian" - name: Install package {{ package_name }} package: name: "{{ package_name }}" state: "{{ package_state }}" notify: Restart service - name: Ensure service {{ service_name }} is {{ service_state }} and enabled={{ service_enabled }} service: name: "{{ service_name }}" state: "{{ service_state }}" enabled: "{{ service_enabled }}" when: service_name is defined and service_name | length > 0 ignore_errors: true

1️⃣ apt cache (Debian only, valid 1h) → 2️⃣ install {{ package_name }} with {{ package_state }}, notify Restart → 3️⃣ service task guarded by when so non-service packages don't break it. (The template/index tasks from the spec land with Step 8's templates.)

7

Write role handlers — handlers/main.yml

--- - name: Restart service service: name: "{{ service_name }}" state: restarted ignore_errors: true - name: Reload service service: name: "{{ service_name }}" state: reloaded ignore_errors: true

Run once at end of play, only if notified — and ignore_errors keeps one bad service from aborting the play.

KEY IDEAThree safety patterns in 20 lines: the when guard makes service management optional per package (a CLI tool with no service won't fail the play) · ignore_errors on both service touchpoints means one misbehaving service degrades, never aborts · and notify keeps restarts change-triggered, not blind.

Steps 8–10

📄 Templates · meta · site.yml

🟠 8 MIN
8

Write the three templates

app.conf.j2 — nginx-specific config when package_name == "nginx", generic comment otherwise:

{% if package_name == "nginx" %} user www-data; worker_processes auto; pid /run/nginx.pid; events { worker_connections {{ worker_connections | default(1024) }}; } http { sendfile on; include /etc/nginx/mime.types; default_type application/octet-stream; server { listen {{ app_port | default(80) }}; root /var/www/html; index index.html; location / { try_files $uri $uri/ =404; } } } {% else %} # Generic config for {{ package_name }} {% endif %}

index.html.j2 — styled landing page showing package name, service name, host, port, and a live "Service Active & Enabled" status badge (gradient CSS, info boxes, pulse animation). nginx.conf.j2 — plain distro-style variant using worker_connections | default(1024) and app_port | default(80).

9

Write role metadata — meta/main.yml

--- galaxy_info: author: ansible description: Generic package installer - install any package (nginx, apache2, redis, etc.) license: MIT min_ansible_version: 2.9 platforms: - name: Ubuntu versions: [focal, jammy] - name: Debian versions: [bullseye, bookworm] galaxy_tags: [package, system, generic] dependencies: []
10

Write the main playbook — site.yml

--- - name: Install nginx via generic role hosts: all become: true roles: - role: generic_package vars: package_name: nginx service_name: nginx app_port: 80 template_enabled: false
KEY IDEAStep 8's {% if package_name == "nginx" %} is a Role-level fork: nginx gets a real server config, everything else gets a documented generic stub — same template, two behaviors, decided by the very variable that drives the install. That's generic packaging done properly.

Steps 11–13

🧪 Check · Dry Run · Real Run

🟠 8 MIN
11

Syntax and inventory checks

$ ansible-playbook site.yml -i inventory.ini --syntax-check $ ansible -i inventory.ini all --list-hosts $ ansible-inventory -i inventory.ini --graph

① Playbook parses without errors · ② every host listed · ③ groups render as [web] / [local] trees.

12

Dry run — no changes, show diff

$ ansible-playbook site.yml -i inventory.ini --limit localhost --check --diff -v

Expected: install/template/index tasks report changed (dry), the config template task reports skipping — because template_enabled: false.

13

Real run

# localhost with sudo prompt $ ansible-playbook site.yml -i inventory.ini --limit localhost --ask-become-pass -v # as root in WSL (no password) $ sudo ansible-playbook site.yml -i inventory.ini --limit localhost -v
PROOF · Run it TWICEThe second run must report ok everywhere — idempotency proof. First run: changed (things installed) · second run: ok (nothing left to do). If the second run still says changed, something in the tasks is non-idempotent — fix before continuing.
The three-gate testing ladder
① syntax-check parses ✓ ──► ② --check --diff predicts, touches nothing ──► ③ real run ×2 applies, then proves idempotent
DEBUG · Why this ladder worksEach gate catches a different class of failure: syntax errors cost seconds, prediction errors cost a dry run, idempotency violations cost one extra real run. Reaching the real run with all three green means the blast radius of any remaining bug is nearly zero.
🎓 EXAMThe gates in order: --syntax-check → --check --diff (expect changed + skipped-for-template_enabled) → real run twice (changed → ok). And --limit localhost keeps the first tests off the remote web hosts.

🧬 Variable Precedence + Role Anatomy

🟡 7 MIN

Objective 3's trickiest concept: who wins when the same variable is set in several places? Ansible's answer is a precedence ladder — and this role uses every rung of it.

The precedence ladder — lowest to highest
defaults/LOWEST — the fallback
◄ loses to
vars/HIGH — the lock
◄ loses to
playbook role vars:the tuning
◄ loses to
-e extra varsHIGHEST

In this lab: defaults set nginx/80 · site.yml's role vars: confirm them · vars/ is commented out (the lock is open) · and -e could flip anything at run time.

AThe role's anatomy — folder by folder, in this project

FolderIn this task
tasks/Cache update (Debian-only) · install via package · service guard · template/index deploys
handlers/Restart + Reload — once at end of play, only if notified, both ignore_errors
templates/app.conf.j2 (nginx if/fork) · index.html.j2 (styled page) · nginx.conf.j2 (distro variant)
defaults/The 8 tunables — including service_name referencing package_name
vars/The high-precedence lock — commented out in this lab
meta/galaxy_info: author, MIT license, Ubuntu/Debian platforms, tags · dependencies: []
TASK [The experiment you can run]see precedence yourself

🔬 Test 1 — playbook beats defaults

site.yml sets app_port: 80 over defaults' 80. Change the playbook to app_port: 8080 → the template renders 8080. Defaults only apply when nobody else spoke.

🔬 Test 2 — vars/ beats the playbook

Uncomment package_name: nginx in vars/, set the playbook to redis → the play still installs nginx. The lock wins. Re-comment to restore.

WATCH OUTThe ladder is why the vars/ lock must stay commented in this lab — with it active, site.yml's vars are dead letters and the "reusability" demo can't work. High precedence isn't "more important," it's "wins the fight."
🎓 EXAMThe ladder by heart: defaults/ < vars/ < playbook role vars: < -e extra vars — lowest to highest. And the design rule that follows: put tunables in defaults/, put invariants in vars/, and let callers tune through playbook vars or -e.

🔴 rescue kit

Five failures this task actually produces, each with its root cause and exact fix — ordered by how likely you are to hit them:

SymptomCauseFix
config file = None + "world writable directory" warning/mnt/c NTFS mounted 777Copy project to ~/ansible, chmod 644 ansible.cfg, run with ANSIBLE_CONFIG=~/ansible/ansible.cfg

WATCH OUT · The #1 trap, expandedThe /mnt/c issue is environmental, not code: OneDrive + NTFS makes everything 777, and Ansible refuses to trust it for config discovery. DEBUG · Reading the table like an engineerThe pattern across all five rows: the symptom is always one layer below the cause. "Role not found" is a config problem; "password required" is an environment problem; the curl echo is a routing problem. Diagnose the layer, then apply the row's fix — don't chase the error text alone.
