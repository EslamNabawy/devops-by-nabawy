Chapter 01 · Foundations

WHY AUTOMATION BEATS SCRIPTS

5 MIN
WHAT — The automation problem

Manual operation scales linearly with machines and fails quietly. Shell scripts capture *commands* but not *intent*: which machines, what state, what if state already exists, how to verify, how to retry. Configuration drifts. Knowledge lives in runbooks and heads.

Manual loop vs declarative converge
Manual

Operator → SSH for-loop → hosts one by one → drift accumulates → re-run repeats side effects

Declarative

Playbook → control node → inventory select → compare desired vs current → CHANGED or OK, audited

Ansible addresses this by declaring desired state for selected targets and converging each target toward that state, reporting whether change was needed.

WHY — Why Ansible exists

Problem it solves: repeatable, auditable, idempotent configuration and orchestration without per-host agents or custom orchestration code for simple cases.

Where it fits:

Provisioning (Terraform) → Configuration (Ansible) → Orchestration (K8s) → Verification (Observability)

Ansible owns the configuration layer: OS, packages, files, services, users, application config — on bare metal, VMs, cloud instances, network devices where supported.

Chapter 01 · Foundations (cont.)

WHY AUTOMATION BEATS SCRIPTS

5 MIN
TERRAFORM VS ANSIBLE — Provision vs configure

Terraform provisions infrastructure (creates it: VPCs, VMs, DNS, load balancers) and tracks it in a state file. Ansible configures what already exists (OS, packages, files, services, users) and converges it on every run, keeping no state of its own.

AspectTerraform / OpenTofuAnsible
OwnsInfrastructure lifecycle (create, change, destroy)Inside-OS desired state (configure, converge)
StateState file (terraform.tfstate) maps config to real resourcesStateless; compares desired vs current on the host each run
Runsplan previews infra diff; apply changes infra--check --diff previews config diff; run converges hosts
Re-run costRe-plans against APIs; safe but slowRe-converges; OK where already correct, fast
SecretsProvider creds + sensitive outputsVault-encrypted vars, no_log, become scoping

Combined workflow (the normal production shape):

Terraform apply → outputs IPs/hostnames → generated inventory → Ansible configures OS/apps → services verified
terraform output -json > tf-out.json # ips of new VMs ansible-playbook -i inventories/prod site.yml

Handoff rule: Terraform hands addresses, Ansible takes responsibility inside the machine. Generate inventory from Terraform outputs (dynamic inventory plugin or terraform output templated into hosts.yml) — never hand-copy IPs between tools.

Anti-patterns:

  • Creating VPCs/VMs with Ansible modules → duplicates Terraform state, two sources of truth
  • Configuring apps with Terraform provisioner blocks beyond bootstrap → provisioners run once at create time, never converge drift; hand off to Ansible after boot
  • Storing Terraform outputs with secrets in plain files → mark sensitive = true, feed Ansible via Vault

Chapter 02 · Architecture

AGENTLESS — CONTROL TO MANAGED

6 MIN
WHAT — Agentless architecture

Ansible requires no permanently running agent on managed nodes. The control node holds automation content and initiates connections; managed nodes receive module payloads and execute them.

Agentless execution path
CONTROL NODEplaybook · inventory · vars→SSH / WinRMconnection plugin→MANAGED NODEmodule runs · JSON back
LinuxOpenSSH + Python 3WindowsWinRM + PowerShell
┌───────────────────┐ │ CONTROL NODE │ │ ansible-playbook │ │ inventory │ │ variables │ │ modules (FQCN) │ └─────────┬─────────┘ │ SSH / WinRM (connection plugins) ┌───────┴────────┐ ↓ ↓ HOST 01 (Linux) HOST 02 (Windows via WinRM)
WHY — Why agentless

Problem: agent lifecycle (install, upgrade, cert rotation) is its own fleet problem. Agentless trades persistent presence for on-demand execution: simpler bootstrap, no agent fleet to patch, works over standard transports already present.

Tradeoff callout:

Why this existsAgents give push-without-SSH but require ongoing fleet. Agentless gives immediate start but requires reachable transport + credentials per run. Choose agentless when SSH/WinRM already managed; choose agented when pull/continuous drift correction required.

Chapter 02 · Architecture (cont.)

AGENTLESS — CONTROL TO MANAGED

6 MIN
WHERE DOES IT FIT — Execution model
COMMAND → LOAD CONFIG (ansible.cfg) → LOAD INVENTORY → SELECT HOSTS → LOAD VARIABLES/FACTS → PROCESS PLAY → EXECUTE TASK → RUN MODULE → RETURN RESULT → NEXT TASK

This lane is the visual anchor reused every chapter.

HOW IT WORKS
  • Control node: where ansible / ansible-playbook runs. Needs Python 3.11+, collections, inventory, ansible.cfg.
  • Managed node: target host. Needs Python (most modules) or PowerShell (Windows), SSH/WinRM reachable, privilege path (become).
  • Transport: connection plugin. Default ssh (Linux), winrm/psrp (Windows). Data sent: module payload + args; result returned as JSON.
  • Module execution: module runs on managed node (or locally if delegate_to: localhost), reports changed, failed, skipped.

Config loading order (callout):

ansible.cfg precedence: ANSIBLE_CONFIG env → ./ansible.cfg → ~/.ansible.cfg → /etc/ansible/ansible.cfg
PRACTICAL — Verify control node
$ ansible --version ansible [core 2.16.x] ...

Meaning: confirms control node install. Target: local. Internal: loads config, no inventory needed. Expected: version + config path. Failure: command not found → install ansible-core + ansible.

Chapter 02 · Architecture (cont.)

AGENTLESS — CONTROL TO MANAGED

6 MIN
WSL SETUP — Control node on Windows

Windows cannot run Ansible natively. WSL2 + Ubuntu is the supported control node: a real Linux kernel where ansible-playbook, Python, and OpenSSH behave exactly like CI.

wsl --install -d Ubuntu # Windows Terminal (admin): installs WSL2 + Ubuntu sudo apt update && sudo apt install -y python3 python3-pip pipx openssh-client git pipx install ansible # ansible + ansible-playbook on PATH pipx inject ansible ansible-lint ansible --version # expect: ansible [core 2.16.x], python 3.11+

Rules that prevent an entire class of failures:

  • Keep the project inside WSL home (~/ansible/), not /mnt/c/ — Windows mounts are slow and cannot hold Linux permissions (SSH keys at 0600 silently break there)
  • Use VS Code with the WSL Remote extension so editors save with LF endings; CRLF line endings corrupt YAML and vault files
  • Generate the SSH key inside WSL (ssh-keygen -t ed25519), copy the public half to servers with ssh-copy-id
  • One .venv or pipx per toolset; never sudo pip install (breaks system Python)
ssh-keygen -t ed25519 -C "ansible-control" # ~/.ssh/id_ed25519 ssh-copy-id ansible@10.0.1.11 # test login without password prompt ansible web -i inventory.ini -m ping # first proof from WSL
WHAT CAN FAIL
  • UNREACHABLE → SSH key / WinRM creds / firewall
  • MODULE FAILURE → Python missing on managed node
  • become failure → sudoers / privilege escalation config

Chapter 03 · Inventory

INVENTORY — WHICH MACHINES

7 MIN
WHAT — Inventory is target declaration

Inventory lists managed nodes and organizes them into groups. Playbooks select from this list; ad hoc commands address it directly.

Inventory hierarchy
INVENTORY FILE→GROUPSweb · db · prod→HOSTSweb-01 · db-01→VARSgroup_vars · host_vars

Static inventory example:

[web] web-01 ansible_host=10.0.1.11 web-02 ansible_host=10.0.1.12 [db] db-01 ansible_host=10.0.1.21 [prod:children] web db

Hierarchy:

INVENTORY +-- groups (web, db, prod) +-- hosts (web-01, web-02) +-- group_vars / host_vars +-- variables (ansible_user, ansible_become)
WHY — Selection before declaration

Without inventory, automation has no audience. Inventory separates *which* from *what* — same playbook against web vs prod yields different blast radius.

Chapter 03 · Inventory (cont.)

INVENTORY — WHICH MACHINES

7 MIN
HOW IT WORKS
  • Static: INI or YAML file, committed to repo, versioned.
  • Dynamic: plugin queries cloud (AWS EC2, Azure) at runtime — generates inventory, not checked in.
  • Patterns: web, web[0], web:db, prod:&web, all:!db — composed at CLI/play hosts:.
  • Variables: inventory vars flow into variable precedence (taught fully in PDF2 Ch 06) via group_vars/web.yml, host_vars/db-01.yml.
PRACTICAL — Ad hoc proof (first execution)

Ad hoc = single task without playbook. Proves inventory + transport before YAML complexity.

COMMAND ──────────────────────── ansible web -i inventory.ini -m ping

Meaning: run ping module against group web. Target: web-01, web-02. Internal: control node loads inventory, selects hosts, sends ping.py via SSH, returns JSON. Expected:

RESULT ──────────────────────── web-01 | SUCCESS => { "changed": false, "ping": "pong" } web-02 | SUCCESS => { "changed": false, "ping": "pong" }

Why it matters: proves selection, transport, Python on target in 5 seconds.

Common failure:

  • UNREACHABLE → check ansible_user, ansible_host, key, ansible -m ping with -vvv
  • changed: false surprise → ping is check-only; not a bug

Second ad hoc:

$ ansible web -i inventory.ini -a "uptime"

-a = command module args. Compare: -m ping vs -a "uptime" shows module vs raw command.

Chapter 03 · Inventory (cont.)

INVENTORY — WHICH MACHINES

7 MIN
CONNECTING — SSH keys, users, IPs

Inventory names the targets; connection variables explain how to reach them. Four variables do 95% of the work:

[web] web-01 ansible_host=10.0.1.11 ansible_user=ansible ansible_port=22 web-02 ansible_host=10.0.1.12 ansible_user=ansible [web:vars] ansible_ssh_private_key_file=~/.ssh/id_ed25519 ansible_become=true
  • ansible_host — real IP/hostname (the inventory name stays a stable alias even when IPs change)
  • ansible_user — SSH login user; create a dedicated ansible user, never automate as root over SSH
  • ansible_port — non-default SSH port where hardened
  • ansible_ssh_private_key_file — which key; one key per environment (prod_ed25519 vs staging_ed25519)

Key bootstrap (once per server, from the control node):

ssh-keygen -t ed25519 -f ~/.ssh/prod_ed25519 # private stays 0600, never leaves control node ssh-copy-id -i ~/.ssh/prod_ed25519 ansible@10.0.1.11 ssh -i ~/.ssh/prod_ed25519 ansible@10.0.1.11 # must log in with no password prompt

WHAT CAN FAIL
  • Pattern selects zero hosts → hosts: web matches nothing if group misspelled → --list-hosts verify
  • Wrong vars file location → group_vars/ must sit beside inventory file
  • Dynamic inventory creds → plugin fails silently if cloud creds missing

Chapter 04 · Playbooks

PLAYBOOK — DESIRED STATE IN YAML

8 MIN
WHAT — Playbook is desired-state document

A playbook maps hosts to tasks that invoke modules with arguments. It is YAML, declarative: describe end state, not step-by-step shell.

Play nests tasks, tasks invoke modules
PLAYhosts · become→TASKname→MODULEansible.builtin.*→ARGSname · state
WHY — From ad hoc to repeatable

Ad hoc proves one module once. Playbooks repeat, order, and audit multiple tasks. They are the unit committed to Git and triggered by CI.

AspectAd hoc commandPlaybook
ShapeOne module call from the CLIPlays and tasks in a YAML file
RepeatRetype the command every timeRun the file again, identical result
ReviewShell history on one laptopGit diff plus --check --diff
HandoffTell someone the commandCommit site.yml; CI runs it

Chapter 04 · Playbooks (cont.)

PLAYBOOK — DESIRED STATE IN YAML

8 MIN
YAML — Syntax before semantics
- name: Configure web server hosts: web become: true # privilege escalation tasks: - name: Install nginx ansible.builtin.package: name: nginx state: present - name: Ensure nginx running ansible.builtin.service: name: nginx state: started enabled: true

Hierarchy:

PLAY (hosts: web, become: true) +-- tasks +-- TASK (name: Install nginx) +-- MODULE (ansible.builtin.package, FQCN) +-- ARGUMENTS (name, state)

Rule: FQCN always (ansible.builtin.*) — short names obsolete. YAML whitespace matters; 2-space indent.

HOW IT WORKS — Execution
PLAY (web) → TASK 1 (package) → SSH → managed node → check nginx absent → install → CHANGED → TASK 2 (service) → check stopped → start → CHANGED → RESULT per host → NEXT PLAY

Play = which hosts; Task = what module with which args; Module = implementation that converges state.

Chapter 04 · Playbooks (cont.)

PLAYBOOK — DESIRED STATE IN YAML

8 MIN
PRACTICAL — Run it
COMMAND ──────────────────────── ansible-playbook -i inventory.ini site.yml

Meaning: execute playbook against inventory. Target: web group. Internal: load site.yml, select hosts, for each task send module, collect changed/ok/failed. Expected:

RESULT ──────────────────────── PLAY [Configure web server] *** TASK [Install nginx] *** changed: [web-01] TASK [Ensure nginx running] *** changed: [web-01] PLAY RECAP *** web-01 : ok=2 changed=2 failed=0

Why it matters: proves declarative convergence; re-run should yield ok=2 changed=0.

Common failure: YAML parse error → ERROR! Syntax Error at line; fix indent or missing :.

WHAT CAN FAIL
  • hosts: web matches zero → skipping: no hosts matched → verify with --list-hosts
  • become: true without sudo → Failed to escalate → ansible_become_user / sudoers
  • Module args typo → unsupported parameter → check ansible-doc ansible.builtin.package

Chapter 05 · Idempotency

MODULES AND IDEMPOTENCY

ADV
WHAT — Module + ideal result

Module = unit of desired state. Takes args, checks current state, acts only if needed, returns JSON with changed, failed, msg.

First run — CHANGED
Desired: nginx present ↓ Current: absent ↓ Install → CHANGED
Second run — OK
Desired: nginx present ↓ Current: present ↓ No action → OK

Idempotency: same input applied twice → same end state, second run reports no change.

WHY — Desired state ≠ re-run commands

Scripts re-run commands blindly. Modules compare desired vs current:

DESIRED STATE (state: present) ↓ CURRENT STATE (nginx absent? present?) ↓ COMPARE → CHANGE OR NO-OP → RESULT (CHANGED / OK)

Without this, automation cannot be safely repeated for drift correction or retries.

MODULES AND IDEMPOTENCY

ADV
HOW IT WORKS — Visual

First run:

Desired: nginx present → Current: absent → Install → CHANGED

Second run:

Desired: nginx present → Current: present → No action → OK

Result states (always labeled with symbol+color, not color alone):

  • OK (green ●) — converged, no change
  • CHANGED (blue ◐) — converged, did change
  • FAILED (red ) — did not converge
  • SKIPPED (gray ○) — conditional skipped
  • UNREACHABLE (amber ) — transport failed
Desired vs current decides everything
DESIRED→CURRENT→COMPARE→CHANGE or NO-OP

Chapter 05 · Idempotency (cont.)

MODULES AND IDEMPOTENCY

ADV
PRACTICAL — Observe idempotency
- name: Idempotency demo hosts: web tasks: - name: Create app directory ansible.builtin.file: path: /opt/app state: directory mode: '0755'

First run: changed: [web-01]. Second run: ok: [web-01]. Proof of desired-state model.

Check and diff modes:

$ ansible-playbook -i inventory.ini site.yml --check --diff

--check dry-runs, --diff shows planned file/service changes. Use for approval gates.

WHAT CAN FAIL — Common misreads
  • OK misread as "nothing happened" → actually "already converged" (GOTCHA callout below)
  • Module not idempotent by misuse → command: apt-get install always CHANGED vs package: converges → use package/file/template not command/shell where module exists
  • changed_when abuse → masks real change signal
Gotcha"OK" does not mean Ansible did nothing meaningful. It means desired state already holds. Always read result state pair: ok vs changed count.

MODULES AND IDEMPOTENCY

ADV
COMMAND + RESULT PATTERN
COMMAND ──────────────────────── ansible web -i inventory.ini -m ansible.builtin.file -a "path=/opt/app state=directory mode=0755" RESULT ──────────────────────── web-01 | CHANGED => { "changed": true, "path": "/opt/app", "state": "directory" } WHAT HAPPENED: file module ensured directory exists, created it. WHY IT MATTERS: proves CHANGED on creation, OK on repeat. COMMON FAILURE: path parent missing → use state=directory (creates parents), mode typo → permission drift.
