CH 00

☸️ What is Kubernetes?

🟢 5 MIN · START HERE

Kubernetes is an open-source container orchestrator: it takes the containers you define and — across a fleet of machines — deploys them, scales them, heals them, connects them, and updates them without downtime. You describe what you want. It makes reality match. Forever.

📜

The Name
Greek κυβερνήτης (kybernetes) = helmsman — the one who steers the ship. Hence the wheel logo ☸️ (and the word cybernetics).

🔢

k8s
Programmer shorthand: K + the 8 letters in between + s. Pronounced "K-eights" — you'll read it a hundred times a day.

🧬

Lineage
Born at Google from Borg (its internal cluster manager, ~2003) → open-sourced 2014 → donated to the CNCF with v1.0 in 2015. Written in Go.

🤔 The problem it solves — running ONE container is easy; running a fleet is not

😩 Without an orchestrator
  • 💀 A container crashes at 3am → you restart it
  • 🗺️ Ten machines free — which one takes the new app? you decide
  • 🕸️ 40 containers need to find each other → hand-written configs
  • 🎞️ Upgrade from v1 to v2 → downtime, or a hand-rolled script
  • 📈 Black Friday? Log in and start containers manually
☸️ With Kubernetes
  • 🔄 Crash → replaced automatically (reconciliation — CH 06)
  • 🎯 New app → the Scheduler picks the best node (CH 02)
  • 🧭 Containers find each other via DNS + Services (CH 12, 26)
  • 🎬 Upgrades roll out with zero downtime + one-command undo (CH 20–21)
  • 📈 Scaling = change one number (Lab 2)
🔑
The core idea — declarative, not imperative: you don't write steps ("start container, then check, then restart…"). You declare a wish ("3 replicas of nginx") and Kubernetes runs a permanent reconciliation loop: watch actual → compare to desired → act. This one idea is the engine behind self-healing, scaling, and rollouts — and it returns on almost every page of this book.

🎁 What's in the box

🔄 Self-healing restarts · replaces
📏 Scaling one command
🎬 Rollouts + rollback zero downtime
🧭 Service discovery + LB built-in DNS
🔐 Config & Secrets injected, not baked
🗄️ Storage orchestration PVC/PV

Industry gravity: every major cloud runs it as a service — GKE (Google) · EKS (AWS) · AKS (Azure) — and it's the CNCF's first graduated project. Learning Kubernetes is learning the operating system of the cloud.

CH 00

☸️ What is Kubernetes? — continued

🟢 5 MIN · START HERE
⚠️
What Kubernetes is NOT: not a programming language · not a PaaS (it ships building blocks, not opinions) · not a container builder (Docker/CI build images — k8s runs them) · not a runtime itself (it drives one — containerd, CRI-O, CH 03) · not a monitoring system (Prometheus & friends watch it). It's the orchestra conductor 🎻 — it doesn't play a single instrument, but nothing plays without it.
🏺
Heritage flex: Kubernetes didn't invent containers or orchestration — Google had been running billions of containers a week on Borg for a decade. Kubernetes is what happened when they distilled that war story into an open-source project the rest of the world could use. You're learning fifteen years of production scars, organized into an API.
🎓
Exam / interview tip: "What is Kubernetes?" has a canonical two-beat answer — (1) an open-source container orchestrator, (2) declarative: you declare desired state, it continuously reconciles reality toward it. Add "descended from Google's Borg" for bonus credibility.

🟡 6 MIN · CORE

The Control Plane controls the cluster. It does not normally run your application workloads. Its job:

📥 Receive requests
💾 Store cluster information
🎯 Decide where Pods should run
👀 Monitor the cluster
✅ Maintain the desired state

🧩 Inside the Control Plane

🧠 Control Plane
API Server 🚪
Scheduler 🎯
Controllers 🔄
etcd 💾

🧪 Example — you tell Kubernetes:

replicas: 3

The Control Plane then figures out:

  • 🧮 "I need 3 Pods."
  • 🗺️ "Where should they run?"
  • 👀 "Are they actually running?"
  • 💀 "Did one die?"
  • 🔁 "Do I need to create another?"

The four components, one line each: API Server = the only door 🚪 · etcd = the memory 💾 · Scheduler = the placement officer 🎯 · Controllers = the watchdogs 🔄. Everything else in the cluster talks through the door.

CH 07

🤔 Can the Control Plane also be a Worker?

🟢 4 MIN

Technically yes. In production: no. The mechanism that separates them is a taint.

🏠 Minikube — yes, by design

A single-node cluster where one machine is both brain and muscle. The Control-Plane taint is removed so workloads can land there. Perfect for learning.

$ kubectl get nodes NAME       STATUS   ROLES minikube   Ready    control-plane,master
🏭 Production — never

Control-Plane nodes carry a taint like node-role.kubernetes.io/control-plane:NoSchedule — the Scheduler refuses to place normal Pods there. The brain is protected.

$ kubectl describe node cp1 | grep Taints Taints: node-role.kubernetes.io/control-plane:NoSchedule
⚠️
Why the isolation matters: a runaway workload on a Control-Plane node can starve the API Server or etcd — and then the entire cluster's brain slows or freezes. etcd is especially latency-sensitive.
🔑
Remember: "Control Plane ≠ Worker" is not a law of nature — it's a taint. Remove the taint and the brain will do deadlifts. (Lab 5 covers taints hands-on.)

CH 08

🗳️ Master : Worker Ratio & etcd Quorum

🟡 6 MIN · CORE

Why does everyone run 3 Control Planes? Because etcd (the memory 💾) needs a quorum — a majority of members alive and agreeing — to accept any write.

The quorum math
quorum = floor((n-1)/2) + 1 members required # of Control Planes → failures tolerated before the cluster freezes: 1 CP → tolerate 0 failures (one crash = frozen) 3 CP → tolerate 1 failure ← the production minimum 5 CP → tolerate 2 failures 7 CP → tolerate 3 failures
Control PlanesQuorum needsToleratesVerdict
11 of 10Dev only
22 of 20Worst choice — same tolerance as 1, double the cost
32 of 31✅ Standard production
53 of 52Large/critical clusters
⚠️
The trap: 2 is the worst number. Two members need both alive for quorum — one failure freezes writes, exactly like having one. Even numbers add cost without adding tolerance.
🔑
Workers scale independently. The ratio isn't "1 master per N workers" — it's 3–5 Control Planes (for quorum) plus as many Workers as your workload needs. A lost quorum means the cluster keeps running what's deployed but accepts no new state.

CH 10

🗂️ Namespaces — The Big Idea

🟢 4 MIN

Without namespaces, one cluster = one giant bucket. Frontend, AI and dev all collide — same names, no boundaries. A namespace is the cluster saying "I can carve logical apartments inside one building."

Problem — one flat bucket
Cluster ├── pod-a ├── pod-b frontend? ├── pod-c ai? └── svc-a # who owns what?
Solution — logical apartments
Cluster ├── frontend Pods + Services ├── ai Pods + Services └── dev Pods + Services same nodes, same control plane

When namespaces shine

👥

Teams
frontend / backend / ai

🌿

Environments
dev / staging / prod via namespaces

🧩

Apps
app-a / app-b isolated, same infra

🔑
Namespace = logical isolation — it affects names, RBAC, quotas. It does not carve hardware or network by itself.
💡
Environment ≠ Namespace. Environment is the concept; namespace is one object you can implement it with (another: separate clusters).

CH 11

🏷️ Names Are Scoped + The Three Superpowers

🟡 6 MIN · CORE

A Pod's full identity is namespace + kind + name. So dev/nginx and prod/nginx are two different objects — no collision.

Cluster ├── dev │ └── nginx Pod ← identity: dev / Pod / nginx └── prod └── nginx Pod ← identity: prod / Pod / nginx

⚡ The three superpowers namespaces unlock

🪪 RBAC — keys

"This team may act only inside frontend." Permissions scoped per namespace.

📊 Quotas — budget

"ai may use at most 4 CPU / 8Gi, 10 Pods." A ResourceQuota caps each apartment's totals.

🚧 NetworkPolicy — door rules

"Pods in dev may not call prod." Traffic rules scoped per namespace.

⚠️
Not everything lives in an apartment. Nodes, ClusterRoles, PersistentVolumes and Namespaces themselves are cluster-scoped — kubectl get nodes -n dev silently ignores the -n. Nodes belong to the building, not an apartment.
🔑
The rule: namespaced → identity includes the namespace · cluster-scoped → namespace flags do nothing. Namespaces partition names, not hardware.

CH 14

🛡️ ReplicaSet — What Is It?

🟡 6 MIN · CORE

A ReplicaSet is the guarantor: it watches a set of Pods that carry specific labels, and keeps their count at the number you asked for. Not one more, not one fewer.

apiVersion: apps/v1 kind: ReplicaSet metadata: name: nginx-rs spec: replicas: 3 # ← the promise selector: matchLabels: app: nginx # ← who it manages template: # ← the pod stamp it uses metadata: labels: { app: nginx } # must match the selector! spec: containers: - name: nginx image: nginx:1.25

🔍 How it "counts"

  • 🔎 Selector — the ReplicaSet claims every Pod whose labels match app: nginx
  • 🧮 Compare — desired 3 vs actual (say) 2
  • 🔧 Act — create one more Pod from the template (or delete surplus)
  • 🔁 Repeat — this is just the reconciliation loop again, one level down
⚠️
Label match is everything. If the template's labels don't satisfy the selector, the ReplicaSet refuses to start. And any stray Pod with matching labels gets adopted — willingly or not.
🔑
ReplicaSet = labels + count + template. You'll rarely write one by hand — a Deployment creates them for you (CH 15).

CH 15

💀 Labels, Death & Why Deployment

🟡 6 MIN · CORE
Standalone Pod dies
🕳️

Gone. Forever. Nobody holds a copy of the wish — the Pod's spec died with it. This is why "just run a Pod" is a demo trick, not a deployment.

Owned Pod dies
🔄

Recreated automatically. The ReplicaSet still holds the template — the mismatch triggers a replacement with a new name (e.g. nginx-rs-x7k2p).

🪆 So why isn't ReplicaSet enough? The ownership chain

Deployment you talk to this one └── ReplicaSet v1 manages Pods at image nginx:1.25 ├── 🫛 pod ├── 🫛 pod └── 🫛 pod change the image → Deployment creates ReplicaSet v2, rolls Pods over ← CH 20
  • 🛡️ ReplicaSet answers: "are the right number of Pods running?"
  • 🚀 Deployment answers: "are they running the right version? — and can we switch versions with zero downtime?"
🔑
Own vs run: a standalone Pod is run; an owned Pod is guaranteed. The Deployment exists because the ReplicaSet can keep count — but it can't change what it's counting without downtime. The Deployment can.

CH 16

👀 The Pod Lifecycle — Owned vs Standalone

🟡 6 MIN · CORE

The five-second experiment that makes ownership real. Two terminals:

👀 TAB 1 · WATCH
$ kubectl get pods -w NAME           READY  STATUS web-7d9f       0/1    ContainerCreating web-7d9f       1/1    Running web-7d9f       0/1    Terminating web-x7k2p      0/1    ContainerCreating web-x7k2p      1/1    Running  # new name!
⚙️ TAB 2 · ACT
$ kubectl delete pod web-7d9f pod "web-7d9f" deleted # watch TAB 1: a replacement appears # same deployment, brand-new pod name

🧾 What we just proved

  • ✅ The Pod's name is disposable — the ReplicaSet's promise is not.
  • ✅ Deletion is just another mismatch: desired 1, actual 0 → create.
  • ❌ A standalone Pod (no owner) deleted = silence. No replacement. No drama.
💡
Status decoding: ContainerCreating = image pulling + CNI wiring · Running = process up · Terminating = shutting down gracefully · Pending = not yet placed (CH 23).
🔑
Owned vs standalone is the single most important workload concept. Every "why did my Pod come back?!" mystery is answered by: someone owns it — find the ReplicaSet.

CH 18

🫛 Pod Deep Dive

🟡 6 MIN · CORE

The Pod is the smallest deployable unit — not the container. A Pod is a co-located family of containers that share fate.

One Pod = one shared environment
🌐 ONE IP address shared by all containers
📦 app containerlistens :80
📦 sidecarreaches app on localhost
💾 shared Volume same files, both containers
  • 🌐 One IP per Pod — containers inside talk via localhost:port, never "find the other container's IP"
  • 💾 Shared volumes — declared in the Pod spec, mounted by any of its containers
  • ⏳ Shared lifecycle — born together, scheduled together (same Node), die together
  • 🚫 Never scale "a container" — you scale Pods; want more copies → more Pods
⚠️
Port clashes are real: two containers in one Pod cannot bind the same port — they literally share the network stack.
🔑
The test for Pod-membership: must these containers live and die together on the same machine? Yes → one Pod. No → separate Pods (and let the Scheduler place them freely).

👥 Multi-Container Pods

🟡 5 MIN

The classic pattern: the sidecar — a helper container riding along with the app container inside one Pod.

spec: containers: - name: app image: myapp:2.0 volumeMounts: - { name: logs, mountPath: /var/log/app } - name: log-shipper # the sidecar image: busybox command: ["sh","-c","tail -F /logs/app.log"] volumeMounts: - { name: logs, mountPath: /logs } # same volume! volumes: - name: logs emptyDir: {}

⚖️ Good vs bad Pod-mates

✅ Belong together
  • 📜 app + log shipper (shared files)
  • 🔐 app + auth proxy (shared localhost)
  • 🔄 app + config reloader (shared lifecycle)
❌ Don't
  • frontend + database (scale & fail independently)
  • two unrelated services (one crash restarts both... and they fight over ports)
🔑
Heuristic: if the two containers could run on different machines, they belong in different Pods. Pod-mates are glued on purpose — glue is a cost.

CH 20

🎞️ Deployment — Rolling Updates

🟡 6 MIN · CORE

Change a Deployment's image and it doesn't rebuild Pods in place — it creates a new ReplicaSet and rolls traffic from old to new, keeping availability the whole time.

$ kubectl set image deploy/nginx nginx=nginx:1.26 deployment.apps/nginx image updated $ kubectl rollout status deploy/nginx Waiting for deployment "nginx" rollout to finish... deployment "nginx" successfully rolled out

🪆 What actually happened

Deployment nginx ├── ReplicaSet v2 nginx:1.26 scales 0 → 3 👆 │ └── 🫛 🫛 🫛 new Pods replace old └── ReplicaSet v1 nginx:1.25 scales 3 → 0 👇 (kept for rollback)
  • ⚖️ The Controller walks the count: add a v2 Pod → remove a v1 Pod → repeat
  • 📉 Service selectors keep pointing at labels — traffic slides over automatically
  • 🗄️ v1's ReplicaSet is retained (scaled to 0) — that's your rollback insurance (CH 21)
🔑
Zero downtime is the point: at every instant, enough healthy Pods serve traffic. The Deployment turned "risky big-bang upgrade" into "boring arithmetic."

⏪ Rollout Commands

🟢 4 MIN
$ kubectl rollout history deploy/nginx REVISION  CHANGE-CAUSE 1         <none> 2         nginx:1.26 $ kubectl rollout undo deploy/nginx deployment.apps/nginx rolled back $ kubectl rollout status deploy/nginx successfully rolled out  # ← back on :1.25
  • 📊 rollout status — watch a rollout finish (script-friendly)
  • 🗂️ rollout history — every revision is just an old ReplicaSet with a number
  • ⏪ rollout undo — flip back to the previous template · --to-revision=1 to pick
  • 🗄️ revisionHistoryLimit: 3 — how many old ReplicaSets to keep (default 10)
⚠️
Undo doesn't rewind time — it creates a new revision (v3) with v1's template. History only moves forward; the ReplicaSet list is the audit trail.
🔑
The rollout trilogy — status / history / undo — is the exam's favorite Deployment command set. Learn it as one unit.

📜 YAML Anatomy — The Two Specs

🟡 6 MIN · CORE

Every Kubernetes manifest is the same envelope: apiVersion · kind · metadata · spec. The "wish" lives in the spec.

FieldMeaningExample
apiVersionWhich API group/version serves this kindv1 (Pod) · apps/v1 (Deployment)
kindWhat object you wantPod, Service, Deployment
metadataName · namespace · labelsname: nginx
specThe desired statereplicas, containers, ports…

🪆 The Two-Specs Mystery (Deployment)

spec: # the DEPLOYMENT's wish   replicas: 3   selector: …   template: # a whole Pod hiding inside!     metadata: labels: …     spec: # ← the POD's wish (spec inside spec)       containers: …
  • 🧠 Outer spec = what the Deployment manages: count, selector, template
  • 🫛 Inner spec (spec.template.spec) = the actual Pod: images, ports, env, resources
  • 🔁 spec.template is the cookie cutter — the ReplicaSet stamps Pods from it; change anything inside and you trigger a rollout (CH 20)
🔑
Indentation is structure in YAML. The most common manifest bug is writing the Pod spec at the wrong nesting level — and the API Server answers with a confusing validation error. Count your two spaces.

🧰 Debugging 2 — The Toolbox

🟡 6 MIN · CORE
$ kubectl describe pod web-x7k2p # 1 · full biography…   Events: # …always read the BOTTOM    Failed to pull image "nginx:1.99" $ kubectl logs web-x7k2p --previous # 2 · crashed container's last words panic: missing REQUIRED_DB_PASSWORD $ kubectl exec -it web-x7k2p -- sh # 3 · go inside $ kubectl get events --sort-by=.lastTimestamp # 4 · cluster timeline
describe — the biography

Config as the cluster sees it, plus the Events block at the bottom — the single most information-dense place in debugging.

logs --previous — the autopsy

CrashLoopBackOff kills the evidence — --previous reads the last dead container's output. Forgetting this flag = reading a fresh empty log and panicking.

🎯 The 4-step playbook (in order)

1get pods — read the STATUS column (CH 23 table)
2describe pod — events at the bottom name the failing stage
3logs --previous — the app's own error message
4exec -it -- sh — poke around inside: DNS, env, files, curl
🔑
90% of debugging is reading. The cluster narrates its own failures — through events and logs — if you ask in the right order.

🚪 NodePort — The Side Entrance

🟡 6 MIN · CORE

ClusterIPs are invisible from outside the cluster. NodePort punches a hole: every Node opens one high port and forwards it to your Service.

apiVersion: v1 kind: Service metadata: name: nginx-svc spec: type: NodePort # default is ClusterIP selector: app: nginx ports: - port: 80 # inside the cluster targetPort: 80 # container's port nodePort: 30080 # outside — or omit & let k8s pick
The path in
🌍 User
──►
ANY node:30080
──►
ServiceClusterIP rules
──►
🫛 Pod :80

"ANY node" is the superpower — even a Node with no nginx Pod opens the door and forwards across.

  • 📏 Valid range: 30000–32767 (omit nodePort and one is auto-assigned)
  • 🔓 Every Node gets the same port — hit 192.168.1.11:30080 or .13:30080, same result
⚠️
NodePort is for demos & edge cases — raw ports, no load balancing across nodes, no TLS story. Production rides Ingress (Book 03 😉).

CH 26

🎭 Service Networking — The Virtual IP

🟡 6 MIN · CORE

Here's the trick nobody tells you: the ClusterIP your Service owns is a lie. Nothing is listening on it. No process holds it. It's a virtual IP (VIP) — and that's the elegance.

Russian dolls — where the VIP really goes
10.96.0.50the VIP — a fiction
──► DNAT ──►
10.244.1.5a real Pod IP

packets "to the VIP" are rewritten in transit to a real Pod — the VIP never terminates anything

Address ranges — separate drawers: Service CIDR 10.96.0.0/12 # VIPs live here (fake, routable only via rules) Pod CIDR 10.244.0.0/16 # real Pod IPs (per-node slices)
  • 🚫 You can't ping a ClusterIP — nothing answers; the rules only rewrite packets passing through
  • 🎭 Pods died and got new IPs? Nobody notices — everyone still dials the VIP
  • 🧮 The ranges must not overlap — two drawers, zero confusion
🔑
The Service is a stable illusion: an eternal name + eternal IP in front of a set of mortals (Pods) that churn constantly. The illusion is maintained by kube-proxy — next chapter.

CH 27

🕸️ kube-proxy's Real Job

🟡 6 MIN · CORE

kube-proxy does not forward a single packet. Its entire job is two verbs: watch & program.

❌ What it does NOT do
  • Sit in the traffic path
  • Proxy connections through itself
  • Touch Pod-to-Pod traffic
✅ What it DOES
  • Watch the API Server: Services + Endpoints
  • Program iptables/IPVS rules on its node
  • Re-program the instant Pods change

🪄 The rules it writes (iptables + DNAT)

# conceptually, on every node: if dst == 10.96.0.50:80 # the VIP   then rewrite dst → 10.244.1.5:80 # pick an endpoint (random)   else if … next endpoint # (rule set balances across all)
✨
The Illusion, resolved: a Pod dies → Endpoints object updates → every node's kube-proxy rewrites its rules → the VIP never moved. Stability on the outside, churn on the inside, and the packets never knew.
🔑
One-liner for exams: kube-proxy watches Services/Endpoints and programs packet-rewriting rules on every node — it never forwards traffic itself.

CH 28

📦 Following ONE Packet — 6 Steps

🔵 FINALE · CORE

A Pod runs curl nginx-svc. Follow the single packet:

1DNS — nginx-svc resolves to the VIP 10.96.0.50 · CoreDNS answered from the Service's namespace
2Send — Pod sends to the VIP (nothing is there — remember CH 26) · dest: 10.96.0.50:80
3DNAT — the node's iptables rules rewrite the destination → a real Pod IP: 10.244.1.5:80
4Route — same node → direct delivery; different node → CNI overlay carries it
5Receive — the Pod sees a normal packet addressed to its own IP · it replies
6Return — conntrack rewrites the reply back through the VIP — the client believes it talked to 10.96.0.50 the whole time 🎩
🔑
The entire machine in one sentence: DNS gives you a stable fake IP; kube-proxy's rules secretly rewrite it to a mortal Pod; conntrack makes the lie symmetric. That's Service networking — everything else is detail.

LAB 5

🚧 Taints & Tolerations

🟠 15 MIN · HANDS-ON
STEP 1 · Taint AFTER the Pod exists
⚙️ RUN
$ kubectl taint node <node> env=prod:NoSchedule $ kubectl scale deploy web --replicas=4
👀 EXPECTED
# existing pods keep running # NEW 4th pod → Pending 0/1 Nodes available …taint…that pod tolerates not

Key insight: NoSchedule only gates new placements — it never evicts.

STEP 2 · Rescue with a toleration
spec: tolerations: - key: env operator: Equal value: prod effect: NoSchedule # pod may now LAND on the tainted node

Apply → the Pending pod schedules immediately. Taint = the lock. Toleration = the key.

STEP 3 · NoExecute — the eviction
⚙️ RUN
$ kubectl taint node <node> env=prod:NoExecute
👀 EXPECTED
# non-tolerating pods on that # node get EVICTED — now
EffectExisting PodsNew Pods
NoSchedulestayblocked (unless tolerated)
PreferNoSchedulestayavoided if possible
NoExecuteevictedblocked (unless tolerated)
🔑
Remember the direction: taints repel (node → pods); tolerations permit (pod → tainted node). Taints never attract — for that you'd use nodeSelector/affinity (Book 04 in depth).

GLOSS

📚 Glossary

🔵 REFERENCE
Cluster — Control Plane + Worker Nodes managed as one unit.
Control Plane — the brain: API Server, etcd, Scheduler, Controllers. Makes decisions; runs no user workloads (by taint).
API Server — the only door 🚪. All reads/writes (kubectl, kubelet, controllers) go through it; only it touches etcd.
etcd — the cluster's memory 💾. Needs quorum (majority) to write — why production runs 3 or 5 Control Planes.
Scheduler — assigns new Pods to Nodes based on resources, taints, affinity.
Controller — reconciliation loop: watch actual vs desired, act to close the gap.
kubelet — the node agent 👷. Talks to the API Server, runs Pods via the runtime, reports status.
Container Runtime — pulls images and runs containers (containerd, CRI-O).
kube-proxy — watches Services/Endpoints, programs iptables/IPVS rules per node. Never forwards packets itself.
Pod — smallest deployable unit: 1+ containers sharing IP, volumes, lifecycle.
ReplicaSet — the guarantor: keeps N matching-labeled Pods alive via a template.
Deployment — manages ReplicaSets to enable versioned, zero-downtime rollouts and rollbacks.
Namespace — logical partition of names + RBAC + quotas inside one cluster. Apartments, not buildings.
Service — stable virtual IP + DNS name in front of a changing set of Pods.
NodePort — Service type opening one high port (30000–32767) on every node.
Taint / Toleration — node-side repulsion / pod-side permission. NoSchedule blocks placement; NoExecute also evicts.
🔑
Self-test the glossary: cover the right side, read each term, say the one-line definition aloud. If you can't — that's tonight's reading.
