🇪🇬 الحماية وSecrets: شرح عربي
Automation تمسّ Root وSecrets معًا، فضيّق Privilege وشفّر السرّ. ارفع الامتياز عند الحاجة فقط عبر become (غالبًا sudo) مع become_user المناسب، وانسخ Secrets مشفّرة بـAnsible Vault (encrypt/decrypt/view/edit/rekey وقيم سطرية بـencrypt_string) وفكّها لحظة التشغيل بكلمة سر أو ملف أو سرّ CI، مع كتم المخرجات الحساسة بـno_log. فرّق بين Ansible Vault (تشفير ملفات داخل المستودع) وHashiCorp Vault (مخزن خارجي عبر lookups). راجع ملكية الملفات وسياقات SELinux ومفسّر ansible_python_interpreter عند الأعطال.
become·Ansible Vault·encrypt_string·no_log·SELinux·sudoers
WHAT — Least privilege + encrypted secrets

become escalates privilege (typically sudo) per play, role, or task. Ansible Vault encrypts variables and files so secrets live in Git safely and decrypt only at run time.

Secrets stay encrypted until run time
PLAINTEXT VAR→VAULT ENCRYPT→COMMIT SAFE→DECRYPT AT RUN
- name: Configure web fleet hosts: web become: true become_user: root vars_files: - group_vars/prod/vault.yml tasks: - name: Deploy TLS key ansible.builtin.copy: src: tls.key dest: /etc/nginx/tls.key mode: '0600'
ansible-vault encrypt group_vars/prod/vault.yml ansible-playbook -i inventory.ini site.yml --ask-vault-pass

Vault file holds vault_tls_key, vault_db_password — referenced as {{ vault_db_password }}, never in plain vars.

WHY — Automation is a privileged secret-spreader

Playbooks run as root across fleets and touch credentials. Plain-text secrets in Git leak to every clone; blanket become: true with passwordless sudo everywhere widens blast radius. Vault + scoped become give two guarantees: secrets encrypted at rest in version control, privilege granted narrowly per task.

WHERE DOES IT FIT — Secure after organize
Roles/collections (Ch 09) define vars → Vault encrypts the sensitive subset → become scopes who applies them → testing (Ch 11) verifies without leaking → CI/CD (Ch 12) injects vault password from CI secrets

Do not confuse Ansible Vault (file/var encryption in-repo) with HashiCorp Vault (external secret store via lookup plugins). They compose: external vault supplies at run, Ansible Vault encrypts what must live in Git.

HOW IT WORKS — Encrypt, scope, inject

Vault: ansible-vault encrypt|decrypt|view|edit|rekey per file; encrypt_string for inline values. Multiple vault IDs (--vault-id prod@prompt) separate environments. At run, password comes from prompt, file (--vault-password-file), or CI secret → file. no_log: true on secret-touching tasks suppresses output.

Become: become: true + become_user + become_method: sudo (or su, runas on Windows). Scope narrowly: play default become: false, escalate only tasks needing root. --ask-become-pass for interactive sudo password; in CI use NOPASSWD scoped sudoers or ephemeral privilege.

- name: Read app status as app user ansible.builtin.command: systemctl --user status app become: true become_user: app register: app_status changed_when: false no_log: false

SUDO PITFALLS — Privilege side: sudoers and become identity

Most Ansible failures on Linux are not Ansible bugs — they are privilege, ownership, or interpreter mismatches. Learn the five usual suspects.

1. Sudoers scope. Grant the automation user exactly what plays need, nothing more:

ansible ALL=(ALL) NOPASSWD: /usr/bin/systemctl *, /usr/bin/apt-get *, /usr/bin/yum *

Blanket ALL=(ALL) NOPASSWD: ALL works in labs and horrifies auditors; passworded sudo needs --ask-become-pass (interactive) or CI-managed credentials. Old RHEL/CentOS images also enforce Defaults requiretty — sudo over non-interactive SSH fails until that line is removed for the automation user.

2. Become identity. become_user decides *who you become*, default root. Database tasks often need the service account instead:

- name: Vacuum app database community.postgresql.postgresql_query: query: VACUUM ANALYZE become: true become_user: postgres

SUDO PITFALLS — Host side: ownership, SELinux, interpreter

3. Ownership and modes. Files created by a root-run task belong to root. Serve them to an app user and reads fail:

- name: Deploy app config ansible.builtin.template: src: app.conf.j2 dest: /etc/app/app.conf owner: app group: app mode: '0640'

Always set owner/group/mode on security-relevant files; verify with a second task using ansible.builtin.stat when the service is picky.

4. SELinux contexts. On enforcing systems, correct mode with wrong context still denies:

ansible web -i inventory.ini -m ansible.builtin.command -a "getenforce" # Enforcing? ansible web -i inventory.ini -m ansible.builtin.command -a "ls -Z /etc/app/"

Fix with community.general.sefcontext + restorecon, or ansible.posix.selinux booleans (httpd_can_network_connect is the classic) — never blanket setenforce 0 in production.

5. Python interpreter. Modules execute in Python on the target. Minimal images lack it, or ship two versions:

[web:vars] ansible_python_interpreter=/usr/bin/python3

Symptom MODULE FAILURE: /bin/sh: python: command not found → install python3 via a raw bootstrap task (ansible.builtin.raw: apt-get install -y python3) before any module that needs Python. CRLF-edited playbooks from Windows editors also break YAML parsing — keep LF endings (see WSL setup, Ch 02).

PRACTICAL — Encrypt and run without leaking
COMMAND ──────────────────────── ansible-vault encrypt_string 's3cr3t-db-pass' --name 'vault_db_password'

Expected: vault_db_password: !vault | $ANSIBLE_VAULT;1.1;AES256... — paste into group_vars/prod/vault.yml, commit safely.

COMMAND ──────────────────────── ansible-playbook -i inventory.ini site.yml --ask-vault-pass --check --diff

Why it matters: proves encrypted vars decrypt at run and dry-run shows structure without exposing values (with no_log: true). Common failure: Attempting to decrypt but no vault secrets found → password file path wrong or --vault-id label mismatch.

ansible-vault view group_vars/prod/vault.yml # read without decrypting to disk ansible-vault edit group_vars/prod/vault.yml # decrypt, edit, re-encrypt in one step ansible-vault rekey group_vars/prod/vault.yml # rotate the password on existing files

view for inspection, edit for changes, rekey for rotation — the file stays encrypted at every step except inside the editor.

Chapter 11 · Quality

LINT · CHECK · MOLECULE

7 MIN
🇪🇬 Quality وTesting: شرح عربي
الخطأ الواحد يتضاعف على مئة Server، فبوّب بثلاثة: ansible-lint يصطاد الأسلوب والأسماء القصيرة، و--check --diff يعاين الأثر على Inventory الحقيقي بلا تغيير، وMolecule (دورة create → converge → verify → destroy) يبرهن Convergence مرتين في بيئة Ephemeral. Convergence الثاني يجب أن يخرج changed=0 وإلا فالمحتوى متطاير (مثل طابع زمني داخل قالب) ويُعدّ رسوبًا متنكرًا. ثبّت إصدارات lint 6+ وmolecule نفسها محليًا وفي CI.
ansible-lint·--check --diff·Molecule·changed=0·verify
WHAT — Three quality gates

ansible-lint enforces style, FQCN, and common mistakes statically. --check --diff dry-runs a playbook against real inventory without changing it. Molecule tests roles in ephemeral containers or VMs (create → converge → verify → destroy).

Three gates before CI trusts a role
LINTstyle + FQCN→CHECK + DIFFblast radius→MOLECULEconverge twice→CIsame gates
ansible-lint site.yml ansible-playbook -i inventories/staging site.yml --check --diff molecule test

Molecule cycle: create (ephemeral host) → converge (apply role) → verify (assert state) → destroy. Second converge should report ok with zero changed — the idempotence proof.

WHY — Automation multiplies mistakes

A typo in one task runs on a hundred hosts in minutes. Lint catches the typo in seconds; check-mode previews blast radius; Molecule proves the role converges twice cleanly before CI ever touches staging. Without gates, every run is a fleet experiment.

WHERE DOES IT FIT — Quality before triggers
Vault-secured roles (Ch 10) → lint (seconds) → check/diff (minutes, safe) → molecule (minutes, ephemeral) → CI/CD (Ch 12) runs the same gates on every push

Local order mirrors CI order: fast static checks first, expensive ephemeral tests last. What passes locally must pass identically in CI — same lint version pinned, same molecule driver.

HOW IT WORKS — Static, dry-run, ephemeral

Lint: rule-based (yaml, fqcn, name[prefix], no-changed-when). Pin ansible-lint 6+ in dev requirements; ansible-lint --fix for safe auto-fixes. Check mode: modules report would-change without acting (--check); --diff shows file/service deltas. Command/shell tasks skip check unless check_mode: true is handled — another reason to prefer modules.

Molecule: molecule init role acme.web -d docker; molecule.yml defines platform, provisioner (ansible_playbook), verifier (ansible asserts). verify.yml asserts converged state:

- name: Verify hosts: all tasks: - name: Nginx is running ansible.builtin.assert: that: - "'nginx' in ansible_facts.services"
PRACTICAL — Gate a role locally
COMMAND ──────────────────────── ansible-lint roles/web/ && ansible-playbook -i inventories/staging site.yml --check --diff

Meaning: static rules, then dry-run delta. Expected: lint clean, --diff shows only intended file lines. Any unexpected changed line blocks the commit.

COMMAND ──────────────────────── molecule test

Expected: create → converge (changed) → converge (ok, idempotent) → verify passed → destroy. Second-converge changed=0 is the quality signature.

Why it matters: three gates catch three bug classes (style/FQCN, blast radius, convergence). Common failure: lint fqcn errors on short names → rewrite to ansible.builtin.*.

كل دفع Git push يقود Fleet بأمان: فحص سريع، اختبار Ephemeral، معاينة check --diff على Inventory Staging، اعتماد يدوي، ثم تقارب Rolling على Production (serial/forks واستراتيجيتا linear/free) مع كلمات سر Vault من أسرار CI. Git push·CI/CD·serial / forks·aws_ec2·--graph·issue catalog
WHAT — Every push drives automation safely

CI/CD triggers ansible-playbook after Git push, with per-environment inventory. The pipeline runs the Ch 11 gates, previews with --check --diff, requires approval for prod, then converges the fleet and feeds results to observability.

Every push can reach the fleet safely
GIT PUSH→LINT + TEST→STAGING DIFF→APPROVAL→PROD ROLLING
Git push → CI (lint) → molecule → ansible-playbook -i inventories/staging --check --diff → approval → ansible-playbook -i inventories/prod → observability → feedback to Git

Project structure:

inventories/{staging,prod}/hosts.yml group_vars/{all,staging,prod}.yml host_vars/ roles/ site.yml ansible.cfg requirements.yml
WHY — Manual runs do not survive scale

SSH-loop runs depend on who runs them, from which laptop, with which vars. CI gives one runner, pinned versions, secret-injected vault passwords, and an audit trail per commit. Staging-then-prod with identical playbooks makes promotion a change of -i path, not a new procedure.

CI/CD — COMMIT TO FLEET

9 MIN
WHERE DOES IT FIT — Production loop
Terraform provisions → Ansible configures (this series) → Docker packages → K8s orchestrates → CI triggers → observability verifies → feedback to Git

Ansible owns inside-OS convergence. Execution tuning (strategy, forks, serial) and inventory at scale (constructed inventory, group_vars layering) keep that convergence fast and scoped as fleets grow.

HOW IT WORKS — Strategies, scale, pipeline

Execution strategies: linear (default, lockstep per task) vs free (hosts race ahead). forks: 20 caps parallelism; serial: 1 (or "25%") rolls hosts in batches for safe restarts. ansible-inventory --graph verifies selection before any run.

- name: Rolling web update hosts: web serial: 1 tasks: - name: Render config ansible.builtin.template: src: nginx.conf.j2 dest: /etc/nginx/nginx.conf notify: Restart nginx handlers: - name: Restart nginx ansible.builtin.service: name: nginx state: restarted

GitHub Actions sketch: checkout → setup Python → pip install ansible ansible-lint molecule → ansible-galaxy install -r requirements.yml → lint → molecule test → check/diff staging (artifact) → manual approval → run prod with vault password from CI secrets.

Inventory at scale: dynamic/construction plugins generate groups from cloud tags; group_vars layers defaults → env → host; ansible-inventory -i inventories/prod --graph --vars is the pre-flight check.

DELEGATION · ASYNC · BLOCKS · TAGS

8 MIN
WHY — Real runs need escape hatches

Migrations fail mid-fleet; long jobs exceed SSH timeouts; load balancers must drain one host at a time; operators need to run only deploy tags at 2am. Without these controls every edge case becomes a separate playbook — with them, one playbook handles happy path, slow path, and failure path.

WHERE DOES IT FIT — Edge after production
CI/CD delivery (Ch 12) runs the standard path → this chapter handles the non-standard: different host (delegate) → long job (async) → failure (block/rescue) → subset (tags/limit)

These are execution modifiers, not new declarative models. Teach them last because each assumes the learner already reads plays, data flow, handlers, and rolling updates fluently.

HOW IT WORKS — Where, how long, what if, which

Delegation: task executes on delegate_to host but inventory_hostname still refers to original target — use for LB/API calls about the target. run_once: true + delegate_to: localhost runs a single API call, not once per host. Async: async: 600 (max seconds) + poll: 10 (check interval); poll: 0 fires and continues (collect with async_status later). Blocks: rescue runs only if block fails; always runs regardless — the try/except/finally of playbooks. Tags: tags: [deploy, never]; --tags, --skip-tags, --list-tags; never tags run only when requested.

Interview check
InterviewWhen do you delegate, async, block, or tag?
Delegate when the action concerns another host (LB, API, control node). Async when the job outlasts comfortable SSH blocking. Block/rescue/always when failure needs scoped recovery with guaranteed cleanup. Tags + limit when the operator must run a named subset safely.
