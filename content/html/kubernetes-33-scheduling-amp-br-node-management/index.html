CH 01

🎯 How Scheduling Works

🟡 6 MIN · CORE

The Scheduler is a control loop (Book 01 · CH 02) with one job: for each unscheduled Pod, pick the best feasible Node and bind the Pod to it. Every decision is a three-stage funnel:

The funnel — every Pod, every time
🆕 Pod appears schedulerName: default
──►
1 · FILTERfeasible nodes only
──►
2 · SCORErank the survivors
──►
3 · BINDwrite it down

filter kills nodes that can't take the Pod · score ranks nodes that can · the highest score wins

1 · FILTER — hard constraints
  • Pod's requests fit the node's allocatable (Book 02 · CH 14)
  • Taints tolerated? (Part II of this book)
  • nodeSelector / required affinity match?
  • Ports, volumes, hostNetwork conflicts

Zero nodes survive → Pod stays Pending. This is the #1 cause.

2 · SCORE — soft preferences
  • Preferred affinity/anti-affinity weights
  • Spreading vs packing balance (CH 08)
  • Image locality (image already pulled?), pod spread across zones…

Every plugin votes 0–100; sum decides. Ties → random.

# the binding is a real API object — you can see the decision: $ kubectl get pod web -o jsonpath='{.spec.nodeName}' minikube
⚠️
Scheduling is one-time, not a lease: once bound, the Scheduler never reconsiders. If the node degrades, the kubelet and node-lifecycle controller react (taints → evict) — the Scheduler only picks new placements. Re-scheduling happens only if the Pod dies and is recreated.
🔑
One sentence: Filter decides IF a node can; Score decides WHICH node should; Bind makes it official — and every tool in this book plugs into exactly one of those stages.

🧰 The Scheduling Toolbox

🟢 5 MIN

Five mechanisms decide placement. Knowing which stage each one acts in tells you which to reach for:

ToolStageHard or soft?One-line job
Resources (requests)Filter + Scorehard (capacity)"this Pod needs 500Mi / 250m somewhere"
Taints + TolerationsFilterhard (node repels)"keep ordinary Pods OFF this node"
Node affinity / nodeSelectorFilter / Scoreboth (required / preferred)"this Pod WANTS certain nodes"
Pod (anti-)affinityFilter / Scoreboth"co-locate / separate from other Pods"
topologySpreadScore (+ filter)soft or hard"spread evenly across zones/nodes"

⇄
🧲 affinity pod pulls toward
⇄
⚖️ spread distribution discipline
💡
Direction matters — the classic confusion: taints are node-side repulsion (the node refuses visitors without keys). Affinity is pod-side attraction (the Pod states its preferences). They never do each other's job — taints can't attract, affinity can't evict.
🗄️

Dedicate nodes
GPU / memory-huge
→ taints + tolerations

📍

Pin to hardware
SSD, region, zone
→ node affinity

🕸️

Resilience layout
HA across zones
→ spread + anti-affinity

🔑
Decision shortcut: keeping things OFF nodes → taints. Getting things ON specific nodes → node affinity. Relationships between Pods → pod affinity/anti-affinity. Evenness → spread. The rest of the book is these four, in depth.

CH 03

🚧 Taints — Effects & Use Cases

🟡 6 MIN · CORE

A taint is a node-side repulsion field: key=value:effect. Book 01's Lab 5 proved the mechanics — this page is the full strategic picture.

$ kubectl taint node node1 gpu=nvidia:NoSchedule node/node1 tainted $ kubectl taint node node1 gpu=nvidia:NoSchedule-  # trailing dash = remove
EffectRunning PodsNew PodsUse case
NoSchedulestayblocked unless tolerateddedicate nodes (GPU, SSD, prod-only)
PreferNoSchedulestayavoided if alternatives existsoft segregation — "try not to"
NoExecuteEVICTED nowblocked unless toleratedremove workloads when a node degrades

🎯 The three strategic uses

1 · Dedication
dedicated=ml:NoSchedule — only ML team's Pods (which tolerate) may land. A reservation without reserving capacity.

2 · Special hardware
gpu=nvidia:NoSchedule — prevents accidental placement of Pods that can't use the GPU… and of Pods that would waste it.

3 · Node condition → eviction
The control plane itself taints sick nodes with NoExecute — workloads flee a dying node automatically (CH 05).

⚠️
Two traps: (1) taints don't attract — a tolerated Pod may land elsewhere; to pin it, combine taints with node affinity (CH 06). (2) NoExecute is a weapon — adding one manually evicts production Pods mid-flight. Book 01 · Lab 5's trick question (taint after Pod exists) is this effect in action.
🔑
One sentence: taints come in three strengths — block new (NoSchedule), gently avoid (PreferNoSchedule), or evict existing (NoExecute) — and their job description is "keep the wrong workloads off this node."

CH 04

🔑 Tolerations — Operators & tolerationSeconds

🟡 6 MIN · CORE

A toleration is a Pod-side permission: "I may land on (or survive on) nodes carrying this taint." Match rule: key + operator (+ value) + effect.

spec: tolerations: - key: gpu operator: Equal # default — value must match exactly value: nvidia effect: NoSchedule - key: "dedicated" operator: Exists # ANY value, as long as key exists effect: NoSchedule - key: "" operator: Exists effect: "" # tolerate EVERYTHING (use with fear)
OperatorMatchesValue field
Equal defaultkey exists and value is identicalrequired
Existskey exists, any value (wildcard)must be empty

⏱️ tolerationSeconds — the grace timer (NoExecute only)

tolerations: - key: node.kubernetes.io/not-ready operator: Exists effect: NoExecute tolerationSeconds: 300 # if the taint lasts > 5 min → THEN evict me
💡
The resilience dial: a transient blip (< 5 min) → your Pod rides it out. A real outage → eviction after the grace period. This is exactly how the default tolerations on Deployments behave — it's why brief node hiccups don't mass-evict your fleet.
  • 🚫 No tolerationSeconds + NoExecute tolerated = survive forever on the tainted node
  • 🧩 Effect matching is literal: a toleration for NoSchedule does nothing against NoExecute on the same key
🔑
One sentence: tolerations are the only way past a taint — Equal for exact locks, Exists for skeleton keys, and tolerationSeconds turns a hard eviction into a grace period.

CH 05

🏥 Well-Known Taints — The Cluster's Own

🟡 6 MIN · CORE

The node-lifecycle controller and kubelet taint nodes automatically as conditions change. These aren't your taints — they're the cluster's immune response, and recognizing them is a diagnostic superpower.

TaintEffectMeaning
node.kubernetes.io/not-readyNoSchedule/NoExecutenode's Ready condition = False (kubelet heartbeat lost)
node.kubernetes.io/unreachableNoExecute/NoSchedulenode unreachable (network partition) — later becomes not-ready
node.kubernetes.io/disk-pressureNoScheduledisk running out — no NEW pods (existing keep running)
node.kubernetes.io/memory-pressureNoSchedulememory scarcity on the node
node.kubernetes.io/network-unavailableNoSchedulenetworking not configured yet (some clouds)
node.kubernetes.io/unschedulableNoScheduleadded by kubectl cordon — CH 10
node-role.kubernetes.io/control-planeNoSchedulethe brain-protection taint (Book 01 · CH 07)
Node degrades → NotReady / Unreachable NoExecute taint applied │ ├─ pods without toleration → evicted (grace per tolerationSeconds) ├─ deployments recreate them on healthy nodes ← Book 01 · CH 06 loop └─ node recovers → taint removed → schedulable again
💡
Debug move: mysterious Pending + "node(s) had untolerated taint" in events (Book 01 · CH 23)? Run kubectl describe node N | grep Taints — the taint list is the diagnosis. disk-pressure appearing on nodes is also your cue for storage cleanup (Book 05's territory).
🔑
One sentence: the cluster self-medicates with taints — sick nodes get NoExecute'd, workloads evacuate, healthy nodes absorb the load — and self-healing "magic" from Book 01 is really this mechanism plus reconciliation.

CH 06

🧲 nodeSelector & Node Affinity

🟡 6 MIN · CORE

Pod-side attraction to specific nodes. nodeSelector is the simple ancestor; node affinity adds operators, weights, and soft preferences.

spec: nodeSelector: # the simple form: hard, exact-match only disk: ssd affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: # HARD (filter) nodeSelectorTerms: - matchExpressions: - { key: disk, operator: In, values: [ssd, nvme] } preferredDuringSchedulingIgnoredDuringExecution: # SOFT (score) - weight: 80 # 1–100 — a vote, not a veto preference: matchExpressions: - { key: zone, operator: In, values: [east] }
OperatorsMeaning
In · NotInvalue is / is not in the list
Exists · DoesNotExistkey present / absent (any value)
Gt · Ltnumeric greater/less than (node labels as numbers)
⚠️
Decode the long names — they're the whole contract: required… = filter (no match → Pending). preferred… = score (hint). IgnoredDuringExecution = if the node's labels change after your Pod is running, the Pod stays — affinity is checked at scheduling time only. (The mirror concept RequiredDuringExecution exists for pod affinity — live re-evaluation.)
label node: kubectl label node n1 disk=ssd
→
Pod with disk In [ssd]
→
lands only there
🔑
One sentence: node affinity = nodeSelector with superpowers — operators for matching, weights for preferences, and "IgnoredDuringExecution" meaning the lock is checked once, at scheduling time. Lab 1 proves the hard/soft split live.

CH 07

👥 Pod Affinity & Anti-Affinity

🟡 6 MIN · CORE

Node affinity asks "which nodes?" — pod affinity asks "near which other Pods?", measured through a topology domain (same node? same zone? same region?).

spec: affinity: podAffinity: # CO-LOCATE — "keep me near my cache" requiredDuringSchedulingIgnoredDuringExecution: - topologyKey: kubernetes.io/hostname # same NODE labelSelector: matchLabels: { app: cache } podAntiAffinity: # SEPARATE — "never put replicas together" preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 podAffinityTerm: topologyKey: topology.kubernetes.io/zone # different ZONES labelSelector: matchLabels: { app: web }
topologyKey (common)Domain = "together means…"
kubernetes.io/hostnamesame physical node
topology.kubernetes.io/zonesame availability zone
topology.kubernetes.io/regionsame region
✅ Affinity (co-locate)

web + its cache on one node → localhost-fast calls, one bill. Latency-sensitive pairs that talk constantly.

✅ Anti-affinity (separate)

3 replicas of web on 3 zones → one zone dies, 2/3 survive. Never stack the blast radius.

⚠️
required anti-affinity is a placement cliff: more replicas than topology domains → the extras sit Pending forever (3 replicas, 1 node = 1 runs, 2 Pending — Lab 2 proves it). Production default: preferred + weight 100, or better — topologySpread (CH 08).
🔑
One sentence: pod (anti-)affinity = relationship rules between Pods, expressed as "same/different topology domain" — powerful for latency and HA, but required versions trade flexibility for guarantees.

CH 08

⚖️ topologySpreadConstraints

🟡 6 MIN · CORE

Anti-affinity answers "are any Pods here?" — spread answers a better question: "is the distribution even?" One constraint replaces a pile of weights.

spec: topologySpreadConstraints: - maxSkew: 1 # max allowed imbalance topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: DoNotSchedule # or: ScheduleAnyway (soft) labelSelector: matchLabels: { app: web } # — maxSkew = (most pods in one domain) − (fewest) # — domains with ZERO pods count too (they pull new pods!)
maxSkew: 1 in action — 6 replicas, 3 zones
zone-a2 🫛🫛
zone-b2 🫛🫛
zone-c2 🫛🫛

2−2−2 → skew 0 ✅  ·  3−2−1 → skew 2 ❌ next Pod forced to zone-c  ·  3−3−0 → skew 3, but 0-domain "pulls" until fed

whenUnsatisfiableBehavior when the rule can't hold
DoNotSchedulehard — Pod waits (Pending) until it can comply
ScheduleAnywaysoft — place anyway, but the score penalty steers future Pods
💡
Spread vs anti-affinity — when which? Anti-affinity: boolean togetherness, per-Pod-pair relationships, cheap on small sets. Spread: numeric evenness across N domains, scales to hundreds of replicas, and — the killer feature — counts empty domains, so a fresh zone always receives traffic first.
🔑
One sentence: topologySpreadConstraints = "keep skew ≤ maxSkew across this topology" — the modern, scalable answer to "spread my replicas," with a hard mode (DoNotSchedule) and a soft mode (ScheduleAnyway).

CH 09

👑 Priority Classes & Preemption

🟡 6 MIN · CORE

When nothing fits anywhere, a high-priority Pod may evict lower-priority Pods to make room. Priority is the cluster's pecking order under scarcity.

apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: { name: high-priority } value: 1000000 # higher = more important globalDefault: false # one class MAY be the default preemptionPolicy: PreemptLowerPriority # default; or Never
spec: priorityClassName: high-priority # attach to the Pod
Built-in classValueReserved for
system-node-critical2,000,001,000kubelet-essential: CNI, kube-proxy
system-cluster-critical2,000,000,000CoreDNS, metrics — cluster functions
your Pods (no class)0everything below the system floor

🗡️ How preemption actually fires

High-prio Pod → Pending (no node fits — filter fails on resources) │ scheduler tries placement ▼ Preemption attempt: find node where evicting lower-prio victims would free enough for the whole Pod (incl. its requests!) ▼ victims deleted gracefully (their owners recreate them — elsewhere, later) ▼ high-prio Pod scheduled into the gap ✅
⚠️
Two honesty notes: (1) preemption is resource-arithmetic, not revenge — the scheduler only kills the minimum set of lowest-priority victims, and only when the high-prio Pod genuinely can't fit. (2) Your Pods' priority also decides kubelet eviction order under node pressure — layered on top of QoS from Book 02 · CH 15.
🔑
One sentence: PriorityClass = a number that means "in a shortage, I eat first" — driving both preemption at scheduling time and eviction order at runtime. Lab 3 watches a real preemption.

CH 10

🛠️ Cordon, Drain & Uncordon

🟡 6 MIN · CORE

Node maintenance (kernel upgrades, hardware swaps) without downtime = a three-verb dance. Cordon stops new arrivals; drain evacuates; uncordon reopens.

$ kubectl cordon node1 # 1 · add unschedulable taint (CH 05) node/node1 cordoned $ kubectl drain node1 --ignore-daemonsets --delete-emptydir-data node/node1 cordoned # drain cordons for you too evicting pod shop/web-7d9f # graceful eviction — PDB-aware! pod/web-7d9f evicted $ # …do the maintenance… $ kubectl uncordon node1 # 3 · reopen node/node1 uncordoned
FlagWhy it exists
--ignore-daemonsetsDaemonSet Pods are node-bound by design (log agents, CNI) — drain skips them; without the flag drain aborts
--delete-emptydir-dataPods with emptyDir lose data on eviction — drain refuses by default; the flag says "ephemeral, go ahead"
--forceevict Pods not managed by a controller (standalone Pods die with no replacement — you were warned, Book 01 · CH 15)
--grace-period / --timeouttune eviction grace; PDBs can block indefinitely → drain waits/times out
⚠️
Drain respects PodDisruptionBudgets (PDBs) — "keep ≥ 2 web replicas alive" pauses drain until it can evict safely. Production rule: define PDBs before your first real drain, or the "safety" is zero. (Also: cordon ≠ drain — cordon alone just stops new placements.)
1cordon — no NEW Pods land (existing keep running)
2drain — evict everything the controllers can recreate, PDB-respecting
3maintain — patch, reboot, swap hardware
4uncordon — taint removed; Scheduler refills the node
🔑
One sentence: maintenance = cordon (close the door) → drain (empty the room, politely) → uncordon (reopen) — and the two flags you'll type forever are --ignore-daemonsets and --delete-emptydir-data. Lab 4 runs the full cycle.

CH 11

🪨 Static Pods

🟡 5 MIN

Static Pods are created and managed directly by the kubelet, from manifest files on the node's disk — no Deployment, no Scheduler, no controller. The Scheduler's total bypass.

kubelet flags: --pod-manifest-path=/etc/kubernetes/manifests │ watches the dir (default on kubeadm) ▼ file appears → kubelet runs the Pod no API call needed file edited → Pod updated file IS the spec file deleted → Pod dies kubectl delete → Pod briefly dies → kubelet recreates it (undeletable!)
$ kubectl get pods -n kube-system NAME                            READY  STATUS etcd-minikube                  1/1    Running  # ← static! kube-apiserver-minikube        1/1    Running  # ← static! kube-controller-manager-minikube 1/1   Running  # ← static! kube-scheduler-minikube        1/1    Running  # ← static! coredns-7db6d8ff4b-abcde       1/1    Running  # ← Deployment
💡
The bootstrap paradox, solved: the Control Plane runs as static Pods because something must run the API Server before the API Server exists. The kubelet + a folder of YAML boot the entire brain — chicken, meet egg. (The -minikube / -nodename suffix: kubelet also creates a read-only mirror Pod in the API so you can kubectl get them.)
  • 🧪 Your own static Pod: drop a valid Pod manifest into the manifest dir → running within seconds, Scheduler never involved
  • 🚧 They ignore taints, affinity, and drain-eviction logic (the file rules) — that's why drain --ignore-daemonsets and static/mirror pods go together
🔑
One sentence: static Pods are kubelet-and-disk only — the mechanism that boots the control plane itself, undeletable through kubectl because the source of truth is a file on the node.

LAB 1

🔬 Node Affinity — Required vs Preferred

🟠 12 MIN · HANDS-ON
STEP 1 · Label the node + hard affinity
$ kubectl label node minikube disk=ssd $ kubectl create deploy aff --image=nginx --replicas=2 $ kubectl patch deploy aff --type=merge -p '{"spec":{"template":{"spec":{ "affinity":{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution": {"nodeSelectorTerms":[{"matchExpressions":[{"key":"disk","operator":"In", "values":["ssd"]}]}]}}}}}}}' $ kubectl get pods -o wide  # all on minikube ✓ (label matches)
STEP 2 · Break the label — watch required bite
$ kubectl label node minikube disk- $ kubectl scale deploy aff --replicas=3 $ kubectl get pods aff-xxx   1/1  Running   # old pods: IgnoredDuringExecution — STAY aff-yyy   0/1  Pending   # new pod: no node matches → filter fails $ kubectl describe pod -l app=aff | grep -A2 Events | tail -2 0/1 nodes are available: 1 node(s) didn't match … affinity
STEP 3 · Switch to preferred — same break, different outcome
$ kubectl delete deploy aff && kubectl create deploy soft --image=nginx --replicas=2 $ kubectl patch deploy soft --type=merge -p '{"spec":{"template":{"spec":{ "affinity":{"nodeAffinity":{"preferredDuringSchedulingIgnoredDuringExecution": [{"weight":80,"preference":{"matchExpressions":[{"key":"disk","operator":"In", "values":["ssd"]}]}}]}}}}}}' $ kubectl scale deploy soft --replicas=3  # label still gone… $ kubectl get pods  # 3/3 Running — preferred only VOTES, never vetoes

Proved: required = filter (Pending on mismatch), preferred = score (never blocks), IgnoredDuringExecution = running Pods stay. Teardown: kubectl delete deploy soft.

LAB 2

🔬 Anti-Affinity — Prove the Separation

🟠 10 MIN · HANDS-ON
STEP 1 · Required anti-affinity on a ONE-node cluster
$ kubectl create deploy sep --image=nginx --replicas=3 $ kubectl patch deploy sep --type=merge -p '{"spec":{"template":{"spec":{ "affinity":{"podAntiAffinity":{"requiredDuringSchedulingIgnoredDuringExecution": [{"topologyKey":"kubernetes.io/hostname", "labelSelector":{"matchLabels":{"app":"sep"}}}]}}}}}}' $ kubectl get pods sep-aaa   1/1  Running  # fits — node is empty of "sep" sep-bbb   0/1  Pending  # node already has one! sep-ccc   0/1  Pending  # same hostname domain — no second one exists
👀 WHY (events)
$ kubectl describe pod sep-bbb | tail -2 0/1 nodes are available: 1 node(s) didn't match pod anti-affinity rules.
🔍 THE LESSON
# required anti-affinity: # replicas > topology # domains = permanent # Pending. 3 replicas # × 1 node = 2 orphans.
STEP 2 · Soften it — everyone fits
$ kubectl patch deploy sep --type=merge -p '{"spec":{"template":{"spec":{ "affinity":{"podAntiAffinity":{"preferredDuringSchedulingIgnoredDuringExecution": [{"weight":100,"podAffinityTerm":{"topologyKey":"kubernetes.io/hostname", "labelSelector":{"matchLabels":{"app":"sep"}}}}]}}}}}}' $ kubectl get pods  # 3/3 Running — co-located, but only because we must

Proved: topology domains are finite; required anti-affinity hard-caps your replica count per domain. Teardown: kubectl delete deploy sep.

LAB 3

🔬 Priority & Preemption Live

🟠 12 MIN · HANDS-ON
💡
Setup note: preemption needs resource pressure. We fill the node with low-priority Pods holding real memory requests, then ask for a big high-priority Pod. Adjust sizes to your cluster's free memory.
STEP 1 · Two classes + a filled floor
$ kubectl create priorityclass low  --value=100 $ kubectl create priorityclass high --value=1000 $ kubectl create deploy filler --image=polinux/stress --replicas=6 \   -- stress --vm 1 --vm-bytes 10M --timeout 6000s $ kubectl set resources deploy/filler --requests=memory=500Mi $ kubectl patch deploy filler --type=merge -p \   '{"spec":{"template":{"spec":{"priorityClassName":"low"}}}}' $ kubectl get pods -l app=filler  # 6 Running — floor is loaded
STEP 2 · The VIP arrives — preemption fires
$ kubectl run vip --image=polinux/stress --restart=Never \   --overrides='{"spec":{"priorityClassName":"high","containers":[{"name":"s", "image":"polinux/stress","args":["--vm","1","--vm-bytes","50M"], "resources":{"requests":{"memory":"1500Mi"}}}]}}' -- stress --vm 1 --vm-bytes 50M $ kubectl get pods -w filler-xxx   Terminating  # ← a low-prio VICTIM was chosen vip          Running      # ← took its place
STEP 3 · Read the verdict
$ kubectl get events | grep -i preempt Preempted by pod default/vip … to make room $ kubectl get events | grep vip | head -3 Successfully assigned … node minikube

Proved: scarcity + priority = eviction of the weak, minimum victims only. The filler Deployment recreates its Pod (Book 01 · CH 06) — everyone survives, the VIP just ate first. Teardown: kubectl delete pod vip && kubectl delete deploy filler && kubectl delete pc low high.

LAB 4

🛠️ The Maintenance Cycle

🟠 12 MIN · HANDS-ON
STEP 1 · Cordon — close the door
$ kubectl cordon minikube $ kubectl get nodes NAME     STATUS              ROLES minikube Ready,SchedulingDisabled  control-plane,master $ kubectl describe node minikube | grep Taints node.kubernetes.io/unschedulable:NoSchedule  # ← the cordon taint (CH 05!) $ kubectl scale deploy web --replicas=3  # (any deployment) $ kubectl get pods -w  # 3rd pod → Pending: nowhere to land
STEP 2 · Drain — empty the room
$ kubectl drain minikube --ignore-daemonsets --delete-emptydir-data node/minikube cordoned evicting pod kube-system/coredns-… evicting pod default/web-aaa pod/web-aaa evicted $ kubectl get pods -A | grep -v Running # (single-node cluster: evicted pods go Pending — they have # nowhere else to go. on a 3-node cluster they'd REAPPEAR # on the healthy nodes — Book 01 · CH 06 in action.)
STEP 3 · Uncordon — reopen
$ kubectl uncordon minikube $ kubectl get nodes  # Ready — SchedulingDisabled gone $ kubectl get pods -w  # Pending pods schedule immediately 🎉

Proved: cordon = a NoSchedule taint you typed; drain = graceful, PDB-respecting evacuation; uncordon = instant refill. Teardown: scale your deployment back and delete leftovers.

GLOSS

📚 Glossary

🔵 REFERENCE
Filter / Score / Bind — the Scheduler's funnel: feasible → ranked → written to the Pod's nodeName.
Taint — node-side repulsion, key=value:effect; effects NoSchedule / PreferNoSchedule / NoExecute.
Toleration — Pod-side permission past a taint; operators Equal (exact) and Exists (wildcard, empty value).
tolerationSeconds — grace period before a NoExecute eviction takes effect.
Well-known taints — not-ready, unreachable, disk-pressure, memory-pressure, network-unavailable, unschedulable, control-plane — the cluster's automatic immune taints.
nodeSelector — simple hard label match on nodes.
Node affinity — required (filter) / preferred (score, weight 1–100) node matching with In/NotIn/Exists/DoesNotExist/Gt/Lt.
IgnoredDuringExecution — affinity evaluated at scheduling time only; later label changes never evict.
Pod (anti-)affinity — co-location / separation rules relative to other Pods, scoped by topologyKey.
topologyKey — the domain label defining "together": kubernetes.io/hostname, topology.kubernetes.io/zone|region.
topologySpreadConstraints — keep distribution even: maxSkew + topologyKey + whenUnsatisfiable (DoNotSchedule / ScheduleAnyway); empty domains attract.
PriorityClass — named integer priority; system-node-critical (2000001000) > system-cluster-critical (2000000000) > default 0.
Preemption — Scheduler evicts minimum lower-priority victims to place a higher-priority Pending Pod.
Cordon — mark node unschedulable (adds unschedulable:NoSchedule taint); no evictions.
Drain — cordon + graceful, PDB-respecting eviction of all recreatable Pods; --ignore-daemonsets / --delete-emptydir-data / --force.
PodDisruptionBudget (PDB) — "keep ≥ N replicas during voluntary disruptions"; drain waits for it.
Static Pod — kubelet-managed Pod from a node-local manifest directory (/etc/kubernetes/manifests); runs the control plane itself; undeletable via API.
Mirror Pod — the API-side read-only reflection kubelet creates so static Pods appear in kubectl.

$ kubectl cordon N $ kubectl drain N --ignore-daemonsets \     --delete-emptydir-data [--force] [--timeout=…] # evicts gracefully, respects PDBs # DaemonSet pods skipped $ kubectl uncordon N static pods: /etc/kubernetes/manifests → kubelet-born, API-undeletable
🧠 Facts worth a job offer
  • Scheduling = Filter → Score → Bind; it happens ONCE — no re-evaluation of running Pods
  • Taints repel (node-side), affinity attracts (pod-side) — they never do each other's job
  • NoExecute = evict existing; tolerationSeconds = grace timer; Equal needs a value, Exists doesn't
  • required anti-affinity caps replicas at topology-domain count; spread constraints scale better
  • Preemption is minimum-victim arithmetic, not revenge; priority also orders kubelet evictions
  • Drain = cordon + PDB-respecting eviction; DaemonSet pods are skipped, not evicted
  • Static Pods bootstrap the control plane — the file on disk is the source of truth
