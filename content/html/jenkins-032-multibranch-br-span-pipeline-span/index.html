LAB 03 — MULTIBRANCH PIPELINE

MULTIBRANCH
PIPELINE

One job that becomes three. Jenkins discovers branches from a generic Git remote, builds each one from its own Jenkinsfile, and scopes behavior with when { BRANCH_NAME }.
GENERIC GIT SOURCE  ·  FOLDER OF JOBS  ·  FILTER BY NAME  ·  WHEN BRANCH_NAME

MULTIBRANCH = FOLDER OF JOBS — DISCOVERY MODEL

MAIN Jenkinsfile found → build main
DEV Jenkinsfile found → build dev
STG Jenkinsfile + when(stg) runs stg
● SCAN● FILTER main dev stg● when BRANCH_NAME● ORPHAN → REMOVE
GIT SOURCE generic Git
not GitHub

KEY CONCEPT — FOLDER OF JOBS

A Multibranch Pipeline is a folder of individual pipeline jobs — one per discovered branch. Jenkins scans the generic Git branch source, applies Filter by name (main dev stg), and for each match looks for a Jenkinsfile. No Jenkinsfile → skipped in scan log. Branch jobs are not directly configurable — only the parent controls behavior.

Behaviors: Check out to matching local branch · Clean before checkout · Clean after checkout  |  Discovery: Scan log · Scan Multibranch Pipeline Now  |  Cleanup: orphaned item removed on next scan  |  Conditional: when { env.BRANCH_NAME == 'stg' }

Concept & Architecture

Why one job replaces three

01 / Branch as Job

Without multibranch, each branch needs its own pipeline job — duplicated config, drift, manual creation. Multibranch inverts this: you configure once at the parent, Jenkins discovers branches that match the filter, and each branch runs the Jenkinsfile committed on that branch. One file, three behaviors — controlled by env.BRANCH_NAME.

SCANDISCOVERGit branches
FILTERMATCHmain dev stg
CHECKJENKINSFILE?found / skip
CREATEBRANCH JOBfolder item
RUNWHENBRANCH_NAME
CLEANORPHANon rescan

BRANCH SOURCE — GENERIC GIT

This lab deliberately uses Git (not GitHub) as the branch source, even if the remote is hosted on GitHub. Proves Jenkins works with any Git URL. No webhook — periodic / manual scans only.

PARENT CONTROLS ALL

Individual branch jobs (main / dev / stg) cannot be reconfigured directly. Filter, checkout behavior, scan triggers, and orphan strategy live only on the parent Multibranch job.

02 / Architecture — Scan → Filter → Jenkinsfile → Conditional

Create, Wire & Scan

Steps 1–4

04 / Step 1 — Create the Multibranch Pipeline Job

ACTION — Jenkins → New Item

Name it to match the repository (mapping clarity). Select Multibranch Pipeline → OK. Skip/reuse if the job already exists (per Step 0.3).
# Jenkins home Dashboard → New Item → Multibranch Pipeline → Name: <repo-name> → OK

05 / Step 2 — Add a Git Branch Source

ACTION — Branch Sources → Add source → Git

Not the GitHub-specific source — this lab uses the generic Git source even if hosted on GitHub. Project Repository: paste clone URL (HTTPS or SSH). Credentials: None if public, else the credential confirmed in Step 0. Leave other defaults.

WHY GENERIC GIT

It decouples Jenkins from GitHub's API. Any Git remote works — GitHub, GitLab, Bitbucket, or internal — and forces explicit branch filtering via wildcards rather than GitHub's org/repo integration.

# branch source config Branch Sources → Add source → Git Project Repository: https://github.com/<user>/<repo>.git Credentials: None (public) / <ssh-or-token> (private)

06 / Step 3 — Configure Branch Filtering & Behaviors

FILTER — Behaviors → Filter by name (with wildcards)

Include: main dev stg (space-separated exact names — no wildcards needed for three fixed branches). Exclude: blank — anything not included is automatically excluded.

BEHAVIORS — Add three more:

  • Check out to matching local branch — build checks out the actual branch HEAD, not a detached commit.
  • Clean before checkout — wipe workspace before pulling.
  • Clean after checkout — clean after (keeps agents tidy).
Leave Build strategies at defaults unless a specific need arises.

07 / Step 4 — Save and Observe the Initial Scan

ACTION — Click Save

This triggers an automatic scan. Open Scan Multibranch Pipeline Log (left nav). If no Jenkinsfile exists yet on any branch, the folder shows empty — scan log reports Jenkinsfile not found per branch. This is expected at this point.
# Scan Multibranch Pipeline Log — before Jenkinsfile exists > git ls-remote --symref https://github.com/<user>/<repo>.git Checking branch main → Jenkinsfile not found (no build) Checking branch dev → Jenkinsfile not found Checking branch stg → Jenkinsfile not found Finished: 0 branches built, 3 discovered, 0 with Jenkinsfile

SCAN LOG IS THE SOURCE OF TRUTH

Every discovery, filter decision, and Jenkinsfile check is logged there. When the folder is empty, the scan log tells you why — no guessing.

Jenkinsfile & Branches

Steps 5–7

08 / Step 5 — Add a Jenkinsfile to the Repository

On the default branch (main), create a minimal pipeline, commit, and push.

pipeline { agent { label 'linux' } options { buildDiscarder(logRotator(numToKeepStr: '5')) disableConcurrentBuilds() } stages { stage('Hello') { steps { echo 'hello' } } } }
# commit on main $ git checkout main $ cat > Jenkinsfile <<'EOF' ... pipeline above ... EOF $ git add Jenkinsfile && git commit -m "Add Jenkinsfile" && git push → origin/main updated

09 / Step 6 — Trigger a Rescan (no webhooks)

No inbound webhook is configured — intentionally, to simulate an air-gapped Jenkins. Jenkins won't know about the new commit until scanned.

ACTION — Multibranch job → Scan Multibranch Pipeline Now

Confirm scan log now shows Jenkinsfile found on the default branch and a build was auto-triggered. Optionally configure a periodic scan interval (e.g. every 2–5 min) so this happens without manual clicks.
# Scan log after Jenkinsfile added to main Checking branch main → Jenkinsfile found → Met criteria → build triggered (#1) Checking branch dev → Jenkinsfile not found (still empty — branch not yet created) Checking branch stg → Jenkinsfile not found # Build #1 — main — console [Hello] echo 'hello' hello Finished: SUCCESS
VERIFY — Branch main now appears as a buildable job inside the Multibranch folder. Stage view shows Hello PASSED. Without Jenkinsfile on dev / stg, they don't appear yet — correct.

10 / Step 7 — Create the dev and stg Branches

Branch both from the default branch that already has the Jenkinsfile, so each inherits it. Skip any that already exist (Step 0.3).

# create + push both branches $ git checkout main && git pull $ git checkout -b dev && git push -u origin dev $ git checkout -b stg && git push -u origin stg → origin/dev new branch → origin/stg new branch # rescan Jenkins → Scan Multibranch Pipeline Now
# Scan log after dev + stg pushed Checking branch main → Jenkinsfile found → build Checking branch dev → Jenkinsfile found → build Checking branch stg → Jenkinsfile found → build Finished: 3 branches built, 3 discovered, 3 with Jenkinsfile
MAIN Hello PASSED main
DEV Hello PASSED dev
STG Hello PASSED stg
PROOF — All three jobs now live inside the parent folder — one parent config created three branch pipelines. ● DISCOVERY PROVED

Conditional & Orphan

Steps 8–9

11 / Step 8 — Branch-Specific Behavior (stg only)

On stg, add a stage that only runs there via when { BRANCH_NAME } — the core mechanism that lets one shared file behave as three pipelines. Also edit README.md so checkout correctness is visible.

# on branch stg — add when-guarded stage stage('Staging Verification (stg only)') { when { expression { return env.BRANCH_NAME == 'stg' } } steps { sh 'cat README.md' } }
# full Jenkinsfile on stg after edit pipeline { agent { label 'linux' } options { buildDiscarder(logRotator(numToKeepStr: '5')); disableConcurrentBuilds() } stages { stage('Hello') { steps { echo 'hello' } } stage('Staging Verification (stg only)') { when { expression { return env.BRANCH_NAME == 'stg' } } steps { sh 'cat README.md' } } } }
# commit on stg $ git checkout stg $ edit Jenkinsfile + README.md $ git add Jenkinsfile README.md && git commit -m "stg: add conditional stage + readme" && git push # trigger Jenkins → branch stg → Build Now (or Scan Multibranch Pipeline Now)

12 / What to Verify After Step 8

STG — STAGE RUNS

Console shows checkout of stg (not detached), then Staging Verification executes and prints README.md.

Checking out stg → origin/stg [Staging Verification] ● RUN cat README.md → # stg readme …

MAIN / DEV — STAGE SKIPPED

Run each job again. Console shows Skipped due to when conditional. The stage definition is inherited but not executed — exactly the intended behavior.

[Staging Verification] ○ SKIPPED when BRANCH_NAME == 'stg' → false

WHY env.BRANCH_NAME

Jenkins injects BRANCH_NAME per branch job. when { expression { env.BRANCH_NAME == 'stg' } } is evaluated before the stage's steps run — no extra Jenkinsfile per branch needed.

CHECKOUTBRANCH HEADmatching local
HELLOALWAYSall branches
WHENBRANCH_NAME?== 'stg'
STG ONLYVERIFYsh cat README
SKIPOTHERmain / dev

13 / Step 9 — Merge Back & Orphan Cleanup

MERGE — Check out default branch, merge stg, push.

git checkout main && git merge stg && git push. Run main again: it now contains the Staging Verification stage definition, but the stage is SKIPPED (since main != stg).

ORPHAN — Delete a branch remotely, then rescan.

git push origin --delete dev (or delete via UI). Then Scan Multibranch Pipeline Now. Scan log reports orphaned item and the Jenkins job for that branch is removed — while main / stg remain.
# delete + rescan $ git push origin --delete dev or: GitHub → Branches → delete Jenkins → Scan Multibranch Pipeline Now → Will remove PR-... / orphaned item: dev → removed Remaining: main, stg (2 branches) # main after merge — stage present but skipped [Hello] ● PASSED [Staging Verification] ○ SKIPPED when → false on main

GOTCHA — ORPHANS ONLY ON RESCAN

Deleting a remote branch does not instantly remove its Jenkins job. Only the next scan (manual, periodic, or webhook-triggered) evaluates orphans. No webhook here is intentional — this lab is air-gapped by design.
