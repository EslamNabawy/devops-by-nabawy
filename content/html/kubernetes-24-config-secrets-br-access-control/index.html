CH 01

⚙️ ConfigMaps — What & Why

🟢 4 MIN

The problem: bake LOG_LEVEL=debug into your image and every environment change = rebuild, re-push, re-pull. A ConfigMap decouples configuration from the image: one image, many configs.

❌ Config baked into the image
app:v1 + debug → build → push app:v1 + info → build → push app:v1 + prod → build → push 3 images, 3 pipelines, 3 chances to drift
✅ Config injected at runtime
app:v1 (built ONCE) + cfg-debug → dev cluster + cfg-staging → staging + cfg-prod → prod same image everywhere — only the map differs

🛠️ Create one — three ways

$ kubectl create configmap app-config --from-literal=LOG_LEVEL=debug $ kubectl create configmap app-conf --from-file=app.conf $ kubectl apply -f configmap.yaml # the declarative way (CH 02) configmap/app-config created
🔑
One sentence: a ConfigMap is a named bag of key/value pairs (or files) that lives inside a namespace — injected into Pods as env vars or files. It's the Kubernetes take on 12-factor config: config belongs to the environment, not the artifact.

⏭️ How do Pods actually consume one? ← CH 02: Creating & Mounting

CH 02

📥 Creating & Mounting ConfigMaps

🟡 6 MIN · CORE
apiVersion: v1 kind: ConfigMap metadata: { name: app-config } data: LOG_LEVEL: "debug" # simple key → env var app.conf: | # whole file as one key listen 8080 workers 4

🔌 Two consumption methods — they behave differently

spec: containers: - name: app image: myapp:2.0 env: # METHOD 1 · single keys as env vars - name: LOG_LEVEL valueFrom: configMapKeyRef: { name: app-config, key: LOG_LEVEL } envFrom: # …or import EVERY key as env - configMapRef: { name: app-config } volumeMounts: # METHOD 2 · keys as FILES - { name: cfg, mountPath: /etc/app } volumes: - name: cfg configMap: { name: app-config } # each key becomes a file
📦 As env vars📁 As volume files
Shapeflat KEY=valuereal files (app.conf, nested keys ok)
Update behaviornever — snapshot at container startauto-updated by kubelet (~1 min, CH 03)
Best forsimple toggles, ports, feature flagsconfig files, templates, anything the app re-reads
🔑
Rule of thumb: env vars are a snapshot, volume mounts are a live feed. Choose by asking: "does my app re-read its config file, or read the environment once at boot?"

CH 03

🔄 Hot-Reload — What Actually Updates

🟡 6 MIN · CORE

The most-Googled ConfigMap question. The answer is a 2×2 matrix — and one famous trap.

Consumed as…ConfigMap changes → Pod sees…Why
Env var❌ Neverenvironment is fixed at container start (Linux process rules, not k8s')
Volume file✅ Yes — eventually (~1 min)kubelet syncs mounted files on its sync period
Volume via subPath❌ NeversubPath mounts a copy; the symlink chain is broken
Env + app restart✅ Yes (on next start)new container = fresh snapshot
⚠️
"Eventually" means eventually: updates ride the kubelet sync period plus the API watch cache — up to ~1 minute of delay, in no guaranteed order. Apps that cache config at startup (Java, many frameworks) still see nothing until they re-read the file. The file changing ≠ your app noticing.
volumes: - name: cfg configMap: { name: app-config, immutable: true } # freeze it entirely
  • 🧊 immutable: true — rejects all updates (and can't be un-set without delete/recreate). Trade-off: zero hot-reload in exchange for protecting against accidental changes + better kubelet performance at scale.
  • 🔁 Common production pattern: app watches its config file (or a sidecar triggers a reload endpoint) — k8s delivers the file, your app decides to care.
🔑
Exam-grade answer: volume-mounted ConfigMaps auto-update (eventually, ~1 min); env vars and subPath mounts never update — a Pod restart is the only guaranteed way to re-read env config. Lab 1 proves it.

CH 04

🔐 Secrets — vs ConfigMaps

🟡 6 MIN · CORE

Same mechanism, different cargo. A Secret holds data you'd flinch to print in a git log: passwords, tokens, TLS keys, registry credentials.

Aspect⚙️ ConfigMap🔐 Secret
Cargoplain configsensitive data (passwords, certs, tokens)
Values on diskplain textbase64-encoded (data) — CH 07 for what that does and doesn't mean
Value size~1 MiB~1 MiB
Consumed asenv / volumeenv / volume — same two methods
Default visibilityanyone who can get itgated by RBAC — reading secrets is its own permission (Part III)
Write conveniencedatadata (pre-encoded) or stringData (plain — API encodes for you)
⚠️
Do not skip this: base64 is encoding, not encryption — anyone can decode it with one command. By default, Secrets sit in etcd unencrypted. Real protection = etcd encryption-at-rest + tight RBAC (Part III). Full autopsy in CH 07.
$ kubectl create secret generic db-pass --from-literal=PASSWORD="s3cr3t" secret/db-pass created
🔑
Mental model: ConfigMap = the whiteboard in the apartment (anyone may read). Secret = the safe (base64 = the box it ships in; RBAC = who has the key). Same delivery mechanism, different trust level.

CH 05

🏷️ Secret Types & Creation

🟡 6 MIN · CORE

type is a label that tells Kubernetes (and tooling) what shape the keys should take. The default is Opaque — "just key/values".

TypeRequired keysUsed by
Opaque defaultanything you likeapp passwords, API keys, generic data
kubernetes.io/dockerconfigjson.dockerconfigjsonimagePullSecrets — private registry auth (CH 06)
kubernetes.io/tlstls.crt + tls.keyIngress TLS termination (Book 03)
kubernetes.io/basic-authusername, passwordbasic-auth integrations
kubernetes.io/service-account-token— (API-managed)SA tokens — mostly automatic since v1.24 (CH 11)

🛠️ Creation — imperative & declarative

$ kubectl create secret generic db-pass --from-literal=PASSWORD="s3cr3t" $ kubectl create secret docker-registry regcred \ --docker-server=registry.example.com --docker-username=ci \ --docker-password=$TOKEN $ kubectl create secret tls web-tls --cert=tls.crt --key=tls.key
apiVersion: v1 kind: Secret metadata: { name: db-pass } type: Opaque stringData: # WRITE-only convenience — plain text in PASSWORD: "s3cr3t" # the API base64-encodes it into `data`
💡
stringData never comes back out — kubectl get secret -o yaml always shows data with base64 values. Handy for readable YAML in Git pipelines (with the Git-secrets caveat of CH 07).
🔑
Remember the pair: dockerconfigjson → pulling images · tls → serving HTTPS. These two built-in types are the exam's favorites because they have mandatory key names.

CH 06

📤 Mounting Secrets + imagePullSecrets

🟡 6 MIN · CORE

Same two doors as ConfigMaps — env vars (snapshot) and volumes (live feed) — plus a third, special-purpose door for the registry.

spec: containers: - name: app image: myapp:2.0 env: - name: DB_PASSWORD valueFrom: secretKeyRef: { name: db-pass, key: PASSWORD } volumeMounts: - { name: sec, mountPath: /etc/secrets, readOnly: true } volumes: - name: sec secret: { secretName: db-pass } # keys → files, kubelet-synced
💡
Prefer the volume door for sensitive data: env vars leak casually — they appear in kubectl describe, crash dumps, child processes (/proc/<pid>/environ), and some error reporters. A read-only file at a known path is easier to contain. (Hot-reload semantics from CH 03 apply identically to Secret volumes.)

🖼️ imagePullSecrets — auth for pulling images

# one-time: create the registry credential (CH 05) $ kubectl create secret docker-registry regcred … # then attach it to the ServiceAccount — every Pod in that # namespace using this SA inherits it (recommended way) $ kubectl patch serviceaccount default -p \ '{"imagePullSecrets":[{"name":"regcred"}]}' # or per-Pod in the spec: spec: imagePullSecrets: - { name: regcred }
🔑
Three doors, one rule: env = snapshot · volume = live feed · imagePullSecrets = only for the kubelet pulling images (never appears inside your container). SA-level attachment wins over per-Pod because it covers every Pod the SA runs.

CH 07

🔓 Base64 ≠ Encryption — The Truth

🟡 6 MIN · MUST-KNOW

The single most common Secrets misconception. Watch it die in one command:

$ kubectl get secret db-pass -o jsonpath='{.data.PASSWORD}' czNjcjN0               # looks safe… it is not $ echo czNjcjN0 | base64 -d s3cr3t                 # decoded by anyone, instantly
⚠️
Base64 is a transport encoding — it makes binary-ish data YAML-safe. It's a locked box made of cardboard: the point is safe shipping, not safe keeping. Anyone with get secrets permission reads every "hidden" value.

🧅 The four real layers of Secret protection

Layer 1 · Encoding base64 NOT protection — just transport Layer 2 · Encryption at rest EncryptionConfiguration on kube-apiserver (aescbc / secretbox / KMS plugin) — encrypts in etcd Layer 3 · RBAC who may get/list secrets at all ← Part III Layer 4 · Externalization External Secrets / Vault — cluster never stores the real value long-term
  • 🚫 Never commit raw manifests with real values to Git — use stringData + sealed/external secret tooling, or SOPS-style encryption
  • ✅ Check your cluster: etcd encryption-at-rest is opt-in — many dev clusters run without it
🎓
Exam tip: "Are Secrets encrypted?" — the honest answer is "encoded by default; encrypted only if etcd encryption-at-rest is configured." Questions usually probe exactly this distinction.

CH 08

🪪 RBAC — The Big Idea

🟡 6 MIN · CORE

Authentication asks "who are you?" — authorization asks "may you do that?". RBAC is Kubernetes' answer to the second question, and it's one grammatical sentence:

👤 WHO User · Group · ServiceAccount
may
🔨 VERB get · list · watch · create · update · patch · delete
on
🎯 RESOURCE pods · secrets · deployments …
in
🗂️ SCOPE namespace or cluster
The four objects
Role rules, namespaced RoleBinding attaches subjects → Role (ns) ClusterRole rules, cluster-wide ClusterRoleBinding subjects → ClusterRole (all)
Default posture

Out of the box, RBAC grants regular users nothing — no Role = no access. Even the default ServiceAccount in each namespace has zero API permissions (a hardening choice since v1.22). Every capability is granted explicitly.

$ kubectl auth can-i delete pods -n dev no  # ← your first authorization question
💡
kubectl auth can-i <verb> <resource> [-n ns] is your constant companion — and with --as=… it answers for other identities (CH 09, Lab 3). Admins live in this command.
🔑
Carry the sentence: Role = the rules · Binding = who gets them · Scope = where they apply. Everything in the next three chapters is this sentence with different nouns.

CH 09

📜 Roles & RoleBindings

🟡 6 MIN · CORE

A Role is a namespaced rulebook; a RoleBinding hands that rulebook to people. Worked example — a CI bot that may read pods and manage config, nothing else:

apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: ci-reader namespace: dev # Roles live IN a namespace rules: - apiGroups: [""] # "" = core group (pods, secrets…) resources: [pods, pods/log] verbs: [get, list, watch] - apiGroups: [""] resources: [configmaps] verbs: [get, list, create, update, patch]
kind: RoleBinding metadata: { name: ci-reader-bind, namespace: dev } roleRef: apiGroup: rbac.authorization.k8s.io kind: Role name: ci-reader # the rulebook subjects: # WHO receives it - kind: ServiceAccount name: ci-bot namespace: dev
# verify — answer FOR the bot without being the bot: $ kubectl auth can-i list pods -n dev \ --as=system:serviceaccount:dev:ci-bot yes $ kubectl auth can-i delete pods -n dev \ --as=system:serviceaccount:dev:ci-bot no  # not in the rulebook → denied
🔑
Bindings are the only on-switch. Creating a Role changes nothing by itself; access exists only when a Binding names a subject. And verbs are literal — list does not imply delete.

CH 10

🌐 ClusterRoles & When to Use Which

🟡 6 MIN · CORE

A ClusterRole is a rulebook that isn't tied to a namespace. Pairing it with the right binding type decides its reach:

PairingEffective scopeUse when…
Role + RoleBindingone namespaceteam/app permissions (the 90% case)
ClusterRole + RoleBindingone namespace per bindingreuse one rulebook in many namespaces — bind the same ClusterRole to dev, qa, prod teams separately
ClusterRole + ClusterRoleBindingentire clusterplatform admins, controllers that watch everything
Role + ClusterRoleBinding❌ impossible — a cluster-wide binding can't reference a namespaced Role
⚠️
The classic trap: some resources are cluster-scoped (Book 01 · CH 11): Nodes, PersistentVolumes, Namespaces, ClusterRoles. They cannot be governed by a namespaced Role — you must use a ClusterRole, even if you only want narrow access to, say, Nodes.
# "let the monitoring bot READ nodes" — needs ClusterRole: kind: ClusterRole metadata: { name: node-reader } # note: no namespace field rules: - apiGroups: [""] resources: [nodes] verbs: [get, list, watch]
💡
Why ClusterRole + RoleBinding is the pro move: one canonical rulebook (audited once), namespace-scoped blast radius per binding. ClusterRoleBinding is a big hammer — reserve it for identities that truly need the whole cluster.
🔑
Decision in one line: start with Role + RoleBinding; graduate to ClusterRole + RoleBinding for reuse; ClusterRoleBinding only for genuinely cluster-wide identities — and remember cluster-scoped resources force a ClusterRole.

CH 11

👷 ServiceAccounts

🟡 6 MIN · CORE

Users are for people; a ServiceAccount (SA) is an identity for workloads — the "staff badge" your Pod wears when it talks to the API Server.

  • 🏷️ Every namespace ships a default SA — Pods without an explicit serviceAccountName wear it
  • 🎫 A Pod's SA gets a projected token mounted at /var/run/secrets/kubernetes.io/serviceaccount — that's the credential the app's k8s client uses (auto-discovered in-cluster)
  • 🚫 Modern RBAC gives the default SA no permissions — a Pod that doesn't call the API should opt out:
spec: serviceAccountName: ci-bot # wear THIS badge automountServiceAccountToken: false # …or wear none

🔗 The full chain — badge → rulebook

Pod wears ServiceAccount ci-bot │ └── RoleBinding grants ci-reader Role (CH 09) │ └── result: list pods ✓ · delete pods ✗ in ns dev only
$ kubectl create serviceaccount ci-bot -n dev $ kubectl set serviceaccount deploy/web ci-bot -n dev $ kubectl auth can-i get secrets -n dev \ --as=system:serviceaccount:dev:ci-bot no  # ← this is what a stolen Pod token can do. audit it.
⚠️
The Pod-token threat model: anyone who can exec into your Pod can read its token and become that SA. Scope each SA's Role to the minimum (Lab 3 audits exactly this) — never run untrusted workloads under an admin-bound SA.
🔑
One sentence: ServiceAccount = workload identity; RoleBinding = its permissions; the mounted token = its key. RBAC + SAs together answer "what damage can this Pod do?"

CH 12

🛡️ SecurityContext

🟡 6 MIN · CORE

RBAC governs your Pod's API permissions; the SecurityContext governs its Linux permissions. Two levels apply:

LevelFieldsNotes
Pod-level spec.securityContextrunAsUser · runAsGroup · runAsNonRoot · fsGroupdefaults inherited by every container
Container-level containers[].securityContextall of the above + readOnlyRootFilesystem · allowPrivilegeEscalation · capabilities · privilegedoverrides pod-level per container
spec: securityContext: # POD level runAsNonRoot: true # refuse to start as uid 0 runAsUser: 1000 fsGroup: 2000 # group ownership for volumes containers: - name: app image: myapp:2.0 securityContext: # CONTAINER level readOnlyRootFilesystem: true # tamper-proof image FS allowPrivilegeEscalation: false capabilities: drop: ["ALL"] # shed Linux superpowers
  • 🧱 readOnlyRootFilesystem → writes must go to mounted emptyDir volumes — a common first hardening step
  • 🚫 privileged: true ≈ root on the node — never for untrusted workloads (PSS · CH 13 forbids it outright at Baseline+)
🔑
Remember the pairing: RBAC = may it call the API? · SecurityContext = what can it do to the machine? Book 01's CH 07 taint story protected the node from scheduling; this protects the node from the container.

CH 13

🚨 Pod Security Standards

🟢 5 MIN

Checking every Pod's SecurityContext by hand doesn't scale. Pod Security Standards (PSS) define three ready-made security levels, enforced cluster-wide by namespace labels.

🔓

Privileged
no restrictions — trusted, cluster-infrastructure workloads only

🔒

Baseline
blocks the obviously dangerous (hostNetwork, privileged:true) while allowing common apps

🔐

Restricted
current hardening best practice: runAsNonRoot, drop ALL capabilities, no privilege escalation

# enforce on a namespace — three modes per level: $ kubectl label ns prod \ pod-security.kubernetes.io/enforce=restricted \ pod-security.kubernetes.io/audit=restricted \ pod-security.kubernetes.io/warn=restricted
  • 🚧 enforce — rejecting non-compliant Pods · 🔍 audit — log violations · ⚠️ warn — message the user
  • 🪜 Migration pattern: run warn+audit first, fix offenders, then switch on enforce
⚠️
Version note: the old PodSecurityPolicy (PSP) was removed in Kubernetes v1.25. If a tutorial teaches PSP, it's stale — the modern mechanism is PSS via Pod Security Admission (the labels above).
🔑
One line: PSS = cluster policy, three levels (Privileged → Baseline → Restricted), applied per-namespace with enforce/audit/warn labels. "Restricted" ≈ your CH 12 SecurityContext, made mandatory.

CH 14

📊 Requests & Limits

🟡 6 MIN · CORE

REQUESTS — the promise

What the container is guaranteed. The Scheduler places Pods only on Nodes with enough requestable capacity (Book 01 · CH 06's "Pending" mystery starts here).

LIMITS — the ceiling

The maximum the runtime enforces. What happens at the ceiling differs radically by resource type — the table below is the exam's favorite nuance.

containers: - name: app image: myapp:2.0 resources: requests: { cpu: "250m", memory: "256Mi" } limits:   { cpu: "500m", memory: "512Mi" }
ResourceExceeding the limit →Feels like
CPU (compressible)Throttled — process slowed via CFS quotasluggish app, elevated latency, no restart
Memory (incompressible)OOMKilled — SIGKILL, exit code 137container dies; RestartPolicy kicks in → often CrashLoopBackOff
$ kubectl describe pod oom-demo | grep -A3 Last State    Last State:     Terminated      Reason:       OOMKilled      Exit Code:    137  # = 128 + 9 (SIGKILL)
⚠️
The overcommit trap: total requests < node capacity < total limits is legal and common — the cluster borrows headroom. When a node runs out of real memory, the kube evicts by QoS class — which is exactly CH 15.
🔑
Memory hook: CPU over limit = tickets get slower · memory over limit = you're escorted out (137). CPU can be shared; memory cannot be un-consumed.

CH 15

🎚️ QoS Classes

🟡 5 MIN · CORE

Every Pod is silently stamped with a Quality-of-Security— sorry, Quality-of-Service class, derived purely from its requests/limits. It decides who gets evicted first when a node runs dry.

Guaranteed  every container: requests == limits for both cpu AND memory Burstable   at least ONE requests/limits field set (anything else) BestEffort  no requests, no limits — anything
ClassDerivationEviction order under node pressure
Guaranteedrequests == limits (all containers)last — killed only after others
Burstablesome resources specifiedmiddle — those exceeding requests go first
BestEffortnothing specifiedfirst — zero promises, zero protection
$ kubectl get pod web -o jsonpath='{.status.qosClass}' Burstable
💡
Why this matters operationally: your database should be Guaranteed (it's the thing you least want killed); dev/experiment Pods can ride BestEffort as the cluster's shock absorber. QoS is how Kubernetes turns your YAML honesty into survival priority.
🔑
The chain, end to end: requests → where the Scheduler may place you · limits → what happens when you misbehave · QoS → who survives when the node itself starves. Part V now proves all of it hands-on.

LAB 1

🔬 ConfigMap — Prove Env ≠ Hot-Reload

🟠 12 MIN · HANDS-ON
STEP 1 · One ConfigMap, both consumption methods
$ kubectl create configmap demo --from-literal=GREETING=hello $ kubectl run cfg-demo --image=busybox --restart=Never \ --overrides='{"spec":{"containers":[{"name":"c","image":"busybox", "command":["sh","-c","sleep 9999"], "env":[{"name":"GREETING","valueFrom":{"configMapKeyRef":{"name":"demo","key":"GREETING"}}}], "volumeMounts":[{"name":"cfg","mountPath":"/etc/cfg"}]}], "volumes":[{"name":"cfg","configMap":{"name":"demo"}}]}}'
👀 TAB 1 · OBSERVE
$ kubectl exec cfg-demo -- printenv GREETING hello $ kubectl exec cfg-demo -- cat /etc/cfg/GREETING hello
⚙️ TAB 2 · CHANGE IT
$ kubectl patch cm demo -p \ '{"data":{"GREETING":"howdy"}}' configmap/demo patched
STEP 2 · Wait ~1 min, re-check
👀 ENV VAR — the snapshot
$ kubectl exec cfg-demo -- printenv GREETING hello  # ← UNCHANGED, forever
👀 VOLUME FILE — the live feed
$ kubectl exec cfg-demo -- cat /etc/cfg/GREETING howdy  # ← updated by kubelet (~1 min)

Proved: the matrix from CH 03 is real — env is a boot-time snapshot; volume mounts are kubelet-synced. Teardown: kubectl delete pod cfg-demo && kubectl delete cm demo.

LAB 2

🔐 Secret — Encoded, Not Encrypted

🟠 8 MIN · HANDS-ON
STEP 1 · Create, mount, go inside
$ kubectl create secret generic lab-sec --from-literal=PASSWORD="hunter2" $ kubectl run sec-demo --image=busybox --restart=Never \ --overrides='{"spec":{"containers":[{"name":"c","image":"busybox", "command":["sh","-c","sleep 9999"], "volumeMounts":[{"name":"s","mountPath":"/etc/sec","readOnly":true}]}], "volumes":[{"name":"s","secret":{"secretName":"lab-sec"}}]}}'
STEP 2 · Read the "hidden" value — three levels of nakedness
# inside the pod — the file is ALREADY DECODED for the app: $ kubectl exec sec-demo -- cat /etc/sec/PASSWORD hunter2 # from the API — only base64 stands in the way: $ kubectl get secret lab-sec -o jsonpath='{.data.PASSWORD}' aHVudGVyMg== $ echo aHVudGVyMg== | base64 -d  # → hunter2. instantly.

Proved: CH 07's claim — base64 protects nothing; the kubelet even hands your app the decoded value. Protection lives in who may run get secret (RBAC) and etcd encryption-at-rest. Teardown: kubectl delete pod sec-demo && kubectl delete secret lab-sec.

🔑
Interview one-liner born from this lab: "Secrets protect against casual exposure and unauthenticated reads — not against anyone holding get secrets RBAC."

LAB 3

🪪 RBAC — Can-I as a ServiceAccount

🟠 12 MIN · HANDS-ON
STEP 1 · Build the chain: SA → Role → Binding
$ kubectl create ns rbac-lab $ kubectl create serviceaccount bot -n rbac-lab $ kubectl create role podlist --verb=get,list --resource=pods -n rbac-lab $ kubectl create rolebinding bot-bind --role=podlist \ --serviceaccount=rbac-lab:bot -n rbac-lab
STEP 2 · Interrogate the bot's permissions
$ K="--as=system:serviceaccount:rbac-lab:bot -n rbac-lab" $ kubectl auth can-i list pods    $K     # in the rulebook yes $ kubectl auth can-i delete pods  $K     # verbs are literal! no $ kubectl auth can-i list secrets $K     # resources too no $ kubectl auth can-i list pods -n default $K # scope is namespaced! no
STEP 3 · What we proved
  • ✅ The bot may list pods — exactly one namespace, exactly the granted verbs
  • ❌ Delete? Secrets? Other namespaces? All no — default posture is deny; the Role's scope is absolute
  • 🔎 --as lets you audit any identity without their credentials — the core of RBAC troubleshooting

LAB 4

💥 Trigger an OOMKill on Purpose

🟠 10 MIN · HANDS-ON
STEP 1 · Deploy a Pod with a tiny memory limit and a big appetite
$ kubectl set image deploy/oom-demo oom=polinux/stress \ -n default 2>/dev/null || kubectl create deploy oom-demo --image=polinux/stress \ -- stress --vm 1 --vm-bytes 200M --timeout 300s $ kubectl set resources deploy/oom-demo --limits=memory=50Mi --requests=memory=30Mi $ kubectl get pods -w
👀 TAB 1 · WATCH
NAME             STATUS   RESTARTS oom-demo-aaaaa  Running  0 oom-demo-aaaaa  Error     1  # OOM! oom-demo-aaaaa  Running  1 oom-demo-aaaaa  Error     2  # again…
🔍 TAB 2 · AUTOPSY
$ kubectl describe pod -l app=oom-demo   Last State: Terminated     Reason:   OOMKilled     Exit:     137 # 128+9 = SIGKILL by the # kernel's OOM killer
STEP 2 · What we proved
  • ✅ Memory limit exceeded → OOMKilled (137), not throttled — CH 14's incompressible-resource rule
  • ✅ The Deployment's reconciliation (Book 01 · CH 06) restarts it → it OOMs again → the classic CrashLoopBackOff signature
  • 🩺 Real-world translation: app that crash-loops right after startup + exit 137 = raise the limit or fix the leak

Teardown: kubectl delete deploy oom-demo. (Then check its QoS: it had requests≠limits → Burstable — CH 15 in the flesh.)

GLOSS

📚 Glossary

🔵 REFERENCE
ConfigMap — namespaced key/value (or file) store for plain config; consumed as env vars or volume files.
Hot-reload — volume-mounted ConfigMaps/Secrets update automatically (~1 min, eventual); env vars and subPath mounts never do.
Secret — ConfigMap's sensitive sibling; base64-encoded values, RBAC-gated reads, same two consumption methods.
Opaque — default Secret type: arbitrary key/value pairs.
imagePullSecrets — registry credentials used by the kubelet to pull private images; best attached at ServiceAccount level.
Base64 — transport encoding, not encryption. Decodable by anyone in one command.
Encryption at rest — opt-in kube-apiserver EncryptionConfiguration that encrypts Secrets inside etcd.
Authentication vs Authorization — who are you vs may you do that. RBAC answers the second.
Role / ClusterRole — namespaced / cluster-level rulebooks: verbs on resources.
RoleBinding / ClusterRoleBinding — attach subjects to rulebooks; a RoleBinding may bind a ClusterRole but scope it to its namespace.
Subject — User, Group, or ServiceAccount named by a Binding.
ServiceAccount — workload identity; its projected token (mounted in the Pod) is the credential Pods use against the API.
SecurityContext — Linux-level hardening: runAsNonRoot, readOnlyRootFilesystem, capabilities, allowPrivilegeEscalation (pod- and container-level).
Pod Security Standards — Privileged / Baseline / Restricted levels enforced per-namespace via pod-security.kubernetes.io labels (successor to removed PSP).
Requests / Limits — guaranteed capacity for scheduling / enforced ceiling (CPU throttles; memory OOMKills with exit 137).
QoS Class — Guaranteed (req==lim) · Burstable (partial) · BestEffort (none) — determines eviction order under node pressure.

🪪 RBAC — commands
$ kubectl create role r --verb=get,list --resource=pods -n ns $ kubectl create rolebinding rb --role=r --serviceaccount=ns:sa -n ns $ kubectl create clusterrole cr --verb=get --resource=nodes $ kubectl auth can-i delete pods -n ns --as=system:serviceaccount:ns:sa $ kubectl describe role/rolebinding …  # audit what exists

🧠 Facts worth a job offer
  • ConfigMap = whiteboard, Secret = safe — same delivery, different trust · both ~1 MiB, namespaced
  • Base64 ≠ encryption — real layers: etcd encryption-at-rest + RBAC (+ external secret managers)
  • Default deny: no Role = no access; default SA has zero permissions; audit with can-i --as
  • RoleBinding may bind a ClusterRole (namespaced reach) · cluster-scoped resources force ClusterRoles
  • SecurityContext = Linux perms; PSS (Privileged/Baseline/Restricted) = namespace-enforced policy; PSP is gone (v1.25)
  • Requests → scheduling · Limits → CPU throttle / mem OOMKill · QoS → eviction order
