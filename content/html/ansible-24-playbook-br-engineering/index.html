Chapter 06 · Data Flow

VARIABLES · FACTS · REGISTERS

8 MIN
WHAT — Three sources of data

Variables parameterize desired state. Facts are auto-gathered system data. Registers capture task output for later use.

Data flows downhill to modules
Inventory→group/host vars→play/task vars→facts + registers→module / template
  • Variables: author-defined values (app_port: 8080) from inventory, group_vars/, host_vars/, play, task, or --extra-vars.
  • Facts: discovered values (ansible_os_family, ansible_default_ipv4.address) collected by ansible.builtin.setup at play start (gather_facts).
  • Registers: per-host results of a prior task (register: host_out), used by later tasks, conditionals, or templates.
WHY — One playbook, many hosts

Same playbook must behave differently per host: web-01 listens on 8080 with one certificate, web-02 on 8081 with another. Hard-coding values per host duplicates playbooks. Data flow explains *how* values travel from inventory and discovery into modules, templates, and conditionals.

WHERE DOES IT FIT — Data lane
Inventory vars → group_vars → host_vars → play vars → task vars → facts/registers → module/template/conditional

This lane sits after mechanics (PDF1): playbooks declare *what*, variables decide *with which values per target*. Logic (Ch 07) and templates (Ch 08) consume this data.

HOW IT WORKS — Precedence, facts, registers

Precedence exists because specificity must win: general defaults lose to host-specific values. Simplified order (low → high):

role defaults → group_vars/all → group_vars/web → host_vars/web-01 → play vars → task vars → extra-vars

Collision example: group_vars/all.yml sets app_port: 8080, host_vars/web-01.yml sets app_port: 9090 → web-01 renders 9090, others render 8080. ansible-playbook -e app_port=9999 overrides everything (operator intent wins for one run).

Facts: gather_facts: true (default) runs setup first, populating ansible_facts. Disable with gather_facts: false for speed when facts are unused. Registers: register stores stdout, stderr, rc, changed per host — never shared across hosts unless hostvars is read explicitly.

Chapter 07 · Logic

CONDITIONALS · LOOPS · FILTERS

7 MIN
WHAT — Branch, repeat, transform

Conditionals (when) branch tasks. Loops (loop) repeat one task over many items. Filters transform data inside Jinja2 expressions ({{ value | filter }}).

- name: Install nginx only on web ansible.builtin.package: name: nginx state: present when: inventory_hostname in groups['web'] - name: Ensure users exist ansible.builtin.user: name: "{{ item }}" state: present loop: [alice, bob]

Jinja2 filters: {{ app_port | default(8080) }}, {{ groups['web'] | length }}, {{ app_name | upper }}.

WHY — Fleets diverge

Real fleets are not uniform: web needs nginx, db needs postgres; ten users, not one. Without logic the author copies tasks per host — drift follows. when keeps one task with a guard; loop keeps one task with many items; filters keep expressions safe when data is missing.

WHERE DOES IT FIT — Logic consumes data
Variables/facts/registers (Ch 06) → when/loop/filter (this chapter) → template/handler (Ch 08)

Conditionals read facts and registers (ansible_facts.os_family == "Debian", host_out.rc == 0). Loops feed {{ item }} into modules. Filters guard undefined data (| default) so a missing var fails gracefully instead of aborting the play.

Chapter 07 · Logic (cont.)

CONDITIONALS · LOOPS · FILTERS

7 MIN
HOW IT WORKS — Evaluation per host

when is a Jinja2 expression evaluated per host, without {{ }} delimiters. loop executes the task once per item, with item and ansible_loop metadata. Filters pipe left value through right function; they chain ({{ name | lower | trim }}).

Combined example:

- name: Deploy app config per host ansible.builtin.template: src: app.conf.j2 dest: /etc/app/app.conf loop: "{{ app_instances }}" when: app_enabled | default(true)

Loop over app_instances (from group vars), skipped entirely when app_enabled is false. loop_control: label keeps output readable for long lists.

Branch per host at run time
when true

Task runs on this host → module converges → result recorded

when false

Task SKIPPED on this host → play continues → no change, no failure

FILTER FIELD GUIDE — The dozen that carry you

Filters group by job. Learn these twelve and you can read any playbook:

JobFiltersExample
Missing-safedefault, is defined{{ app_port | default(8080) }}
Branch in one lineternary{{ tls_enabled | ternary('https', 'http') }}
Typesint, bool, string, list{{ replicas | int + 1 }}
Listslength, join, map, select, unique, sort{{ groups['web'] | length }}, {{ users | map(attribute='name') | join(',') }}
Dictsdict2items, combine{% for kv in app_env | dict2items %} with kv.key / kv.value
Textupper, lower, trim, replace{{ app_name | lower | trim }}
Data formatsto_json, from_yaml, to_nice_yaml{{ cfg | to_nice_yaml }} for debug output

The safety pattern first: when: myvar is defined and myvar == "x" never explodes on missing hosts; {{ myvar | default('x') }} never aborts a template. Write every optional value one of these two ways.

Chapter 07 · Logic (cont.)

CONDITIONALS · LOOPS · FILTERS

7 MIN
LOOP VARIANTS — Beyond flat lists

Dictionaries need dict2items (a dict cannot loop directly):

- name: Export environment entries ansible.builtin.lineinfile: path: /etc/app/env line: "{{ item.key }}={{ item.value }}" loop: "{{ app_env | dict2items }}"

Long or slow loops stay readable and controllable:

- name: Pull service images ansible.builtin.command: docker pull {{ item }} loop: "{{ images }}" loop_control: label: "{{ item }}" pause: 2

Polling waits for reality instead of sleeping blindly:

- name: Wait for healthy endpoint ansible.builtin.uri: url: "http://{{ inventory_hostname }}:8080/health" register: health until: health.status == 200 retries: 30 delay: 10

until re-runs the task until the condition holds (or retries run out); combine with changed_when: false for pure checks so successful polls report OK, not CHANGED.

Chapter 08 · Files

TEMPLATES AND HANDLERS

7 MIN
WHAT — Render files, defer restarts

ansible.builtin.template renders a Jinja2 file (src: *.j2) to the managed node. Handlers run once at end of play — only if notified by a task that reported CHANGED.

Render, compare, notify once
TEMPLATE→COMPARE→CHANGED → notify→HANDLER ONCE

Five notifying tasks still restart the service exactly once, at play end.

- name: Render nginx config ansible.builtin.template: src: nginx.conf.j2 dest: /etc/nginx/nginx.conf mode: '0644' notify: Restart nginx handlers: - name: Restart nginx ansible.builtin.service: name: nginx state: restarted

Template (nginx.conf.j2):

server { listen {{ app_port | default(8080) }}; server_name {{ inventory_hostname }}; }
WHY — Config varies, restarts are expensive

Config files differ per host (port, TLS path, server name) — copy ships identical bytes, template ships per-host rendering. Restarting a service per task is noisy and can flap: five config tasks → five restarts. Handlers batch: five tasks notify, handler runs once at end, only if something actually changed.

Chapter 08 · Files (cont.)

TEMPLATES AND HANDLERS

7 MIN
WHERE DOES IT FIT — Data + logic → files + actions
Variables/facts (Ch 06) + when/loop (Ch 07) → template renders → compare → CHANGED → notify queue → handler once

copy = static bytes. template = bytes computed from data. lineinfile/blockinfile = surgical edits (prefer full template when the file is owned; prefer line edits for foreign files like /etc/sudoers.d/ fragments).

HOW IT WORKS — Compare, queue, flush

Template renders locally, compares checksum with remote dest, transfers only on difference → CHANGED or OK. notify appends handler name to per-play queue; duplicates collapse to one entry. At play end (or meta: flush_handlers mid-play), each queued handler runs once in handler order, not notify order. listen: groups multiple notify names onto one handler.

handlers: - name: Restart web stack listen: Restart nginx ansible.builtin.service: name: nginx state: restarted

validate: guards syntax before install (validate: "nginx -t -c %s"); failed validation → task FAILED, dest untouched.

TEMPLATES AND HANDLERS

7 MIN
PRACTICAL — Observe notify-on-change
COMMAND ──────────────────────── ansible-playbook -i inventory.ini site.yml

First run: TASK [Render nginx config] changed: [web-01] → RUNNING HANDLER [Restart nginx] changed: [web-01]. Second run: both ok — handler silent. Proof of deferred idempotent restart.

Why it matters: handler silence on second run is the convergence signal for config management. Common failure: handler name typo → ERROR! The requested handler 'Restart ngnix' was not found — names match exactly unless listen aliases.

Chapter 09 · Organization

ROLES AND COLLECTIONS

8 MIN
WHAT — Reusable units and their distribution

Role = reusable unit with conventional directories (tasks, handlers, templates, defaults, vars). Collection = versioned distribution of roles plus modules and plugins, addressed by fully qualified names (namespace.collection).

roles/web/ tasks/main.yml handlers/main.yml templates/nginx.conf.j2 defaults/main.yml vars/main.yml meta/main.yml

Conventional layout: tunables in defaults (lose), assertions in vars (win).

roles/web/ tasks/main.yml handlers/main.yml templates/nginx.conf.j2 defaults/main.yml vars/main.yml meta/main.yml
- name: Configure web fleet hosts: web roles: - role: web vars: { app_port: 8080 }

Install: ansible-galaxy collection install community.general. FQCN in tasks: community.general.ufw, ansible.builtin.template.

WHY — Playbooks do not scale flat

One site.yml with 200 tasks is unreviewable: variables collide, handlers duplicate, copy-paste spreads. Roles give boundaries (defaults vs vars, tasks vs handlers); collections give versioning and sharing (pin requirements.yml, upgrade deliberately). Galaxy and private automation hub become the package registry for automation.

Chapter 09 · Organization (cont.)

ROLES AND COLLECTIONS

8 MIN
WHERE DOES IT FIT — Organization after mechanics
Play → task → module (Ch 04) + data (Ch 06) + logic (Ch 07) + files (Ch 08) → role bundles them → collection ships them → ansible.cfg/CLI locates them

defaults/main.yml = lowest precedence (safe to override). vars/main.yml = high precedence (role asserts). requirements.yml pins collections per project — same discipline as requirements.txt.

HOW IT WORKS — Resolution and inclusion

Role search path: playbook roles/ dir → roles_path in ansible.cfg → Galaxy default. Task inside role resolves templates/ and files/ relative to the role. import_role is static (parsed when playbook loads — when applies per task inside). include_role is dynamic (evaluated at execution — can loop over roles).

- name: Static web role ansible.builtin.import_role: name: web - name: Dynamic per-env roles ansible.builtin.include_role: name: "{{ item }}" loop: [base, web]

Collections: ansible-galaxy collection install -r requirements.yml; reference namespace.collection.module. Short names (template, package) still resolve today but are obsolete — lint flags them, content uses FQCN throughout.

ansible.cfg loading order: ANSIBLE_CONFIG env → ./ansible.cfg → ~/.ansible.cfg → /etc/ansible/ansible.cfg. Keep project-local ansible.cfg (roles_path, inventory, forks) committed beside site.yml.
