Section 01

🎯 Objective & End State

🟢 4 MIN

The mission: automate a complete MariaDB setup on a Linux server using Ansible — so the whole process is repeatable, version-controlled, and doesn't rely on manual steps.

KEY IDEAThis isn't "install a database." It's "encode a database setup into code" — so any server, any time, run once, ends up identical. The value isn't the first run; it's the hundredth run being free.
TASK [The End State]what exists when the playbook finishes

A running MariaDB server with all four of these:

1️⃣ Custom configuration

Deployed from a known location — /opt/mariadb — charset, port, max connections, InnoDB buffer pool. Not hidden in OS default files.

2️⃣ An application database

A dedicated database (default: myapp_db) created only if it doesn't already exist.

3️⃣ A dedicated application user

(default: myapp_user@localhost) with full privileges on that database only — not the whole server.

4️⃣ Initialized schema & seed data

The database starts with its tables and initial rows from a versioned SQL script.

TASK [Why this matters]manual vs automated

❌ Manual setup

SSH in, remember the package names, edit config by hand, restart, create DB in a client, forget whether you granted the user… Every server becomes its own snowflake. Recovery = archaeology.

✅ This task

One playbook, one command. The server's entire DB setup lives in Git — reviewable, revertible, and identical on every machine it touches.

🎓 TAKEAWAYThe four end-state items are the acceptance criteria of the whole task. If verification (Section 6) can prove all four, the automation is done — regardless of how many steps it took.

Section 02

🧰 The Tools — What & Why

🟡 5 MIN

Six tools carry this task. Knowing why each one exists matters more than knowing their names.

ToolPurpose
AnsibleThe automation engine — runs all the steps idempotently (safe to re-run, changes only what needs changing).
community.mysql collectionProvides the mysql_db and mysql_user modules for database and user management.
community.general collectionSupporting modules used alongside the core set.
MariaDBThe database server itself — version 10.11.x, installed via the OS package manager.
PyMySQLThe Python library that Ansible's mysql modules need on the target host to connect and run SQL.
Jinja2 templatesUsed to render my.cnf and initdb.sql from variables — one template, many environments.
mysql client / mysqldumpManual verification, querying, and backups — the human-side tools after automation finishes.
TASK [The two most-misunderstood pieces]clarifications

🐍 Why PyMySQL on the target?

Ansible is agentless — but its mysql_db/mysql_user modules execute on the managed node and speak to MariaDB through a Python driver. No PyMySQL → the DB tasks fail with a "python mysql module not found" error, even though MariaDB itself is running fine.

📦 Why a "collection"?

community.mysql isn't shipped with Ansible core — it's a Galaxy collection that must be installed first (Section 5). Forgetting this = "couldn't resolve module" on the very first DB task.

DEBUG · The division of laborAnsible = the conductor (order and idempotency) · MariaDB = the musician (the actual server) · PyMySQL = the translator between them · Jinja2 = the copywriter (renders config per environment) · mysql client/mysqldump = the inspector after the show.
🎓 TAKEAWAYThree install-time dependencies people forget: the collections (on the control node, via requirements.yml), PyMySQL (on the target, installed by the role itself in Step 1), and MariaDB's own packages. All three are handled by the automation — that's the point.

Section 03

🌳 Project Structure — The Tree

🟡 5 MIN

Every file in the project, and what it's for. This tree is the architecture:

mariadb_project/ ├── playbook.yml # Entry point — runs the mariadb role ├── inventory.ini # Target host(s) ├── requirements.yml # Ansible Galaxy collections needed ├── group_vars/ │ └── db_servers/ │ └── vault.yml.example # Template for storing the DB password securely └── roles/ └── mariadb/ ├── defaults/main.yml # All tunable variables (db name, user, password…) ├── vars/ │ ├── Debian.yml # apt-based package/service names │ └── RedHat.yml # dnf/yum-based package/service names ├── tasks/main.yml # The 8 provisioning steps ├── handlers/main.yml # Restart handler └── templates/ ├── my.cnf.j2 # Config file template └── initdb.sql.j2 # DB init/seed script template
TASK [Reading the tree]four things to notice

🗂️ vars/ split by family

Debian.yml vs RedHat.yml — package and service names differ per distro. The role loads the right file per OS, so the same task code works everywhere.

🔐 vault.yml.example

The .example suffix is deliberate: it's a template to copy into your own (Ansible-Vault-encrypted) file. The real password never enters Git.

📄 Two Jinja2 templates

my.cnf.j2 (server config) and initdb.sql.j2 (schema + seed) — both rendered from variables, both living inside the role's templates/ folder.

🎯 defaults/main.yml

Every tunable in one place: db name, user name, password reference, ports, buffer sizes. Override from the playbook or extra-vars without touching the role.

KEY IDEAThe layout is standard Ansible role convention — which means any Ansible engineer can navigate this project without a guide. Convention is documentation that never goes stale.
🎓 TAKEAWAYEntry point = playbook.yml → calls role mariadb → which carries tasks (8 steps), handlers (restart), templates (2 files), OS-specific vars, and defaults. Everything else in the tree is plumbing for that flow.

Section 04 · Part 1 of 3

🧱 Steps 1–3 — Install · Service · Folder

🟠 7 MIN

The foundation phase: get MariaDB on the machine, running, and a home ready for its custom config.

1

Install MariaDB + PyMySQL

The role installs mariadb-server and mariadb-client (Debian) or mariadb-server/mariadb (RedHat) via the OS package manager — plus PyMySQL, so Ansible's mysql modules can connect later in Steps 6–8. The OS-specific package names come from the vars/Debian.yml / RedHat.yml split.

2

Enable and start the service

The mariadb systemd service is enabled (starts on boot) and started immediately. Both in one task — a fresh server goes from "no database" to "database accepting local connections" in a single step.

3

Create the configuration folder

A directory is created at /opt/mariadb to hold the custom config and init script — kept separate from the OS's default config locations. Everything this deployment owns lives in one known place.

After steps 1–3 — the server state
📦 mariadb-server installed + 🐍 PyMySQL installed + ⚡ service: enabled + started + 📁 /opt/mariadb/ ready
KEY IDEAStep 1's quiet hero is PyMySQL — installing it now, alongside the packages, means Steps 6–8 won't fail later with "mysql module not found." Front-loading dependencies is what makes the playbook run top-to-bottom without surprises.
WATCH OUTWhy /opt/mariadb instead of editing the OS config directly? Ownership and clarity. The OS owns /etc/mysql/...; this deployment owns /opt/mariadb. One folder to back up, inspect, or blow away — no guessing which lines in the default config were "ours."
🎓 TAKEAWAYSteps 1–3 are pure preparation: packages + service + a home directory. Nothing custom has landed yet — that's Steps 4–5. Keeping setup and configuration as separate steps is what makes failures easy to locate.

Section 04 · Part 2 of 3

📄 Steps 4–5 — Config Deploy + Restart

🟠 8 MIN

The most interesting pair of steps: render the custom files from templates, make MariaDB actually read them, and restart at exactly the right moment.

4

Deploy the config file and init script

  • 📄 my.cnf is rendered from templates/my.cnf.j2 into /opt/mariadb/my.cnf — charset, port, max connections, InnoDB buffer pool size, etc.
  • 📄 initdb.sql is rendered from templates/initdb.sql.j2 into /opt/mariadb/initdb.sql.
  • 🔗 Because MariaDB doesn't read /opt by default, the role symlinks the config into the distro's real include directory — so the settings actually take effect.
The symlink bridge — where the config goes per distro
/opt/mariadb/my.cnf the real file ── symlink ──► Debian: /etc/mysql/mariadb.conf.d/99-custom.cnf
/opt/mariadb/my.cnf ── symlink ──► RedHat: /etc/my.cn.d/

Same source file, different landing spot per OS family — the vars/ split from Section 3 decides which.

5

Restart MariaDB — via handler, flushed immediately

The config deployment notifies a handler that restarts the mariadb service — and the playbook flushes handlers immediately so the new configuration is live before the next steps run. The DB creation in Steps 6–8 must talk to a server that's already loaded the new settings.

Why the flush matters — the timing
Step 4: config changes ── notify ──► handler: restart (queued) ── meta: flush_handlers ──► ✅ new config live ──► Steps 6–8 run against it
KEY IDEATwo classic Ansible patterns working together: the handler guarantees a restart happens only when the config actually changed (idempotent runs = no pointless restarts), and the flush guarantees the restart lands before dependent steps — not at the end of the play, when it's too late.
WATCH OUTDrop the flush, and Steps 6–8 could run against MariaDB still using the old config — for example the wrong charset or buffer settings, silently. The handler fires eventually, but your DB was created under the wrong settings.
🎓 TAKEAWAYStep 4 in one line: render two templates into /opt/mariadb, then symlink my.cnf into the OS include path (Debian: mariadb.conf.d/99-custom.cnf · RedHat: /etc/my.cnf.d/). Step 5: notify restart + flush_handlers = config live exactly when needed.

⏭️ Server ready and configured — now fill it: database, user, data → Steps 6–8

Section 04 · Part 3 of 3

🐬 Steps 6–8 — DB · User · Seed

🟠 8 MIN

With MariaDB installed, configured, and freshly restarted — the actual database assets get created. All three steps use the community.mysql collection modules, all three are idempotent.

6

Create the database

community.mysql.mysql_db creates the application database — default name myapp_db — if it doesn't already exist. Second run? The database is there → status ok, untouched.

7

Create the user and grant privileges

community.mysql.mysql_user creates the application user — default myapp_user@localhost — and grants ALL PRIVILEGES on the new database only.

KEY IDEA · Scope matters"On the new database only — not on the whole server." The app can fully own its own database but cannot touch mysql.*, other databases, or server settings. Least privilege, enforced at grant time.
8

Initialize the database

community.mysql.mysql_db with state: import runs /opt/mariadb/initdb.sql against the new database — creating the starting schema/tables and seeding the initial rows. The SQL itself came from the initdb.sql.j2 template rendered back in Step 4.

Steps 6–8 — the chain
6️⃣ mysql_db create myapp_db ──► 7️⃣ mysql_user myapp_user + grants ──► 8️⃣ mysql_db state: import initdb.sql

Order is mandatory: no database → nowhere to create the user's grants · no user → the import could still work but the app couldn't connect · no import → empty schema.

PROOF · Idempotency across all threeRun the playbook again tomorrow: the DB exists (ok), the user exists with identical grants (ok), and the import behavior keeps the state consistent instead of duplicating rows blindly. The whole playbook is safe to re-run — that's the entire design goal.
WATCH OUTThe -e mariadb_db_password='…' you pass at run time (Section 5) is what Steps 7's user creation uses. Lose it or change it between runs → the task reports a change or fails to connect. The password is part of the state, not just a one-time secret.
🎓 TAKEAWAYThe final triad: 6 mysql_db create (name: myapp_db) · 7 mysql_user create + ALL PRIVILEGES scoped to that DB only · 8 mysql_db state: import from /opt/mariadb/initdb.sql. Database → user → data, in that order, every run.

Section 05

▶️ Running It — The Commands

🟠 6 MIN

Two commands from a fresh clone to a running database. First the terminal, then what every piece means:

TASK [The exact commands]from the project root
cd mariadb_project # Install required collections $ ansible-galaxy collection install -r requirements.yml # Run the playbook $ ansible-playbook -i inventory.ini playbook.yml \ --ask-become-pass \ -e mariadb_db_password='YourStrongPassword'
TASK [The inventory note]pointing at your target

inventory.ini should point at the target host — two common shapes:

💻 Local testing

localhost ansible_connection=local

Runs against the same machine — no SSH involved.

🌐 Remote server

myserver ansible_host=10.0.0.5

A real hostname/IP — uses standard SSH.

TASK [Every flag decoded]nothing is magic
-i inventory.iniwhich hosts to run against
--ask-become-passprompts for the sudo password (package installs need root)
-e var=valueextra-var — injects the DB password into the run
DEBUG · The two commands, in orderCommand 1 stocks your control node with the community.mysql and community.general collections (Section 2). Command 2 does the actual work on the target. Skip command 1 → command 2 dies on its first mysql task with "module not found."
WATCH OUTThe -e password ends up in your shell history. For anything beyond a lab, prefer the group_vars/db_servers/vault.yml route (encrypted with Ansible-Vault — see the project structure, Section 3) and drop the -e flag entirely.
🎓 TAKEAWAYThe run recipe: cd → galaxy collections → playbook with inventory + become password + DB password extra-var. Local test = ansible_connection=local; remote = real host in inventory.ini.

Section 06

✅ Verifying the Result

🟡 6 MIN

A finished playbook proves nothing — a green recap means the tasks ran, not that the outcome is correct. Five checks, each mapping to one end-state promise from Section 1:

TASK [Check 1 — the service is alive]end state: running server
$ sudo systemctl status mariadb --no-pager ● mariadb.service — MariaDB 10.11.x database server Active: active (running)
TASK [Check 2 — the custom config actually applied]end state: /opt/mariadb config live
$ sudo mysql -e "SHOW VARIABLES LIKE 'character_set_server';" +----------------------+---------+ character_set_server utf8mb4 ← proves the symlinked config loaded
TASK [Checks 3 & 4 — database and user exist]end states: DB + scoped user
$ sudo mysql -e "SHOW DATABASES;" myapp_db ← the application database is there $ sudo mysql -e "SHOW GRANTS FOR 'myapp_user'@'localhost';" GRANT ALL PRIVILEGES ON `myapp_db`.* TO … ← scoped, not server-wide
TASK [Check 5 — seeded data is present]end state: schema + rows
$ sudo mysql myapp_db -e "SELECT * FROM app_info;" …seeded rows appear… ← Step 8's import actually landed
KEY IDEAEach check targets a specific step from Section 4: status → Step 2 · charset variable → Step 4 (config live) · SHOW DATABASES → Step 6 · SHOW GRANTS → Step 7 · SELECT → Step 8. If all five pass, every layer of the automation is proven — not just "it didn't crash."
DEBUG · The cleverest checkCheck 2 is the one people skip — and the one that catches the most. MariaDB starting fine doesn't mean it read your custom config. Querying a variable you set in my.cnf.j2 is the only direct proof the symlink bridge worked.
🎓 TAKEAWAYThe verification set: systemctl status · SHOW VARIABLES · SHOW DATABASES · SHOW GRANTS · SELECT. Five commands = five end-state promises verified. Keep them in your runbook next to the playbook.

Section 07

➕ Adding New Data — Two Paths

🟡 5 MIN

There are two legitimate ways to put new data into this database — and they serve different purposes. Knowing which to reach for is the whole lesson.

TASK [Path 1 — one-off, via the mysql client]quick, manual, not reproducible
$ mysql -u myapp_user -p'YourStrongPassword' -D myapp_db \ -e "INSERT INTO app_info (key_name, value) VALUES ('app_name', 'MyApp');"

Fast for a quick test row or an ad-hoc fix. But: it lives only on this server, in this moment — a rebuilt machine won't have it.

TASK [Path 2 — permanent / repeatable, via the role]the Ansible way

Add your CREATE TABLE / INSERT statements to roles/mariadb/templates/initdb.sql.j2, then rerun the playbook — so the schema stays reproducible on any server it's deployed to:

✏️ edit initdb.sql.j2 ──► ▶ rerun playbook ──► ✅ schema reproducible everywhere
KEY IDEA · The decision ruleWill this data need to exist on the next server too? Yes → it belongs in initdb.sql.j2 (version-controlled, part of the state). No → the mysql client is fine. Everything reproducible goes in code; everything throwaway stays in the client.
WATCH OUTRemember from Step 8: the import runs against the DB at provision time. A brand-new server gets the full updated initdb.sql; an existing server only picks up changes the next time its state is reconciled — for row-level data on live servers, the client (or a migration task) is the operational path.
🎓 TAKEAWAYOne-off row/test = mysql client INSERT · permanent schema/seed = edit initdb.sql.j2 + rerun. The second path is why this whole task exists: the data setup travels with the code.

Section 08

👀 Viewing the Data — 4 Ways

🟡 5 MIN

"Where is my data?" has four different honest answers — each useful in a different situation, and one of them is a trap.

1️⃣ The seed file — plain text

$ cat /opt/mariadb/initdb.sql

The source that seeded the DB — readable, versioned, rendered from the template. Read this to see what was supposed to be created.

2️⃣ On-disk storage — the trap ⚠️

/var/lib/mysql/<db_name>/

Binary .ibd files — not human-readable; never edit these directly. This is where the data physically lives, but it belongs to MariaDB, not to you.

3️⃣ Readable full snapshot

$ sudo mysqldump myapp_db > myapp_db_backup.sql

Schema + data exported as readable SQL — the proper way to capture the complete current state (also your backup move).

4️⃣ Querying directly

$ sudo mysql myapp_db -e "SELECT * FROM <table>;"

The everyday move — ask the live server a question, get the live answer.

TASK [Choosing a viewer]which one when?
You want to…Reach for
See what the automation intended to create1️⃣ cat initdb.sql
Back up or hand off the full current state3️⃣ mysqldump
Check rows right now4️⃣ mysql -e "SELECT…"
Satisfy curiosity about storage internals2️⃣ /var/lib/mysql/ — look, never touch
WATCH OUT · EmphasizedEditing files under /var/lib/mysql/ while MariaDB is running (or ever, really) is how databases die. The server owns those bytes. Your interface to the data is always SQL — through the client, or a dump.
🎓 TAKEAWAYFour views: seed source (initdb.sql, text) · raw storage (/var/lib/mysql, binary — hands off) · full snapshot (mysqldump, readable SQL) · live query (mysql -e). Each answers "where is my data" from a different altitude.

Section 09

⚠️ Gotchas — Lessons From the Trench

🔴 real errors

Three things that actually went sideways while building this task. Each one costs minutes (or hours) the first time — reading them here costs you seconds.

GOTCHA 1 · Two interpreters, one promptThe mysql client and the bash shell are two different command interpreters. SQL pasted into bash — or shell commands pasted into an open mysql session — produces confusing, unrelated errors. Always check the prompt before typing:

💵 $ means bash

Shell commands live here: sudo systemctl…, cat, mysql -e "…". SQL typed here = syntax error nonsense.

🐬 MariaDB [db]> means mysql

SQL lives here: SELECT…, SHOW…. Shell commands typed here = ERROR 1064 nonsense.

GOTCHA 2 · Multi-line SQLMulti-line SQL is safest saved to a .sql file and piped in (mysql … < file.sql) rather than pasted interactively. Pasting long statements into the client invites partial-line errors, lost semicolons, and copy bugs — the file is repeatable, the paste is a gamble.
GOTCHA 3 · bind-address = 127.0.0.1The deployed config sets bind-address = 127.0.0.1 — the server only accepts local connections. This is intentional for a dev/local setup: the database simply isn't reachable from other machines. If remote access is ever needed, change the bind address and open the firewall — both, or it still won't answer.
Remote access checklist — only when needed
1️⃣ change bind-address + 2️⃣ open the firewall + 3️⃣ user host ≠ localhost ──► reachable

Note the 3️⃣: the default grant is myapp_user@localhost — a remote client needs a matching user/host too.

KEY IDEAAll three gotchas share one root: the error appears far from its cause. Wrong interpreter, wrong input channel, wrong bind address — each one looks like a totally different problem than it is. Slow down, check the prompt, check the file, check the config.
🎓 TAKEAWAYThe trench notes: 1. prompt tells you the language ($ = bash, MariaDB [>] = SQL) · 2. pipe multi-line SQL from a file · 3. bind-address 127.0.0.1 = local-only by design; remote needs config + firewall + user host.
