CH 01

🕳️ Why Storage Is Different

🟢 4 MIN

Everything so far assumed Pods are expendable — and their filesystem is too. A container's writable layer is built fresh from the image every time the container is replaced. Data written "inside the container" has a death wish.

The three lives of data — how long does it survive?
1 · Container writable layer dies with the CONTAINER crash → kubelet restarts → fresh layer → your writes GONE 2 · emptyDir volume dies with the POD survives container restarts — deleted when the Pod leaves the node 3 · PersistentVolumes outlives EVERYTHING pods, nodes, even the cluster's opinion — data remains
❌ Fine without persistence
  • Stateless APIs (state lives in a DB elsewhere)
  • Static sites, proxies, workers
  • Scratch space, temp files (emptyDir!)
💀 Dies without persistence
  • Databases (MySQL, Postgres — Book 01's YAML wrote nothing durable!)
  • User uploads, sessions
  • Message queues, ML models, indexes
💡
Book 04 foreshadowed this: drain --delete-emptydir-data exists precisely because emptyDir data dies with the Pod — drain makes you admit it. And Book 01's MySQL lab ran on the container layer: that database was one crash away from amnesia.
🔑
One sentence: Kubernetes treats Pods as cattle — so anything that must outlive a Pod needs to live outside the container layer, declared as a Volume at minimum and a PersistentVolume at best. This book is the ladder from scratch space to real persistence.

CH 02

🎒 Volumes — The Pod's Attachments

🟡 6 MIN · CORE

A Volume is a directory, declared at Pod level, mounted into containers. It outlives the containers in the Pod — but its lifespan depends on its type.

spec: containers: - name: app image: myapp:2.0 volumeMounts: - { name: scratch, mountPath: /tmp/cache } volumes: # declared at POD level — shared by containers - name: scratch emptyDir: {}
TypeBackingLifespanUse for
emptyDirnode disk / RAM (medium: Memory)Pod's lifescratch, multi-container share, checkpointing
hostPatha path on the nodesurvives the Pod — tied to the node⚠️ node agents, privileged daemons only
configMap / secretAPI objects (Book 02 · CH 02/06)Pod's life, kubelet-syncedconfig & credentials as files
nfsan NFS shareindependent of Podshared file storage
persistentVolumeClaima PV via bindingindependent — the star ⭐real persistence (Part II)
csiany CSI driver (CH 11)driver-definedephemeral CSI volumes
⚠️
hostPath is a loaded weapon: it hard-couples your Pod to a specific path on whatever node it lands on — rescheduling to another node = "where did my data go?" It can also read any path on the node (including /) — a container-escape classic. Legit uses: kubelet-adjacent daemons (log shippers, CNI). Everything else: use a PVC.
  • 🤝 Shared fate, shared files: two containers in one Pod mounting the same Volume = the Book 01 · CH 19 sidecar pattern's backbone (the log-shipper read the app's file from one)
  • 📏 emptyDir.sizeLimit caps growth — beyond it, eviction (kubelet treats it like disk pressure)
🔑
One sentence: a Volume is a Pod-scoped directory whose backing (and lifespan) is chosen by its type — from RAM-speed scratch (emptyDir) to node-coupled files (hostPath) to the fully independent PVC, which is where the rest of this book lives.

CH 03

🤝 PV & PVC — Supply Meets Demand

🟡 6 MIN · CORE

The genius of Kubernetes storage is a divorce of concerns: the people who provision storage (ops, storage admins) and the people who consume it (developers) never talk to each other. They meet through two objects.

📦 PersistentVolume — the SUPPLY
apiVersion: v1 kind: PersistentVolume metadata: { name: pv-warehouse-1 } spec: capacity: storage: 5Gi accessModes: [ReadWriteOnce] persistentVolumeReclaimPolicy: Retain hostPath: { path: /data/pv1 }

Cluster-scoped (Book 01 · CH 11 promised!). Real storage: NFS, cloud disk, hostPath. No namespace, owned by admins.

📝 PersistentVolumeClaim — the DEMAND
apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: db-data, namespace: shop } spec: resources: requests: storage: 3Gi accessModes: [ReadWriteOnce] storageClassName: "" # "" = manual binding only (CH 07)

Namespaced. Not storage — a wish: "I need 3Gi, RWO." The developer's entire vocabulary of storage.

The meeting — binding turns two wishes into a contract
👷 Opsprovisions PVs
──►
📦 PVcluster supply
⇄
📝 PVCns: shop
◄──
👩‍💻 Devwrites a claim

PVC bound → Pods mount the claim, never the volume: volumes: [{name: data, persistentVolumeClaim: {claimName: db-data}}]

💡
The apartment analogy, upgraded: the PV is the warehouse in the building's basement (building-wide, managed by the landlord). The PVC is your lease application ("3Gi storage, I need to write to it"). You never touch the warehouse — you mount your lease.
🔑
One sentence: PV = cluster-scoped real storage (supply) · PVC = namespaced request (demand) · binding = the matchmaking — and Pods only ever reference the PVC, keeping consumers and infrastructure permanently decoupled.

CH 04

🔗 The Binding Process

🟡 6 MIN · CORE

A controller (the PV controller, inside kube-controller-manager) continuously matches Pending claims to Available volumes. Four checks, all must pass:

The matcher's four questions
1 · Capacity PV ≥ request?
2 · Access modes PV ⊇ requested?
3 · storageClassName exact match?
4 · selector labels match?

smallest PV that fits wins · binding is 1:1 — a bound PV is spoken for

CheckRuleGotcha
CapacityPV's storage ≥ PVC's requestyou get the whole PV, not a slice — a 3Gi claim on a 5Gi PV wastes 2Gi
Access modesPV offers at least what the claim asksclaim [RWO] can bind a PV offering [RWO, RWX]
StorageClassexact string match — including ""claim with className: "" binds only PVs also stamped ""; a claim with no field uses the default class (CH 07)
Selectorclaim's selector.matchLabels ⊆ PV labelsops tags PVs (tier: gold), devs target the tag
$ kubectl get pvc db-data NAME     STATUS   VOLUME         CAPACITY  ACCESS MODES db-data  Pending                    # nobody fits — check the 4 questions db-data  Bound    pv-warehouse-1  5Gi       RWO
  • 🎯 Pre-binding: a PV can name its soulmate in spec.claimRef — skips the matchmaking entirely (migrations, DR drills)
  • 🔒 Binding is exclusive: one PV ↔ one PVC, period. Sharing storage between Pods happens through the same claim, not through multiple bindings
⚠️
Pending PVC triage: 90% of stuck claims are the storageClassName mismatch — claim says "" but only classed PVs exist, or vice versa. The other 10%: capacity too small, access-mode subset missing, or selector pointing at labels nobody has.
🔑
One sentence: binding = capacity ≥, modes ⊇, class ==, labels match — smallest fitting PV wins, exactly one claim per PV. Every Pending PVC is one of those four questions answered wrong.

CH 05

🔀 Access Modes — RWO·ROX·RWX Decoded

🟡 6 MIN · CORE

The names are honest about read/write but lying about the unit. The unit is NODES, not Pods — and that one fact explains half of all storage tickets.

ModeName saysReally meansTypical backing
ReadWriteOnceone writerread-write mounted by ONE NODEcloud block disks: EBS, PD, Azure Disk
ReadOnlyManymany readersread-only on MANY nodesNFS, EFS (ro), pre-staged datasets
ReadWriteManyshared writeread-write on MANY nodesNFS, EFS, Azure Files, CephFS
ReadWriteOncePod newerone writerread-write by ONE POD — truly exclusive (GA 1.29)block disks, with the strictest semantics
⚠️
The interview trap: RWO ≠ one Pod. It's one node — so three Pods on the same node can all mount one RWO volume simultaneously, while the same three Pods spread across three nodes cannot. When your scaled Deployment mysteriously wedges, this is why: replicas scattered across nodes fight over one RWO claim.
Multi-Attach — the classic failure
$ kubectl describe pod db-2 | tail -2   Events:   Multi-Attach error for volume "pvc-abc":   Volume is already exclusively attached to one node   and can't be attached to another # Pod B (other node) wants the RWO volume Pod A's node holds. # The volume driver physically can't attach a block disk twice.
  • 🧱 Block storage = RWO-only: a cloud disk plugs into one machine — RWX demands a shared filesystem (NFS/EFS/Ceph) or an in-cluster one (NFS provisioner, Longhorn, EFS CSI)
  • 🔍 Check reality, not hopes: kubectl get pv shows the PV's ACCESS MODES — a claim asking RWX will sit Pending forever against an RWO-only fleet
🔑
One sentence: access modes are promises about node-level attach — RWO = one node (not one Pod!), RWX = needs genuinely shared backing — and Multi-Attach error in events is the sound of a block disk refusing to be in two places at once.

CH 06

♻️ Reclaim Policies & the PV Lifecycle

🟡 6 MIN · CORE

A PV has a whole life after its claim dies. The reclaim policy decides what that afterlife looks like — and whether your data survives it.

Available → Bound → PVC deleted → Released → policy decides → │ │ Retain: stays Released forever — data intact, ADMIN must intervene Delete: PV object + backing storage both destroyed ← dynamic default Recycle: scrub & re-offer — REMOVED from the API (dynamic provisioning replaced it)
PolicyPVC deleted →DataUse when
RetainPV → Released, never auto-reusedkept — hostage until an admin actsdatabases, anything you'd cry over
DeletePV + cloud disk annihilatedgonetruly ephemeral state, CI scratch
# the Released hostage situation — and the escape: $ kubectl get pv NAME    CAPACITY  CLAIM             RECLAIM  STATUS pv-db   5Gi       shop/db-data     Retain   Released # reuse it manually: clear the claimRef → back to Available # (data intact! next binding re-attaches the same disk) $ kubectl patch pv pv-db -p '{"spec":{"claimRef": null}}'
⚠️
Two honest warnings: (1) the pvc-protection finalizer — a PVC in use by a Pod shows Terminating indefinitely; Kubernetes refuses to yank storage from a running Pod. (2) Default is Delete for dynamic volumes — an innocent kubectl delete pvc on a Delete-class volume is a production data-loss event. Patch the PV (or the class, CH 08) to Retain for anything real.
  • 🔁 Released ≠ Available: Released PVs are NOT re-matchable — that's the point of Retain (no accidental rebinding of dirty state)
  • 🧾 Audit trick: kubectl get pv -o custom-columns=NAME:.metadata.name,POLICY:.spec.persistentVolumeReclaimPolicy,STATUS:.status.phase — one glance, whole estate
🔑
One sentence: the PV lifecycle is Available → Bound → Released → {Retain: wait for admin | Delete: erase everything} — and the difference between "I deleted a claim" and "I deleted the company's data" is one policy field.

CH 07

🏭 StorageClasses — Build on Demand

🟡 6 MIN · CORE

Writing PVs by hand doesn't scale — it's the landlord hand-building a warehouse per lease. A StorageClass is the construction company: PVCs name it, and it builds the warehouse automatically.

apiVersion: storage.k8s.io/v1 kind: StorageClass metadata: name: fast annotations: storageclass.kubernetes.io/is-default-class: "true" # THE default provisioner: ebs.csi.aws.com # WHO builds (CSI driver — CH 11) parameters: # the build spec, vendor-specific type: gp3 encrypted: "true" reclaimPolicy: Delete # default for dynamic volumes allowVolumeExpansion: true # grow later (CH 08) volumeBindingMode: WaitForFirstConsumer # smart timing (CH 08)
Dynamic provisioning — the whole dance, automated
📝 PVCclassName: fast
──►
🏭 SC"fast"
──►
🔌 ProvisionerCSI driver
▼ builds real storage (EBS volume etc.)
📦 PV auto-createdcap · modes · policy
──►
📝 PVCBound ✓
──►
🫛 Pod mounts it

zero PVs hand-written · the SC name in the claim is the only thing a developer must know

PVC's storageClassNameResult
names a class (fast)dynamic provisioning from that class — manual PVs of the same name are bypassed unless matching perfectly
field omitted + a default class existsuses the default class — standard on minikube/kind
field omitted + no defaultold-school manual binding only — usually Pending forever
"" (empty string)explicitly opts OUT of dynamic — manual PVs only (CH 04's matcher)
💡
Classes are also a menu: fast (NVMe), cheap (HDD), shared (NFS/RWX) — the same cluster offers different storage tiers, and the developer picks by writing one name. Multi-cloud? One class per backend, one field per claim.

CH 08

⚙️ Class Tuning — Binding Modes & Expansion

🟡 6 MIN · CORE

⏱️ volumeBindingMode — WHEN to bind

Immediate (default)

Bind the instant the PVC exists — before any Pod exists. Simple, but with zoned storage the disk may be born in zone A while your Pod later schedules to zone C → attach impossible → Pod wedged.

0/1 nodes available: volume node affinity conflict # ← this error = bound to the wrong zone
WaitForFirstConsumer ✅

The PVC waits in Pending until a Pod that uses it is scheduled — then provisions the disk in the Pod's zone. Topology-correct by construction. Production default for zoned clouds.

# PVC waits… pod schedules to zone-c… # disk born IN zone-c — attach just works

📈 allowVolumeExpansion — grow, never shrink

# class must allow it (CH 07)… then just edit the claim: $ kubectl patch pvc db-data -p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}' $ kubectl get pvc db-data NAME     CAPACITY  STATUS db-data  10Gi      Bound  # filesystem resized online (most drivers) # SHRINKING IS IMPOSSIBLE — storage can only ever grow. plan headroom.
SettingRecommendedWhy
volumeBindingModeWaitForFirstConsumer (zoned clouds)disk and Pod land in the same zone, always
allowVolumeExpansiontrueDBs outgrow their bids; growing online beats migrating
reclaimPolicyRetain for real data classesCH 06: default Delete is a loaded foot-gun
parametersvendor-specific (type: gp3…)the tier definition itself
💡
Debugging zoned wedges: the PV inherits the zone as a nodeAffinity (kubectl describe pv → Node Affinity section) — the Scheduler literally cannot place Pods elsewhere. Wrong-zone = delete PVC + Pod, recreate with WaitForFirstConsumer. (Topologies from Book 04 · CH 08 pay off here.)
🔑
One sentence: production classes set WaitForFirstConsumer (zone-correct disks), allowVolumeExpansion: true (grow-only flexibility), and Retain for anything with a pulse — Immediate binding on zoned storage is how disks get born in the wrong ZIP code.

CH 09

🪪 StatefulSets — Why Identity Matters

🟡 6 MIN · CORE

A Deployment's Pods are interchangeable cattle — random names, any replica can serve any request. Databases are not cattle: replica 0 is the primary, replica 1 is its follower, and each owns its own data. Enter the StatefulSet.

🐄 Deployment identity
web-7d9f-x7k2p random web-7d9f-bbbba random die → replaced by NEW random names any pod can serve anything no "which one owns the data?"
🐕 StatefulSet identity
db-0 PRIMARY — born first db-1 follower — waits for 0 db-2 follower — waits for 1 die → RESURRECTED WITH THE SAME NAME + same storage (CH 10) + same DNS

📮 The headless service — per-Pod DNS

apiVersion: v1 kind: Service metadata: { name: db } spec: clusterIP: None # HEADLESS — no VIP, no balancing selector: { app: db } ports: [{ port: 5432 }] # instead of one VIP, DNS returns EACH POD's address: # db-0.db.shop.svc.cluster.local → db-0's IP (the primary!) # followers find the primary BY NAME — no IPs in any config
  • 🔢 Ordered by default: 0 → Ready → then 1 → Ready → then 2; deletion runs in reverse (2 → 1 → 0). The bootstrap sequence a database needs, built in
  • 🏷️ Name = contract: replication configs say "follow db-0" — and it's true forever, across rescheduling and crashes
💡
Scope note: this chapter covers identity + storage — the reason StatefulSets exist for data. The full lifecycle (rolling updates, partition canaries, OnDelete) is Book 06's territory.
🔑
One sentence: StatefulSets give each replica a stable name, stable DNS, and ordered startup — the preconditions for "replica 0 owns the data" to mean anything; next chapter attaches the storage that makes the promise complete.

CH 10

🗄️ volumeClaimTemplates — Storage Per Replica

🟡 6 MIN · CORE

The StatefulSet's killer storage feature: instead of one shared claim, you embed a template — and each replica gets its own PVC stamped from it, named after the Pod it belongs to.

apiVersion: apps/v1 kind: StatefulSet metadata: { name: db } spec: serviceName: db # the headless service (CH 09) replicas: 3 selector: { matchLabels: { app: db } } template: # the pod stamp metadata: { labels: { app: db } } spec: containers: - name: db image: postgres:16 volumeMounts: - { name: data, mountPath: /var/lib/postgresql/data } volumeClaimTemplates: # ★ THE COOKIE CUTTER FOR CLAIMS - metadata: { name: data } spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 10Gi } } storageClassName: fast
StatefulSet db (replicas: 3) ├── pod db-0 ⇄ PVC data-db-0 ⇄ PV (own disk) ├── pod db-1 ⇄ PVC data-db-1 ⇄ PV (own disk) └── pod db-2 ⇄ PVC data-db-2 ⇄ PV (own disk) naming law: <template-name>-<statefulset>-<ordinal>
✅ Scale UP → claims born

3 → 4 replicas: data-db-3 dynamically provisioned (CH 07!), mounted by db-3. Fresh disk, zero setup.

⚠️ Scale DOWN → claims RETAINED

4 → 2: Pods db-3, db-2 die — but their PVCs stay (data-safety by design). Scale back up and the same replicas reunite with their old disks.

⚠️
Deleting the StatefulSet deletes NOTHING storage-wise — every data-db-N survives (Retain-like behavior, baked in). Cleanup is manual: kubectl delete pvc data-db-0 data-db-1 … This is the storage counterpart of Book 01's cascade lesson — some deletes cascade (namespaces), some deliberately don't (STS claims).
🔑
One sentence: volumeClaimTemplates = one PVC per replica, named for its Pod, born on scale-up, kept on scale-down — the mechanism that lets db-0 mean "the primary and its exact disk" forever.

CH 11

🔌 CSI — The Universal Plug

🟡 5 MIN

Every provisioner you've met (ebs.csi.aws.com, minikube's hostpath, Ceph…) speaks CSI — the Container Storage Interface: a vendor-neutral gRPC contract that lets any storage backend plug into any Kubernetes.

🏺 Before CSI (in-tree era)
  • Driver code lived inside the k8s source tree
  • Vendors begged SIGs for inclusion; releases tied to k8s cycles
  • k8s shipped hundreds of drivers it couldn't all test
🔌 After CSI
  • Drivers are containers you install (Helm charts)
  • Vendors release on their schedule, any k8s version
  • In-tree drivers: frozen & deprecated — CSI is the only growth path
Pod ⇄ PVC ⇄ StorageClass.provisioner = "ebs.csi.aws.com" │ ▼ CSI driver — two halves, both just Pods: ├── Controller plugin (Deployment) — CreateVolume, DeleteVolume, Expand └── Node plugin (DaemonSet — one per node, Book 04 CH 10 skips these!) └── NodeStageVolume / NodePublishVolume → the disk appears at the mountPath
  • 🔐 Credentials, of course, are Secrets (Book 02 · CH 05–06): the driver's chart consumes a Secret holding cloud API keys / backend tokens
  • 🧩 volumeMode: Filesystem (default — a formatted dir) vs Block (raw device handed to the Pod — databases that manage their own formatting love it)
  • 🌍 Examples in the wild: ebs.csi.aws.com · pd.csi.storage.gke.io · disk.csi.azure.com · rbd.csi.ceph.com · driver.longhorn.io
💡
Reading a class like a pro: the provisioner field is a CSI driver identity. If a class says kubernetes.io/aws-ebs (old in-tree name) on a modern cluster — that's a legacy class on migration watch.
🔑
One sentence: CSI is the USB standard of storage — a stable plug spec that turned storage drivers from kernel-adjacent k8s features into ordinary installable containers, which is why every class you'll ever write ends in a …csi… provisioner.

LAB 1

🔬 Manual PV ↔ PVC Binding

🟠 12 MIN · HANDS-ON
STEP 1 · Provision supply by hand
$ kubectl apply -f - <<EOF apiVersion: v1 kind: PersistentVolume metadata: { name: pv-manual-1, labels: { tier: lab } } spec: capacity: { storage: 1Gi } accessModes: [ReadWriteOnce] persistentVolumeReclaimPolicy: Retain storageClassName: "" hostPath: { path: /data/pv-manual-1, type: DirectoryOrCreate } EOF $ kubectl get pv pv-manual-1  # STATUS: Available (2 of the 4 checks pre-passed)
STEP 2 · Demand + consume
$ kubectl apply -f - <<EOF apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: lab-claim } spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 500Mi } } storageClassName: "" # match the PV's "" — CH 04 rule 3 selector: { matchLabels: { tier: lab } } EOF $ kubectl get pvc lab-claim   # Bound → pv-manual-1 (smallest fitting PV) $ kubectl run writer --image=busybox:1.36 --restart=Never --rm -it \   --overrides='{"spec":{"containers":[{"name":"w","image":"busybox:1.36", "command":["sh","-c","echo persistent rocks > /data/hello.txt; sleep 5"], "volumeMounts":[{"name":"d","mountPath":"/data"}]}], "volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"lab-claim"}}]}}'
👀 PROVE IT'S THE WAREHOUSE
$ minikube ssh "cat /data/pv-manual-1/hello.txt" persistent rocks # the file lives on the NODE's disk, # inside the PV's hostPath — # not in any container
🔍 THE 4 CHECKS, VERIFIED
capacity: 1Gi ≥ 500Mi ✓ modes: RWO ⊇ RWO ✓ class: "" == "" ✓ selector: tier=lab ✓ → smallest-fitting win, 1:1 bound

Teardown: kubectl delete pvc lab-claim → PV goes Released (Retain! CH 06) → kubectl delete pv pv-manual-1.

🏭 Dynamic Provisioning + Reclaim Proof

🟠 10 MIN · HANDS-ON
STEP 1 · Zero PVs — just a claim
$ kubectl get storageclass NAME       PROVISIONER              RECLAIMPOLICY  BINDINGMODE standard  k8s.io/minikube-hostpath Delete        Immediate  # default ✓ $ kubectl apply -f - <<EOF apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: dyn-claim } # no className → default class (CH 07) spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 1Gi } } EOF $ kubectl get pvc dyn-claim  # Bound — and NOBODY wrote a PV: $ kubectl get pv | grep dyn-claim  # pvc-xxxx… auto-created by the provisioner!

🔑

LAB 3

🔬 StatefulSet — Identity & Per-Replica Data

GLOSS

📚 Glossary

🔵 REFERENCE
Volume — a Pod-level directory mounted into containers; lifespan set by its type (emptyDir, hostPath, configMap, PVC…).
emptyDir — scratch volume sharing the Pod's life; survives container restarts, dies with the Pod; optional sizeLimit.
hostPath — node-local path; couples Pods to nodes and can expose the whole filesystem — daemon-only territory.
PersistentVolume (PV) — cluster-scoped piece of real storage with capacity, accessModes, reclaimPolicy; the supply.
PersistentVolumeClaim (PVC) — namespaced request (capacity + modes + class + selector); the only thing Pods mount.
Binding — 1:1 PV↔PVC match: capacity ≥, modes ⊇, class ==, selector match; smallest fitting PV wins.
Access modes — RWO (one NODE!), ROX, RWX (many nodes, shared filesystem), RWOP (one Pod, GA 1.29).
Multi-Attach error — a block volume refusing simultaneous attach to two nodes; the RWO-wedge signature.
PV phases — Available → Bound → Released (Retain holds here) → Failed; Released never auto-rebinds.
Reclaim policy — Retain (keep data, admin intervenes) / Delete (PV + backing storage destroyed; dynamic default) / Recycle (removed).
pvc-protection finalizer — keeps a PVC Terminating while a Pod still uses it.
StorageClass — named provisioning recipe: provisioner + parameters + reclaimPolicy + bindingMode + expansion flag.
Dynamic provisioning — claim names a class → provisioner builds storage + PV automatically; default class serves omitted fields; "" opts out.
volumeBindingMode — Immediate (bind now) vs WaitForFirstConsumer (bind when a Pod schedules — zone-correct).
allowVolumeExpansion — permits PVC growth (never shrink); filesystem resize online.
StatefulSet — workload controller giving replicas stable names (web-0…), per-Pod DNS via a headless Service, and ordered lifecycle.
Headless Service — clusterIP: None; DNS resolves each Pod individually — how followers find the primary by name.
volumeClaimTemplates — per-replica claim cookie-cutter: data-<sts>-<ordinal>; born on scale-up, retained on scale-down and on STS deletion.
CSI — Container Storage Interface: standard gRPC contract; drivers ship as controller (Deployment) + node (DaemonSet) plugins, out-of-tree.
volumeMode — Filesystem (formatted dir, default) vs Block (raw device passed to the Pod).

🧠 Facts worth a job offer
  • Three lives of data: container layer (dies with container) → emptyDir (dies with Pod) → PV (outlives everything)
  • PV = cluster-scoped supply · PVC = namespaced demand · Pods mount the claim, never the volume
  • RWO = one NODE, not one Pod — same-node Pods share it; RWX needs shared backing (NFS/EFS/Ceph)
  • Retain keeps Released data hostage; Delete (dynamic default) erases PV + disk — patch before you delete
  • WaitForFirstConsumer = disks born in the Pod's zone; storage grows but never shrinks
  • StatefulSet claims: one per replica, named after the Pod, kept on scale-down and STS deletion
  • CSI = the universal plug: drivers are containers (Deployment + DaemonSet), out-of-tree, independent releases
