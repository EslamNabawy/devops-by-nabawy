👁️ What is Observability? — الركائز الأربع

🟢 5 MIN

Observability هي القدرة على فهم ما يحدث داخل النظام من خلال فحص البيانات التي يُنتجها — دون الحاجة إلى نشر Code جديد لطرح سؤال جديد. تعتمد على أربع ركائز أساسية:

TASK [الركائز الأربع]والسؤال الذي تجيبه كل ركن
📜
Logs
"What happened, and what did it say?"

سجلات منفصلة مختومة بالـ Timestamp لكل حدث — الخطأ، التحذير، رسالة التشغيل.

📈
Metrics
"How much, how fast, how often?"

قياسات رقمية عبر الزمن — CPU، الـ Requests في الثانية، زمن الاستجابة.

🔗
Traces
"Where did the time go?"

المسار الكامل لـ Request واحد وهو ينتقل عبر الخدمات المختلفة.

📊
Visualization
"Can a human act on this?"

يحوّل الإشارات الخام إلى Dashboards يمكن للإنسان قراءتها والتصرف بناءً عليها.

الركائز الثلاث الأولى تنتج وتخزّن الإشارات — والرابعة تجعلها قابلة للفهم والفعل.

KEY IDEAالركائز لا تكرر بعضها — كل واحدة تجيب نوعًا مختلفًا من الأسئلة: الـ Log يخبرك ماذا حدث بالتفصيل، والـ Metric يخبرك بكم وبأي سرعة، والـ Trace يخبرك أين ذهب الوقت. التحقيق الكامل يستخدم الثلاثة معًا.
NOTE · لماذا التعريف مهم؟لاحظ العبارة المفتاحية: «بدون نشر Code جديد لطرح سؤال جديد». تجهّز النظام مرة واحدة؛ وبعدها أي سؤال جديد («لماذا كان الـ Latency عاليًا الساعة 2 فجرًا؟»، «أي Pod رمى الخطأ؟») يُجاب بالاستعلام عن بيانات موجودة أصلًا — لا بإعادة نشر مع print statements إضافية. نظام المراقبة الجيد يجيب على أسئلة لم تتوقعها وقت البناء — عكس الـ Monitoring التقليدي الذي يجيب فقط على أسئلة مكتوبة مسبقًا.
🎓 EXAMسؤال الافتتاح في أي Interview: «ما الـ Observability وركائزها؟» ← فهم حالة النظام من بياناته دون نشر Code جديد · الركائز: Logs · Metrics · Traces · Visualization — مع السؤال الذي تجيبه كل ركن.

📜 Why Loki? — الفلسفة والفروق

🟡 6 MIN

Loki هو نظام تجميع Logs أفقي التوسّع (Horizontally-Scalable) يدعم Multi-Tenancy، مبني من Grafana Labs. يتميّز عن أنظمة النص الكامل مثل ELK لأربعة أسباب جوهرية:

💰 Cost-Effective — الأرخص

أرخص 10–20× في التخزين، لأنه يفهرس الـ Metadata فقط (Labels) — لا النص الكامل لكل سطر Log. فهرسة خفيفة = فاتورة تخزين خفيفة.

🗄️ Storage — تخزين رخيص

الـ Logs تُضغط إلى Chunks وتُخزَّن في Object Storage رخيص (أو Filesystem محلي في الـ Labs) — بلا Search Nodes ضخمة.

🔍 Querying — LogQL

تستعلم Loki بـ LogQL — لغة مصممة عمدًا لتكون شبيهة بـ PromQL. تعلّم واحدة والثانية تبدو مألوفة.

🔗 Integration — تكامل أصلي

تكامل أصلي مع Grafana (بلا واجهة منفصلة)، ويستخدم نفس الـ Label Model الخاص بـ Kubernetes وPrometheus بالضبط.

TASK [Loki vs ELK — الفرق في سطر واحد]المقايضة
ELK: يفهرس النص الكامل ← بحث نصي قوي 💪 ⇄ Loki: يفهرس الـ Labels فقط ← أرخص 10–20× 💰
KEY IDEA · النموذج الذهني + الفلسفةفكّر في Loki كـ «Prometheus للـ Logs». والفلسفة في سطر: «لا تفهرس ما لا تستعلم عنه». فهرسة الـ Metadata (أي Namespace؟ أي Pod؟ أي Container؟) تكفي لتصفية ملايين الأسطر، وترك النص خامًا يُقرأ عند الاستعلام فقط — هذا هو الجذر المشترك لرخصته وسلوك استعلاماته: محددات الـ Labels سريعة، وفلترة الأسطر تُدار لحظة الاستعلام.
WATCH OUTالمقايضة حقيقية: لأن Loki لا يفهرس نص الـ Log نفسه، البحث النصي الحر أضعف من ELK. أنت تستعلم بالـ Labels أولًا ثم تضيّق بالـ LogQL. في بيئات Kubernetes ذات الـ Labels الجيدة — وهذه حالتنا بالضبط — المقايضة مجدية جدًا.
🎓 EXAMالأسباب الأربعة: Cost (أرخص 10–20× — فهرسة Labels فقط) · Storage (Chunks في Object Storage رخيص) · LogQL (شبيه بـ PromQL) · تكامل Grafana أصلي + نفس الـ Label Model. النموذج الذهني: «Prometheus للـ Logs» · الفلسفة: «لا تفهرس ما لا تستعلم عنه».

🏗️ Loki Architecture — مسار الكتابة والقراءة

🟡 6 MIN

3-Aالـ Pipeline بمراحله الخمس

الـ Logs تعبر معمارية Loki عبر مسار محدد — الكتابة تنزل عبر الـ Pipeline، والقراءة تعود من الـ Store:

1️⃣ Promtailيشحن من الـ Nodes
──►
2️⃣ Distributorيحقّق وي عمل Hash للـ Streams
──►
3️⃣ Ingesterيدفعها دفعات Chunks ويكتبها
▼
4️⃣ StoreChunks + Index (Object Storage / Disk)
◄──
5️⃣ Querierينفّذ LogQL القادم من Grafana

الكتابة: ملفات Container Logs ← Promtail ← Distributor ← Ingester ← Store  ·  القراءة: Grafana —LogQL→ Querier ← يقرأ Chunks + Index من Store/Ingester

المكوّنمهمته
1. Promtailيشحن الـ Logs من الـ Nodes
2. Distributorيحقّق ويعمل Hash لتدفقات الـ Logs الواردة
3. Ingesterيدفع الـ Streams دفعات Chunks ويكتبها
4. Storeيحفظ الـ Chunks والـ Index (Object Storage أو Disk محلي)
5. Querierينفّذ استعلامات LogQL القادمة من Grafana
KEY IDEAالـ Log Stream = مزيج Labels فريد. كل مجموعة Labels مختلفة هي Stream مستقلة بذاتها — ولهذا بالضبط تهم كثيرًا الـ Labels التي يلحقها Promtail (الجزء 3·c).
NOTE · القراءة مقابل الكتابةالكتابة تتدفق يسارًا→يمينًا عبر الـ Pipeline (1←4). القراءة لا تلمس مقدمة مسار الكتابة: الـ Querier (5) يسحب الـ Chunks + Index المخزنة من الـ Store (ومن الـ Ingester للبيانات الحديثة غير المفرغة بعد).
🎓 EXAMالـ Pipeline: Promtail ← Distributor (يحقّق ويعمل Hash) ← Ingester (Chunks) ← Store (Chunks + Index) ← Querier (LogQL). الـ Log Stream = مزيج Labels فريد.

🚚 Promtail Workflow — لماذا DaemonSet + الخطوات الأربع

🟡 6 MIN

يعمل Promtail كـ DaemonSet — Pod واحد لكل Node في الكلستر. لماذا؟ لأن Container Logs هي ملفات على الـ Filesystem المحلي لكل Node. وPod Promtail على Node A يستحيل جسديًا أن يقرأ /var/log/pods الخاصة بالـ Node B. بيانات محلية للـ Node ⇐ جامع محلي للـ Node.

TASK [الخطوات الأربع]discover ← tail ← label ← ship

1️⃣ Discover — اكتشف

يستخدم Service Discovery الخاص بـ Kubernetes لاكتشاف كل Pod يعمل على الـ Node الخاصة به.

2️⃣ Tail — اقرأ

يقرأ ملفات الـ Container Logs مباشرة من /var/log/pods — مثل أمر tail -f.

3️⃣ Label — علّم

يلحق الـ Kubernetes Metadata كـ Labels: namespace, pod, container, node.

4️⃣ Ship — اشحن

يدفع دفعات الأسطر إلى Distributor الخاص بـ Loki عبر HTTP.

KEY IDEA · الـ Labels هي الترس في الماكينةالخطوة 3 أهم مما تبدو: لأن Labels الـ Promtail مطابقة تمامًا لـ Labels الـ Prometheus، يصبح التنقّل بين الـ Logs والـ Metrics في Grafana سلسًا — نفس الـ Namespace، نفس الـ Pod، نفس اللغة — والـ Logs والـ Metrics قابلة للربط المتبادل افتراضيًا. ترى قفزة CPU على pod X, namespace Y في Panel من Prometheus ← تستعلم {namespace="Y", pod="X"} في Loki ← تقرأ الـ Logs من نفس النافذة. صفر إعدادات إضافية ينتج هذا.
WATCH OUT · Cardinality الـ Labelsالـ Labels مفهرسة إذًا مكلفة نسبيًا في Loki — لا تلصق قيمًا متغيرة بلا حدود (مثل user_id) كـ Labels. التزم بالثوابت المنظمة: namespace, app, pod, container, node.
NOTEالخطوة 4 تكمل نموذج الدفع: Promtail يدفع دفعات عبر HTTP — عكس Prometheus الذي يسحب من الـ Targets. نفس الـ Labels، واتجاه نقل معاكس.
🎓 EXAMPromtail = DaemonSet (Pod لكل Node — الـ Logs ملفات محلية في /var/log/pods) · الخطوات: Discover ← Tail ← Label (نفس Labels الـ K8s كما في Prometheus) ← Ship (دفع HTTP) · الـ Labels المشتركة = ربط Logs↔Metrics مجاني.

📈 Prometheus — الأساسيات

🟡 6 MIN

Prometheus هو نظام مراقبة مفتوح المصدر يستخدم نموذج السحب (Pull Model): يسحب (Scrape) الـ Metrics من الـ Targets على فاصل زمني منتظم، بدلًا من انتظار التطبيقات لدفع البيانات إليه.

TASK [المفاهيم الثلاثة الجوهرية]تخزين · استعلام · تنبيه

🗄️ Storage

كل قياس هو Time Series: اسم Metric + Labels مفتاح/قيمة + سلسلة قيم مختومة بالوقت. مثال: container_cpu_usage_seconds_total{namespace="app", pod="api-7d9f"} — الـ Labels هي الأبعاد التي تجمع عليها.

🔍 Querying — PromQL

لغة استعلام قوية للتجميع (Aggregation) والفلترة وحساب المعدلات (Rates) فوق بيانات الـ Time Series.

🚨 Alerting — Alertmanager

يتزامن مع Alertmanager لتحويل شروط PromQL إلى تنبيهات موجَّهة — Slack وEmail وPagerDuty. (معطّل في هذا الـ Lab — لكن المفهوم قائم.)

TASK [لماذا يهم السحب؟]نتائج عملية
سيطرة مركزيةالـ Scraper هو من يقرر الإيقاع وقائمة الـ Targets — التطبيقات لا تحتاج لمعرفة مكان Prometheus أصلًا. فقط اكشف نقطة /metrics، ولا شيء أكثر.
الفشل مرئيالـ Target الميت لا يترك فجوة في البيانات فقط — مقياس الـ up عنده يصبح 0. تستطيع حرفيًا الاستعلام عمّا إذا كانت المراقبة نفسها تعمل.
TASK [اكتشاف الـ Targets]بلا قوائم IPs يدوية
في Kubernetes يجد Prometheus الـ Targets تلقائيًا via Service Discovery + Custom Resources (CRDs)

لا أحد يصون قائمة عناوين Pods — الـ Pods زائلة أصلًا؛ القائمة ستكون قديمة خلال دقائق.

WATCH OUTكل مزيج Labels فريد يُنشئ Series جديدة — نفس مسألة انفجار الـ Labels في Loki: كثرة الـ Labels المتغيرة = انفجار في عدد الـ Series.
🎓 EXAMPrometheus: Pull Model · الـ Time Series = اسم + Labels + قيم مختومة بالوقت · الاستعلام: PromQL · التنبيه: Alertmanager (معطّل هنا) · اكتشاف الـ Targets: تلقائي عبر Service Discovery + CRDs · الـ Target الميت = up == 0.

🔗 Traces — رحلة الـ Request

🟢 4 MIN

الـ Trace يسجّل الرحلة الكاملة لـ Request واحد وهو ينتقل عبر عدة Services:

TASK [رحلة Request واحدة]مثال محلول
🌐 API Gateway 2ms ──► 🔐 Auth Service 15ms ──► 📦 Order Service 40ms ──► 🗄️ DB Query 120ms ⚠

الـ Trace يكشف فورًا: أغلب الوقت ذهب إلى الـ DB Query — لا تخمين، ولا فحص يدوي لكل Service.

5.1الغرض

الـ Traces تُظهر بالضبط أين صُرف الوقت أثناء الـ Request. الـ Metrics تخبرك أن الـ Requests بطيئة؛ والـ Traces تخبرك أي Hop جعلها بطيئة — أي Service تباطأت، أي استدعاء تكرر، وأين الاختناق الحقيقي.

5.2الأدوات

الـ Tracing يستخدم عادةً Grafana Tempo أو Jaeger أو Zipkin، مع تجهيز التطبيقات عبر OpenTelemetry.

NOTE · في هذا الـ Labالـ Traces غير منشورة في هذا الـ Lab تحديدًا — لكنها تمثل الخطوة الطبيعية التالية بعد وجود الـ Logs (Loki) والـ Metrics (Prometheus). اثنتان من الإشارات الثلاث تعملان الآن.
KEY IDEAعندما يقول لك أحدهم «الـ API بطيء» — الـ Logs تخبرك ماذا حدث، والـ Metrics تخبرك بكم هو بطيء، لكن الـ Trace وحده يخبرك أين بالضبط ذهب الوقت داخل رحلة الـ Request.
🎓 EXAMالـ Trace = رحلة Request واحد عبر Services متعددة · الغرض: أين صُرف الوقت · الأدوات: Grafana Tempo / Jaeger / Zipkin عبر OpenTelemetry · غير منشور في هذا الـ Lab — إنه الخطوة التالية.

📊 Grafana — الواجهة الموحدة

🟡 7 MIN

Grafana هو الواجهة الموحدة لمنظومة الـ Observability — لوح الزجاج الذي يلتقي عنده الـ Logs والـ Metrics.

TASK [أربعة مفاهيم]البيانات · الإعداد · الـ Dashboards · Explore

🔌 التعامل مع البيانات

Grafana لا يخزّن البيانات بنفسه — يتصل بـ Data Sources (Prometheus وLoki) ويستعلمها مباشرة عند كل تحديث للـ Panels. امسح الخلفيتين وليس لدى Grafana ما يعرض — إنه عدسة لا قاعدة بيانات.

⚙️ Configuration

كل Data Source يحتاج: URL + Authentication + لغة الاستعلام التي سيتحدثها (PromQL أو LogQL).

📊 Dashboards & Panels

الـ Dashboard مجموعة من الـ Panels. كل Panel يشغّل استعلامًا ويعرضه كـ Graph أو Table أو Log Stream أو Gauge. والـ Dashboards تُكتب JSON — قابلة للـ Version-Control أو الاستيراد من grafana.com/dashboards برقم ID.

🔍 Explore Mode

تشغيل استعلامات Ad-hoc من PromQL أو LogQL دون بناء Dashboard — الأداة المفضلة للتصحيح («أرني أخطاء ذلك الـ Namespace الآن»).

TASK [التسلسل الهرمي داخل Grafana]التسلسل
📊 Dashboard ◂ تحتوي 🧩 Panels ◄ تستعلم من 🔌 Data Source ◄ وهو 🗄️ Loki / 📈 Prometheus
KEY IDEAGrafana عديم الذاكرة عمدًا: كل Panel = استعلام حي في لحظة المشاهدة. لا يسأل أحد «هل الـ Dashboard محدَّث؟» — إنه محدَّث بحكم التعريف، لأنه يستعلم المصدر مباشرة عند كل تحميل.
✅ استغل هذه الميزة · Dashboards كـ Codeالـ Dashboards ملفات JSON — ضعها في Git. Dashboard مفقود = استرجاعه من Git؛ وتغيير مقصود = Pull Request يُراجع مثل أي Code آخر. إدارة إصدارات الـ Dashboards ميزة تُستغل، لا مصادفة.
WATCH OUT · تفصيلة نشرفي هذا الـ Stack، Grafana منشور بواسطة kube-prometheus-stack لا مستقلًا. هذه الحقيقة هي بالضبط سبب فخ تعارض الـ Datasource في الجزء 8·b — أفضل قصة «عطل صلّحته» في هذا الدليل.
🎓 EXAMGrafana: لا يخزّن — Data Sources حية · الـ Data Source = URL + Auth + لغة استعلام · Dashboard = مجموعة Panels (graph/table/logs/gauge) · Dashboards = JSON ← Git: استرجاع + مراجعة PR · Explore = تصحيح Ad-hoc.

Part 07

🧩 How It All Fits Together — في Kubernetes

🟡 6 MIN
TASK [تدفق البيانات الكامل]ست خطوات من طرف لطرف
  1. Pods التطبيقات تكتب Logs وتكشف (اختياريًا) نقطة /metrics.
  2. على كل Node، Promtail (DaemonSet) يقرأ /var/log/pods، يلحق كل سطر بـ Metadata الـ Kubernetes، ويدفع دفعات إلى Distributor الخاص بـ Loki.
  3. على كل Node، node-exporter (DaemonSet) يعرض مقاييس الـ Host؛ وcAdvisor (داخل الـ kubelet) يعرض مقاييس كل Container؛ وkube-state-metrics يعرض حالة الـ Objects.
  4. Prometheus يسحب كل تلك المقاييس على فاصل scrape، مكتشفًا الـ Targets عبر Service Discovery والـ CRDs (ServiceMonitor/PodMonitor).
  5. Grafana يحمل الاثنين كـ Data Sources ويستعلم Prometheus (PromQL) وLoki (LogQL) مباشرة.
  6. تفتح Grafana في المتصفح عبر نفق port-forward وترى كل شيء.
TASK [ناقلان، نموذج Labels واحد]اللاصق
📜 Promtail ── يدفع الـ Logs (HTTP) ──► 🗄️ Loki
📈 Prometheus ◄── يسحب الـ Metrics (scrape) ── 🖥️ node-exporter · cAdvisor · kube-state-metrics · التطبيقات

لكلهما يحمل نفس الـ Labels — namespace / pod / container / node — وهذا ما يجعل الـ Stack يبدو كنظام واحد.

KEY IDEAالـ Logs تُدفع؛ والـ Metrics تُسحب. اتجاهات النقل تختلف، لكن مفردات الـ Labels متطابقة — وهذا النموذج المشترك هو اللاصق. لهذا تكفيك قفزة Labels واحدة في Grafana لتنقلك من Graph للـ CPU إلى أسطر الـ Logs التي تشرحه.
NOTE · نمط الوصولGrafana Service من نوع ClusterIP — يُوصل من داخل الكلستر فقط. من حاسبك تصل إليه عبر kubectl port-forward (الأمر الكامل وتشريحه في الجزء 8·b).
🎓 EXAMالتدفق: Apps/Nodes تولّد ← Promtail يدفع Logs ← Loki · Prometheus يسحب Metrics ← TSDB · Grafana يستعلم الاثنين حيًّا ← المتصفح عبر port-forward. Push ≠ Pull، لكن الـ Labels مشتركة.

🚀 Helm + kube-prometheus-stack

🟠 8 MIN

Helm هو مدير حزم لـ Kubernetes. يجمع كل الـ Manifests اللازمة — Deployments وServices وConfigMaps وCRDs — في «Charts». تثبيت Chart يُنشئ Release. والـ Charts تعيش في Repositories تضيفها إلى جهازك. بدل عشرات ملفات YAML المكتوبة يدويًا، أمران من Helm ينشران المنظومة كاملة — بما فيها الـ Dashboards الافتراضية وربط الـ Data Sources. Helm حوّل مشروعًا من أسبوع إلى أمرين.

TASK [الإعداد — Repos + Namespace]أفضل ممارسة: Namespace مخصص
# أضف المستودعين، حدّث الفهارس، أنشئ الـ Namespace helm repo add prometheus-community https://prometheus-community.github.io/helm-charts helm repo add grafana https://grafana.github.io/helm-charts helm repo update kubectl create namespace observability # يُبقي المراقبة منفصلة عن أعباء التطبيقات
TASK [الـ Chart الأول: kube-prometheus-stack]Chart واحد، مكوّنات كثيرة
يثبّتPrometheus · Alertmanager · Grafana · node-exporter · kube-state-metrics · الـ ServiceMonitor/PodMonitor CRDs · Dashboards افتراضية للـ Kubernetes — دفعة واحدة.
⚠ إدارة المواردافتراضيًا يطلب هذا الـ Chart CPU وRAM أكثر مما يستطيع Cluster Minikube صغير تحمّله — ثبّته خامًا وستعلق الـ Pods في Pending لأن الـ Scheduler لا يجد مكانًا يتسع لطلبات الموارد. يجب تقليم Resource Requests/Limits لكل مكوّن بشراسة عبر أعلام --set:
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \ -n observability \ --set alertmanager.enabled=false \ --set prometheus.prometheusSpec.retention=6h \ --set grafana.adminPassword=admin123 \ --set prometheus.prometheusSpec.resources.requests.cpu=100m \ --set prometheus.prometheusSpec.resources.requests.memory=256Mi \ --set grafana.resources.requests.cpu=50m \ --set grafana.resources.requests.memory=128Mi # ...وما شابه من التقليم لـ kube-state-metrics وnode-exporter. # مفاتيح القيم الدقيقة: helm show values prometheus-community/kube-prometheus-stack

retention=6hتخزين الـ TSDB يكبر مع مدة الاحتفاظ؛ الـ Lab لا يحتاج تاريخًا — 6 ساعات تكفي للتصحيح
alertmanager.enabled=falseلا حاجة لتوجيه تنبيهات في Lab ← Pods أقل وRAM أقل

🎓 EXAMHelm = مدير حزم K8s (Charts ← Releases من Repos) · Chart واحد يثبّت منظومة الـ Metrics كاملة · Minikube يحتاج تقليم الـ Requests وإلا Pending · retention 6h يوفر القرص · helm upgrade --install = Idempotent.

⚠️ loki-stack + الفخ الشهير + Port-Forward

🟠 8 MIN
helm upgrade --install loki-stack grafana/loki-stack \ -n observability \ --set grafana.sidecar.datasources.defaultDatasourceEnabled=false # ← العلم الحاسم
TASK [⚠ تعارض تزويد الـ Datasource]الفخ الوحيد غير البديهي
  1. loki-stack يُرفق ConfigMap خاصًا به للـ Grafana Data-Source الخاص بـ Loki.
  2. الـ Grafana Sidecar (العامل داخل Grafana المنشور من kube-prometheus-stack) يكتشف تلقائيًا ConfigMaps الـ Datasources ويحمّلها — فيظهر Loki في Grafana بلا أي إعداد يدوي. لطيف.
  3. التعارض: kube-prometheus-stack يعيّن Prometheus كـ Datasource الافتراضي (Default). وloki-stack يحاول أيضًا تعيين Loki كافتراضي.
  4. Grafana يسمح بافتراضي واحد بالضبط. اثنان افتراضيان = «Datasource provisioning error» ← Grafana يهدم ← يعيد التشغيل ← يهدم ← CrashLoopBackOff.
✅ الحلثبّت Loki مع --set grafana.sidecar.datasources.defaultDatasourceEnabled=false — يبقى Loki Datasource، لكن ليس الافتراضي (ويبقى Prometheus هو الافتراضي).

🔍 LogQL — الاستعلام عن Loki

🟡 7 MIN

التأطير: خلفيتان، لغتا استعلام، واجهة واحدة. LogQL صُمم عمدًا ليكون شبيهًا بـ PromQL، وكلاهما يختار بنفس الـ Labels — تعلّم واحدة والثانية تصبح مألوفة.

TASK [ابدأ من وضع Explore]بلا Dashboard
Grafana ← Explore ← اختر Data Source ← شغّل استعلامات Ad-hoc
🗄️ Loki: {namespace="observability"} ← Streams حية 📈 Prometheus: up ← 1 سليم، 0 ساقط
TASK [LogQL — لكل استعلام حتى ثلاث مراحل]محدد ← فلترة ← غلاف رقمي

1️⃣ محدد الـ Stream

الـ Labels — مفهرسة وسريعة. يختار أي Log Streams ستُقرأ.

2️⃣ Pipeline الفلترة

فلترة الأسطر — تُقيَّم لحظة الاستعلام على الـ Streams المطابقة.

3️⃣ غلاف الـ Metric

يحوّل عدّ الأسطر إلى أرقام — الـ Logs تصبح Metric.

# 1) محدد الـ Stream: كل Logs الـ Namespace {namespace="observability"} # تضييق بالـ Pod / Container (الـ Labels التي لحقها Promtail) {namespace="default", pod="my-app-7d9f8b6c-", container="app"} # 2) فلترة الأسطر: احتفظ / احذف حسب المحتوى (Loki يبحث النص هنا) {namespace="observability"} |= "error" {namespace="observability"} |= "error" != "timeout" # 3) استعلام Metric: عدّ الأسطر المطابقة لكل Pod في نافذة 5m sum by (pod) (count_over_time({namespace="default"} |= "error" [5m]))
KEY IDEA · لماذا يهم هذا الترتيب؟محدد الـ Labels يُشغَّل على الـ Index؛ والبحث النصي يُشغَّل على الـ Streams المطابقة لحظة الاستعلام. هذا هو العائد المباشر من تصميم Loki «فهرس الـ Labels فقط» — التخزين الرخيص لا يعني استعلامات بطيئة إذا اخترت Labels جيدة.
NOTE · الجسرالمرحلة 3 تحوّل الـ Logs إلى Metric (count_over_time فوق نطاق [5m]) — شقيق بنيوي لـ rate() في PromQL، والجسر بين نوعي الإشارات.
🎓 EXAMLogQL = محدد Stream (مفهرس) ← فلترة أسطر (لحظة الاستعلام) ← غلاف Metric اختياري · |= احتفظ، != احذف · count_over_time(...[5m]) يحوّل أسطر الأخطاء إلى معدل لكل Pod.

TASK [آليتان تستحقان الاستيعاب]Range Vectors والتجميع

⏱ [5m] = Range Vector

يختار نقاطًا كثيرة خلال 5 دقائق — دوال مثل rate() تتطلب نطاقًا. قيمة لحظية واحدة لا تُنتج معدلًا.

🧮 sum by (pod) = تجميع

يجمع عبر الـ Labels مع إبقاء pod ك بعد التجميع — نفس الـ Labels التي يستخدمها Loki، فتصطف النتائج عبر الخلفيتين.

TASK [تصحيح لحظي أم اتجاهي؟]اختر السؤال الصحيح
«هل هو معطّل الآن؟» ← up · Stream خام {namespace="..."}
«هل يتجه للتعطّل؟» ← rate() على [5m] · عدد الأخطاء/Pod · Graph كسر الـ Memory
KEY IDEAلأن لغتي الاستعلام تختاران نفس الـ Labels، يعمل نفس التجميع sum by (pod) على الجانبين — معدل الأخطاء لكل Pod من Loki يتطابق تمامًا مع معدل الـ CPU لكل Pod من Prometheus في Panels متجاورة داخل Grafana.
🎓 EXAMup = صحة السحب · rate(counter[5m]) يحتاج Range Vector · sum by (pod) يُبقي label التجميع · cAdvisor ← مقاييس الـ Containers · node-exporter ← مقاييس node_*.

🛠️ Troubleshooting — السيناريوهات 1–3

🟠 8 MIN

فكّر بمنطق: عرض ← تشخيص ← سبب جذري ← إصلاح. تسلسل أوامر التشخيص أهم من حفظ الإصلاحات.

🔴 السيناريو 1 — Pods عالقة في Pending

العرضkubectl get pods -n observability ← Pods جاثمة في Pending لا تبدأ
التشخيصkubectl describe pod <pod> -n observability ← الأحداث تُظهر FailedScheduling: Insufficient cpu / memory
السبب الجذريالكلستر يفتقر CPU/Memory حرّة — طلبات الموارد الافتراضية للـ Chart لا تتسع على Node الـ Minikube، والـ Scheduler لن يضع Podًا لا تتسع طلباته
الإصلاحقلّل الطلبات (أعلام --set من الجزء 8) أو كبّر Minikube (--cpus=... --memory=...)
الدرسPending = مشكلة جدولة = انظر إلى الطلبات مقابل المتاح قبل أي شيء آخر

🔴 السيناريو 2 — Grafana بحالة OOMKilled

العرضGrafana يعيد التشغيل باستمرار؛ kubectl describe pod يُظهر OOMKilled (Exit Code 137)
السبب الجذريالـ Container نفدت ذاكرته — تجاوز حدّ الـ Memory الخاص به
شخّص أولًاافحص ذاكرة الـ Node الحرة أولًا (kubectl top nodes) — لا ترفع حدّ Grafana بدم بارد
الإصلاحالـ Node فيها مجال ← ارفع الحدّ عبر --set؛ الـ Node مكتظة ← حرّر الموارد (عطّل مكوّنات، قلّم Pods، كبّر Minikube)
الدرسOOMKilled = مشكلة حدّ؛ إنهاك الـ Node = مشكلة سعة. شخّص أي الاثنين أمامك.

🔴 السيناريو 3 — Grafana في CrashLoopBackOff مع خطأ Provisioning

العرضGrafana يدور في CrashLoopBackOff؛ Logs تُظهر «Datasource provisioning error»
التشخيصkubectl logs <grafana-pod> -n observability · kubectl get configmap -n observability ← ستجد ConfigMapَي Datasource، كلاهما Default
السبب الجذريDatasourceان معلَّمان Default — Grafana يسمح بواحد بالضبط؛ التزويد يفشل عند كل إقلاع ← حلقة هدم. ليست مشكلة موارد — فشل تحقق Config قد يُسقط Podًا مضبوط الحجم تمامًا.
الإصلاحوقاية: ثبّت loki-stack مع defaultDatasourceEnabled=false · علاج: احذف isDefault: true من الـ ConfigMap الزائد ثم kubectl delete pod (الـ Deployment يعيد إنشاءه نظيفًا)
الدرساقرأ Logs الانهيار — رسالة الخطأ تسمّي النظام الفرعي (Provisioning)، وهذا يشير مباشرة إلى الـ ConfigMaps. هذه قصة المقابلة النجمية.

🔴 السيناريو 4 — «Connection refused» من Windows / WSL

العرضمتصفح Windows لا يصل إلى localhost:3000 رغم أن الـ port-forward يعمل
السبب الجذريالنفق ارتُبط على الـ loopback داخل الـ WSL VM فقط — كان علم --address 0.0.0.0 مفقودًا
الإصلاحأعد الأمر كاملًا kubectl port-forward --address 0.0.0.0 -n observability svc/kube-prometheus-stack-grafana 3000:80
الدرسعلى WSL، متصفحك والكلستر تسكنهما حدود شبكية مختلفة — اربط كل الواجهات ليعمل الترحيل

🟠 السيناريو 5 — «Grafana لا يُظهر بيانات» (تسلسل الاستدلال العام)

اعمل على السلسلة بالترتيب — الأسباب المملة هي الأكثر شيوعًا:

  1. هل Pod الخلفية يعمل؟ ← kubectl get pods -n observability (Loki أو Prometheus منهار = لا استعلام سينجح).
  2. هل الـ Datasource حي؟ ← Explore ← شغّل up (Prometheus) أو {namespace="observability"} (Loki). إن عمل Explore ولم يعمل Dashboard، فالمشكلة في استعلام/نطاق زمن الـ Dashboard — لا في الـ Stack.
  3. Metrics التطبيق مفقودة تحديدًا؟ ← لا نقطة /metrics، أو الـ ServiceMonitor Selector لا يطابق — افحص up للـ Target.
  4. الـ Namespace الصحيح؟ النطاق الزمني الصحيح؟ ← الأسباب البسيطة تستحق نظرة أولًا.

12التنظيف — إزالة الـ Stack بالكامل

helm uninstall kube-prometheus-stack -n observability helm uninstall loki-stack -n observability kubectl delete namespace observability
⚠ ملاحظة عمليةحذف الـ Namespace يزيل ما تركه الـ Chartان بداخله — لكن الـ CRDs التي ثبّتها kube-prometheus-stack هي Cluster-Scoped وقد تبقى بعد الـ Uninstall. احذفها يدويًا إن أردت Cluster نظيفًا تمامًا.

🎤 أسئلة المفاهيم — بإجابات مركّزة

🟠 10 MIN
Q1 ما هي الـ Observability؟
فهم ما يحدث داخل النظام من البيانات التي ينتجها — بدون نشر Code جديد لسؤال جديد. الركائز: Logs وMetrics وTraces وVisualization.
Q2 Logs vs Metrics vs Traces — متى تستخدم كلًا؟
Logs = ماذا حدث (أحداث حرفية). Metrics = كم وبأي سرعة (اتجاهات وتنبيه). Traces = أين ذهب الوقت (لكل Hop). تدفق التصحيح: تنبيه ← Trace ← Log.
Q3 لماذا Loki أرخص 10–20× من أنظمة النص الكامل؟
يفهرس الـ Metadata (Labels) فقط لا نص الـ Logs؛ النص يُبحث لحظة الاستعلام. والـ Chunks تُضغط في Object Storage رخيص.
Q4 Pull vs Push — نموذج Prometheus مقابل Promtail؟
Prometheus يسحب (scrape على فاصل — سيطرة مركزية على الإيقاع؛ والـ Target الميت مرئي عبر up=0). وPromtail يدفع دفعات HTTP إلى Distributor الخاص بـ Loki.
Q5 لماذا Promtail وnode-exporter يعملان DaemonSets؟
بياناتهما محلية للـ Node: الـ Container Logs في /var/log/pods لكل Node؛ ومقاييس الـ Host لكل Machine. Pod لكل Node = تغطية كاملة.
Q6 ممّ يتكوّن الـ Time Series في Prometheus؟
اسم Metric + Labels مفتاح/قيمة + سلسلة قيم مختومة بالوقت.
Q7 node-exporter vs kube-state-metrics vs cAdvisor؟
مقاييس الـ Machine (DaemonSet) مقابل حالة الـ Objects من API Server (حالة Pods وReplicas وRestarts) مقابل استهلاك كل Container المدمج في kubelet.
Q8 ما الـ ServiceMonitor/PodMonitor ولماذا وُجدتا؟
CRDs تخبر Prometheus تصريحيًا أي Services/Pods يسحب — بلا قوائم IPs يدوية؛ نشر الـ CRD هو الإعداد (Helm يوصله تلقائيًا).
Q10 لماذا helm upgrade --install لا helm install؟
الـ Idempotency — إعادة التشغيل ترقّي Release موجودًا في مكانه بدل الفشل.
Q11 لماذا port-forward لا NodePort/LoadBalancer؟
Grafana منشور ClusterIP (داخلي فقط). الـ port-forward = وصول Lab بلا إعدادات؛ وNodePort/LB/Ingress هو ما تكشف به الخدمة رسميًا. على Windows/WSL يجب تمرير --address 0.0.0.0.
Q12 لماذا نُنزل retention الـ Prometheus إلى 6h في Lab؟
تخزين الـ TSDB يكبر مع الـ retention؛ الـ Lab لا يحتاج تاريخًا — 6h توفر قرصًا معتبرًا.
Q13 كيف ترتبط الـ Logs بالـ Metrics في هذا الـ Stack؟
نفس الـ Label Model — Promtail يلحق الـ Labels نفسها التي يستخدمها Prometheus (namespace/pod/container/node)، فتترجم شذوذة Metric مباشرة إلى Stream الـ Logs لذلك الـ Pod.
Q14 ما الخطوة الطبيعية التالية لهذا الـ Stack؟
الـ Traces — انشر Grafana Tempo (أو Jaeger/Zipkin) وجهّز التطبيقات بـ OpenTelemetry — لتكتمل الإشارات الثلاث.
Q9 ⭐ احكِ لي عن Bug صلّحته في هذا الـ Stack.
Grafana في CrashLoopBackOff مع خطأ Datasource provisioning: كلا الـ Chartين زوّد Datasource معلَّمًا Default؛ وGrafana يسمح بواحد بالضبط. شخّصته عبر Logs الـ Pod + kubectl get configmap؛ وأصلحته بـ grafana.sidecar.datasources.defaultDatasourceEnabled=false (أو حذف isDefault: true).
🎓 نصيحة المقابلةالسؤال Q9 هو القصة النجمية — يُظهر تصحيحًا حقيقيًا: اقرأ Log الانهيار، كوّن فرضية من النظام الفرعي المسمّى في الخطأ (Provisioning)، تحقّق بالـ ConfigMaps، طبّق الإصلاح الموجّه، واذكر الدرس (فشل تحقق Config قد يُسقط Podًا مضبوط الحجم تمامًا).

  7. إنه طبقة عرض: يتصل بـ Data Sources (Prometheus وLoki) ويستعلمها حيًّا.
