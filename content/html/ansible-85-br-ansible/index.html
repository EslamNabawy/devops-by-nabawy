🤖 Intro — مقدمة ونظرة عامة

🟢 5 MIN

Ansible هي أداة Automation مفتوحة المصدر (Open-Source) تُستخدم بشكل أساسي في ثلاثة مجالات:

Configuration Management

إدارة الإعدادات داخل الـ Servers.

Infrastructure Provisioning

بناء وتجهيز البنية التحتية.

Network Automation

أتمتة أجهزة الشبكة.

KEY IDEA · الفكرة الأساسيةأنت تحدد الـ Desired State التي تريد أن يصل إليها الـ Infrastructure — وAnsible يتولى تنفيذ الخطوات المطلوبة للوصول إليها. أنت توصف النهاية، وهو يصنع الطريق.
TASK [كيف تعمل الفكرة عمليًا؟]the core loop
✍️ أنت تكتبالـ Desired State في YAML
──►
Ansibleيحسب الـ Steps المطلوبة
──►
Infrastructureيصل للحالة المطلوبة ✅

نفس الـ Code في كل مرة = نفس النتيجة. لا Scripts عشوائية ولا خطوات منسية.

DEBUG · لماذا هذا مهم؟في الإدارة اليدوية، كل Server حالة مستقلة: من لمّس ماذا؟ ما الذي تغيّر؟ مع Ansible، الـ Infrastructure كلها موصوفة في Code واحد قابل للقراءة والمراجعة وإعادة التنفيذ — هذا جوهر الـ IaC mindset الذي تبنيه Ansible.
🎓 EXAMاحفظ المجالات الثلاثة بالترتيب: Configuration Management · Infrastructure Provisioning · Network Automation — والجملة الجوهرية: «تحديد الـ Desired State وAnsible ينفّذ الخطوات».

Chapter 02 · Features 1/2

📡 Agentless — بدون عميل

🟢 5 MIN

من أهم مميزات Ansible أنها Agentless — يعني لا تحتاج إلى تثبيت برنامج أو Agent خاص بـ Ansible على الـ Managed Nodes. لا تثبيت مسبق، لا صيانة Agents، لا Versions تتزامن.

🐧 في Linux

  • الاتصال عادةً باستخدام SSH.
  • المتطلب الأساسي على الـ Managed Node: وجود بيئة Python.

🪟 في Windows

يمكن استخدام WinRM أو SSH للاتصال والتنفيذ.

TASK [القناة بين الجهازين]the connection
Control Nodeعليه Ansible فقط
━━━ SSH / WinRM ──►
Managed NodeUbuntu / CentOS / DB

الـ Control Node يتصل عند الحاجة وينفّذ ويرحل — الـ Managed Node لم يتغير إعداده أصلًا.

KEY IDEAقارن مع أدوات أخرى تطلب Agent على كل جهاز: تثبيت، تحديث، صيانة. في Ansible: المتطلب = SSH + Python (موجود افتراضيًا في أغلب التوزيعات). هذا يقلل الـ friction في الـ Onboarding لأدنى حد.
WATCH OUT«Agentless» لا تعني «بلا متطلبات» — الـ Python environment على الـ Managed Node شرط أساسي في Linux. أنظمة نادرة بلا Python تحتاج خطوة تجهيز واحدة قبل أول Run.
🎓 EXAMسؤال كلاسيكي: «ما معنى Agentless وما المتطلبات؟» → لا Ansible Agent يُثبَّت على الـ Managed Nodes · الاتصال عبر SSH (Linux) أو WinRM (Windows) · المتطلب: Python على الـ Target.

🎯 Declarative + Idempotency

🟡 7 MIN

2.2Simple Syntax

الـ Playbooks تُكتب باستخدام YAML — مصممة بحيث تكون سهلة القراءة والكتابة، وتعتمد بشكل أساسي على الـ Indentation لتنظيم الـ structure. (التفصيل الكامل في فصل YAML لاحقًا.)

2.3Declarative Approach

في الـ Declarative Approach أنت تحدد ما الذي تريده في النهاية بدلًا من كتابة كل خطوة يدوية للوصول إليه:

- name: Install Apache apt: name: apache2 state: present

❌ أنت لم تقل

apt install

أمر تنفيذي أعمى — يُنفَّذ دائمًا حتى لو غير مطلوب.

✅ أنت قلت

Apache must exist

وحدة هدفية — state: present = الـ Desired State.

Ansible يحدد بنفسه ما إذا كان يحتاج إلى إجراء تغيير للوصول إلى هذه الحالة — أم أن كل شيء على ما يرام.

DEBUGAnsible يدعم أيضًا الـ Imperative Approach عند استخدام الـ Ad-hoc Commands — أمر فوري لمهمة سريعة. الأسلوبان معًا: Playbooks للتوصيف الدائم، Ad-hoc للتنفيذ اللحظي.

2.4Idempotency — التكرار الآمن ♻️

الـ Idempotency تعني أن تنفيذ نفس الـ Automation عدة مرات لا يؤدي إلى تغييرات غير ضرورية:

🎬 First Run

Apache غير مثبت ↓ Ansible installs Apache ↓ changed

🎬 Second Run

Apache موجود بالفعل ↓ No change required ↓ ok
🎓 EXAMلو كان Apache مثبتًا بالفعل، Ansible لن يعيد تثبيته بدون حاجة — يظهر ok لا changed. وفرق Declarative/Imperative: الأول يوصّف الحالة (Playbooks)، الثاني ينفّذ أمرًا فوريًا (Ad-hoc).

Chapter 04

🏗️ Architecture — معمارية Ansible

🟢 5 MIN

تتكون الـ Ansible Architecture بشكل أساسي من مكوّنين: Control Node وManaged Nodes.

Architecture — المكوّنان وما يحملانه
Control NodeAnsible · Playbooks · Inventory
━━━ SSH / WinRM ──►
Managed NodesUbuntu / CentOS / Database

الـ Control Node يحمل كل العتاد الفكري — الـ Managed Nodes يستقبلون وينفّذون فقط.

3.1Control Node — عقدة التحكم

هو الجهاز أو الـ Server الذي يتم تثبيت Ansible عليه. من خلاله يقوم الـ DevOps Engineer بـ:

  • ▸ تشغيل أوامر Ansible.
  • ▸ تشغيل الـ Playbooks.
  • ▸ إدارة الـ Managed Nodes.

يمكن أن يكون: Laptop · Linux Server · WSL Ubuntu Environment — أي جهاز تستطيع عليه تشغيل Ansible.

3.2Managed Nodes — العقد المُدارة

هي الـ Target Machines التي سيقوم Ansible بإدارتها. تستقبل الـ Instructions من الـ Control Node وتنفذها بدون الحاجة إلى تثبيت Ansible Agent عليها.

KEY IDEAالمعمارية «Star» بسيطة: مركز واحد ذكي (Control) يتحكم بنقاط متعددة (Managed) عبر قناة قياسية (SSH/WinRM). لا طبقات وسيطة، لا Coordination Services — لذا الـ Setup والتشخيص سهلان.
WATCH OUTالـ Ansible + الـ Playbooks + الـ Inventory كلها تعيش على الـ Control Node. الـ Managed Nodes تعرف شيئًا واحدًا فقط: «وصلني أمر SSH — أنفّذه».
🎓 EXAM«ما مكونات Ansible Architecture؟» → Control Node (Ansible + Playbooks + Inventory — منه التشغيل) وManaged Nodes (الـ Targets — تستقبل عبر SSH/WinRM بلا Agent). و«ما أشكال الـ Control Node؟» → Laptop / Linux Server / WSL.

TASK [قراءة الجدول على الواقع]practical lens

لنفس المهمة (تثبيت Nginx على الثلاثة): الـ Manual = 3 جلسات SSH و3 صيغ أوامر مختلفة (apt/yum/apk) وتحقق يدوي. الـ Bash = Script واحد لكن بفروع لكل Package Manager وكل توزيعة جديدة تضيف فرعًا. الـ Ansible = Task واحدة بـ YAML تعمل على الثلاثة — والـ Modules تختفي اختلافات التوزيعات، والـ Idempotency مدمجة تلقائيًا.

ASIDE · المفارقةBash Scripts خطوة تقدم عن الـ Manual — لكنها دَين تقني يتراكم: كل توزيعة = فرع، كل تغيير = مراجعة. Ansible يقلب السؤال: لا «كيف أنفّذ على كل نظام؟» بل «ما الـ State التي أريدها؟» — والـ Modules تعرف الباقي.
🎓 EXAMأربعة أزواج تحفظها: Manual = بطء + أخطاء + بلا Idempotency · Bash = مركزي لكن Scripting ثقيل + if/else · Ansible = YAML مركزي + Idempotency عبر Modules + تجاهل اختلافات الـ OS تلقائيًا.

🔐 SSH Keys — Passwordless Setup

🟠 8 MIN

في Linux يستخدم Ansible عادةً SSH للتواصل مع الـ Managed Nodes. الفكرة:

The Key Flow — من ينقل ماذا
Control Nodeيحمل الـ Private Key
── SSH Login ──►
Managed Nodeيحمل الـ Public Keyفي Authorized Keys

8.1إنشاء الـ SSH Key Pair — على الـ Control Node

$ ssh-keygen -t rsa -b 4096

ينتج عن ذلك ملفان:

🔑 id_rsa — Private Key

يُحفظ بشكل سري على الـ Control Node — لا يُشارك أبدًا.

🗝️ id_rsa.pub — Public Key

يتم وضعه على الـ Managed Node. قفله لا يفتح شيئًا.

8.2نسخ الـ Public Key إلى الـ Managed Node

$ ssh-copy-id -i ~/.ssh/id_rsa.pub ubuntu@<MANAGED_NODE_IP>

8.3اختبار الاتصال

$ ssh ubuntu@<MANAGED_NODE_IP> Welcome to Ubuntu 22.04 LTS … # no password ✅ $ exit

إذا تم إعداد الـ SSH Keys بشكل صحيح، يمكنك الاتصال بدون إدخال الـ Password في كل مرة.

WATCH OUTالـ Private لا يسافر أبدًا — الـ Public هو الوحيد الذي يُنسخ. عكسهما = اتصال لا يعمل + خطر أمني.
🎓 EXAMالسلسلة: ssh-keygen -t rsa -b 4096 ← ssh-copy-id -i ~/.ssh/id_rsa.pub user@ip ← اختبار ssh user@ip. النتيجة: أتمتة صامتة بلا Passwords.

🗂️ Inventory — ملف الـ Servers

🟡 5 MIN

الـ Inventory هو الملف الذي يخبر Ansible بالـ machines التي يستطيع إدارتها. يمكن أن يحتوي على: IP Addresses · Hostnames · Groups · Connection Variables.

TASK [مثال hosts.ini]inventory example

web ├── 192.168.1.101 └── 192.168.1.102

Group: db

DEBUG · التشريح[web] = اسم Group بين أقواس · الأسطر تحته = الأعضاء · ansible_user=ubuntu = Connection Variable تحدد الـ SSH User — تُعرَّف مرة بدل تكرارها.
KEY IDEAالـ Inventory = «مصدر الحقيقة» لخريطة الـ Infrastructure: Server جديد = سطر. User متغير = تعديل واحد. كل الـ Commands والـ Playbooks القادمة تحيل إليه بـ -i hosts.ini.

🎓 EXAMالـ Inventory يحتوي: IPs · Hostnames · Groups · Connection Variables — الـ Groups وحدات استهداف، ويُمرَّر الملف بـ -i.

TASK [الأمثلة الثلاثة]practical examples

11.1 اختبار الاتصال:

$ ansible all -i hosts.ini -m ping 192.168.1.101 | SUCCESS => { "ping": "pong" } 192.168.1.201 | SUCCESS => { "ping": "pong" }

$ ansible web -i hosts.ini -a "uptime"

11.3 تثبيت Nginx:

$ ansible all -i hosts.ini -m apt -a "name=nginx state=present" --become
TASK [معنى أهم الـ Options]flags decoded
-mاختيار الـ Module
-aModule Arguments
--becomeتشغيل العملية بصلاحيات مرتفعة
KEY IDEAاقرأ أي Ad-hoc Command كجملة: «على المجموعة X، وبالـ Inventory Y، استخدم Module Z بالـ Arguments W، بصلاحيات مرتفعة» — كل Flag جزء من الجملة.
WATCH OUTعند حذف -m يُستخدم الـ command Module افتراضيًا — لهذا -a "uptime" تعمل مباشرة. وAd-hoc لمهام لا تتكرر — المتكرر يذهب لـ Playbook.

📖 Playbooks — الكتيبات

🟠 8 MIN

الـ Playbook هو ملف YAML يحتوي على مجموعة من الـ Plays. كل Play تستهدف مجموعة من الـ hosts وتحتوي على مجموعة من الـ Tasks.

TASK [الـ Hierarchy الأساسية]the structure
Playbook │ ├── Play │ ├── Task │ ├── Task │ └── Task │ └── Play ├── Task └── Task
TASK [مثال: تثبيت وتشغيل Apache]أنشئ ملف site.yml
--- - name: Install and Start Apache Web Server hosts: web become: yes tasks: - name: Install Apache Package apt: name: apache2 state: present - name: Ensure Apache Service is Running and Enabled service: name: apache2 state: started enabled: yes
DEBUG · القراءة السريعةالملف = List فيها Play واحد · الـ Play تستهدف hosts: web (من الـ Inventory) · become: yes = صلاحيات root · Task1 تضمن الحزمة present · Task2 تضمن الـ Service started + enabled.
KEY IDEAلاحظ أن كل Task = Name وصفي + Module + State — أنت تقرأ الـ Playbook كقصة: «ثبّت Apache، ثم تأكد أن الخدمة تعمل ومفعّلة». الـ YAML يجعل الـ Automation مقروءًا كوثيقة.
🎓 EXAMالـ Hierarchy: Playbook → Plays → Tasks · Play = hosts targeting + قائمة Tasks · وكل Task يستدعي Module بـ State محددة.

📁 Role Structure 1/2 — tasks & handlers

🟡 7 MIN

عند إنشاء Role، يتم تنظيمها في Directories لها وظائف محددة:

nginx/ ├── tasks/ ├── handlers/ ├── vars/ ├── defaults/ ├── files/ ├── templates/ └── meta/

19.1tasks/ — المكان الأساسي

هذا هو المكان الذي تضع فيه الـ Tasks التي سينفذها الـ Role. أمثلة:

Install Nginx Create directories Configure packages Start service

19.2handlers/ — المهام المشروطة

يحتوي على الـ Handlers. الـ Handler هو Task يتم تنفيذها عندما يتم عمل Trigger لها — غالبًا من خلال notify:

The handler flow — المثال الشائع
Configuration File Changed
▼
notify
▼
Handler
▼
Restart / Reload Service

إذا تغيّر Nginx Configuration File، يمكن تشغيل Handler لعمل Restart أو Reload للـ Nginx Service.

KEY IDEAالـ Handler = رد فعل مشروط لا خطوة دائمة: يتلقى Trigger من notify عند حدوث تغيير فعلي — فلا Restarts عشوائية في كل Run، ولا تغييرات تبقى بلا تأثير.
WATCH OUTالـ notify يطابق اسم الـ Handler حرفيًا — خطأ إملائي = الـ Handler لن يشتغل أبدًا ولا يظهر Error.
🎓 EXAMtasks/ = الـ Tasks الرئيسية للـ Role · handlers/ = Tasks تُطلق بـ notify عند التغيير — المثال النموذجي: Config File Changed → notify → Restart Service.

Chapter 15·b · Part 2 of 2

📁 Role Structure 2/2 — vars إلى meta

🟡 8 MIN

19.3vars/ — المتغيرات الثابتة

يحتوي على الـ Variables الخاصة بالـ Role — ولها High Precedence مقارنةً بمصادر الـ Variables الأخرى. تُستخدم للقيم الخاصة بالـ Role التي لا يُفترض تغييرها بسهولة.

19.4defaults/ — المتغيرات القابلة للتجاوز

يحتوي على الـ Default Variables — مصممة بحيث يمكن عمل Override لها بسهولة عند استخدام الـ Role:

defaults/ ▼ Default Values ▼ Can be overridden

19.5files/ — الملفات الثابتة

يحتوي على الـ Static Files التي يمكن للـ Role نسخها إلى الـ Managed Nodes:

files/ └── index.html

19.6templates/ — القوالب الديناميكية

يحتوي على ملفات Jinja2 Templates — غالبًا بامتداد .j2. تُستخدم لإنشاء Configuration Files بشكل Dynamic اعتمادًا على الـ Variables:

Variables + Jinja2 Template ▼ Dynamic Configuration File

19.7meta/ — البيانات الوصفية

يحتوي على الـ Metadata الخاصة بالـ Role — ومن ضمن استخداماته تعريف الـ Dependencies: مثل Role أخرى يجب تنفيذها لكي يعمل الـ Role الحالي بشكل صحيح.

WATCH OUTأكثر خلط شائع: vars/ = قيم داخلية عالية الـ Precedence (لا تُلمس) · defaults/ = قيم مصممة للـ Override من المستخدم. الخاطئ في المكان = Role لا تقبل التخصيص أو تقبله أكثر من اللازم.
🎓 EXAMالسبعة بوظائفهم: tasks (التنفيذ) · handlers (مشروطة بـ notify) · vars (ثابتة عالية الأولوية) · defaults (قابلة للـ Override) · files (Static) · templates (Jinja2 .j2 ديناميكية) · meta (Metadata + Dependencies).

🔗 Using a Role + Galaxy

🟡 7 MIN
TASK [استخدام Role داخل Playbook]calling a role

DEBUG · فصل المسؤولياتالـ Playbook يقول ماذا يحدث (orchestration) — والـ Role تحمل كيف يحدث بالتفصيل (implementation). هذا الفصل يجعل الـ Playbook الرئيسي قصيرًا مقروءًا مهما كبر المشروع.
