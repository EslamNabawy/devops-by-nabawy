CH 01

⚙️ How a Cluster Is Born — kubeadm

🟡 6 MIN · CORE

Eight books assumed a cluster existed. Now: who builds it? A cluster is just machines running seven binaries (Book 01's cast) with a shared CA and a wired network. kubeadm is the official tool that does this plumbing — not a product, just a disciplined bootstrap.

$ kubeadm init \   --control-plane-endpoint="k8s-api.example.com:6443" \   --pod-network-cidr=10.244.0.0/16 # output: root CA · certs · static-pod manifests · the join command $ kubectl apply -f calico.yaml  # kubeadm does NOT install a CNI — you do $ kubeadm join k8s-api.example.com:6443 --token … --discovery-token-ca-cert-hash … # run on each worker → kubelet starts → node registers → Ready
What kubeadm init actually does ├── generates PKI: CA, certs for apiserver/etcd/scheduler… ├── writes static-pod manifests → /etc/kubernetes/manifests │ (Book 04 · CH 11: kubelet boots the control plane!) ├── starts etcd + CP components as static pods ├── writes kubeconfig → /etc/kubernetes/admin.conf └── prints the join command (token + CA hash = trust on first use)
💡
The bootstrap paradox, revisited: kubeadm doesn't "run" the control plane — it drops manifest files on disk, and the kubelet (the only thing already running) spawns the API Server as static pods. Book 04 · CH 11 explained why they're undeletable; now you know who wrote them.
ToolForVibe
kubeadmvanilla clusters on your VMs/metalthe official reference — CKA's stage
kops / Cluster APIinfrastructure-aware creation (cloud, IaC)kubeadm under the hood + lifecycle
managed (GKE/EKS/AKS)someone else runs the CP (CH 05)you run workers only
k3s / minikube / kindedge, dev, testingcondensed — what this series ran on
🔑
One sentence: kubeadm init is ceremony, not magic — generate a CA, write static-pod manifests, let the already-running kubelet conjure the control plane from files, then hand out signed join tokens so workers can trust and be trusted.

CH 02

💾 etcd — The Book of Record

🟡 6 MIN · CORE

Book 01 called etcd "the memory." Sharper: it's the single source of truth — every Deployment spec, every Secret, every Helm release receipt (Book 08 · CH 01!), every ServiceMonitor ever applied. Back it up or you don't have a cluster — you have a cluster-shaped amnesia waiting to happen.

💀

etcd gone, no backup
every object lost; nodes keep running Pods that nobody can change; rebuild = re-declare everything from Git (if you have it…)

⚠️

etcd slow
every API call waits — the whole cluster feels it (Book 07's "API slow" playbook row)

✅

etcd healthy + backed up
quorum serving (Book 01 · CH 08) · snapshots on a schedule · tested restores

  • 🔐 etcd holds Secrets in plaintext by default (Book 02 · CH 07) — encryption-at-rest + locked-down PKI are etcd hygiene, not options
  • ⚖️ Quorum math rules here too: 3 members tolerate 1 failure; a 2-member etcd is the worst number (Book 01's table, life-or-death edition)
  • 🗄️ State separation (Book 05, finale-level): etcd = cluster state (specs, wishes). PVs = app data. Back up BOTH — an etcd restore with empty PVs is a database cluster full of empty databases
# talking to etcd directly — mTLS, always (its own certs!): $ ETCDCTL_API=3 etcdctl \   --endpoints=https://127.0.0.1:2379 \   --cacert=/etc/kubernetes/pki/etcd/ca.crt \   --cert=/etc/kubernetes/pki/etcd/server.crt \   --key=/etc/kubernetes/pki/etcd/server.key \   endpoint health https://127.0.0.1:2379 is healthy
⚠️
Two CKA-favorite gotchas: (1) ETCDCTL_API=3 — the v2 API is ancient; snapshots don't exist in v2. (2) The certs are mandatory — etcd refuses unauthenticated clients by design; forgetting --cacert/--cert/--key fails with a connection error that looks like "etcd is down" when etcd is fine and you're just anonymous.
🔑
One sentence: etcd is the book of record for the entire cluster — everything Books 01–08 ever declared lives in its key-space — and its care routine is fixed: quorum membership (odd counts), encryption-at-rest, mTLS access, and snapshots you have actually restored at least once.

CH 03

📸 Backup & Restore — The Sacred Drill

🟡 6 MIN · CKA-CRITICAL

Two commands. Guaranteed exam points. Career-saving muscle memory. Take the shot:

# BACKUP — one snapshot file, consistent point-in-time: $ ETCDCTL_API=3 etcdctl \   --endpoints=https://127.0.0.1:2379 \   --cacert=/etc/kubernetes/pki/etcd/ca.crt \   --cert=/etc/kubernetes/pki/etcd/server.crt \   --key=/etc/kubernetes/pki/etcd/server.key \   snapshot save /backup/etcd-snapshot-$(date +%F).db Snapshot saved at /backup/etcd-snapshot-2026-01-15.db # VERIFY — never trust an unverified backup: $ ETCDCTL_API=3 etcdctl --write-table=json \   snapshot status /backup/etcd-snapshot-2026-01-15.db HASH    TOTAL KEYS  TOTAL SIZE 4a2c…   1842       6.2 MB
⚠️
Restore is not "put the file back": snapshot restore builds a new etcd data directory (new cluster identity, written to a fresh --data-dir). The dance: stop the API Server → stop etcd → restore to a new data-dir → point etcd at it → restart everything. On a kubeadm cluster that means moving the static-pod manifests out, restoring, and moving them back — the API Server must be down during restore, because it would keep writing to the old, broken reality.
The restore choreography (single-CP) 1 · mv /etc/kubernetes/manifests/*.yaml /tmp/ → CP static pods die 2 · snapshot restore --data-dir=/var/lib/etcd-restored /backup/x.db 3 · edit etcd static-pod yaml → --data-dir=/var/lib/etcd-restored 4 · mv manifests back → etcd boots from the snapshot 5 · API Server returns → cluster = the snapshot's moment multi-CP: restore ALL members from the SAME snapshot (quorum must agree on one history — mixing timelines = split brain)
Backup reality checkThe honest answer
Does a snapshot include PV data?No — etcd stores specs, not bytes. Database data needs PV-level backups (Book 05 · CH 06 + volume snapshots)
Snapshot replaces GitOps?No — they're a pair. Book 08: Git rebuilds declared state; snapshot recovers exact state including runtime-only fields (status, tokens, Helm receipts)
How often?Scheduled (cron + etcdctl) and before every risky operation (CH 04's upgrades!)
🔑
One sentence: snapshot save + snapshot status take minutes and save careers — but restore is a choreography (quiesce → restore to a new data-dir → boot), and a backup you've never restored is a rumor, not a backup. Lab 1 runs the whole drill.

CH 04

🎬 Cluster Upgrades — The Choreography

🟡 6 MIN · CORE

Kubernetes ships three releases a year; running a stale cluster means unsupported APIs and a painful jump eventually. The upgrade is a fixed dance — learn it once, perform it forever.

0Snapshot etcd (CH 03) — the undo for the entire dance
1Control Plane: upgrade the kubeadm binary → kubeadm upgrade plan → kubeadm upgrade apply vX.Y → upgrade kubelet & kubectl → restart kubelet
2Drain the CP node (Book 04 · CH 10) → upgrade → uncordon
3Each worker, one at a time: drain → kubeadm upgrade node → upgrade kubelet → uncordon → verify before the next
RuleWhy
One minor at a time (1.28 → 1.29, never → 1.30)skew guarantees only hold between adjacent versions
API Server first, kubelets afterskew policy: kubelet may lag the API Server (up to 3 minors) — never lead it
Control plane before workersnew kubelets must speak to a new-or-equal API Server
Read the "Upgrade notes"deprecated APIs get removed — your Book 08 CRDs and Helm charts may need version bumps before the cluster jumps
$ kubeadm upgrade plan Components that must be upgraded: etcd · kubelet ×3 You can now apply: v1.29.x $ kubectl get nodes -o wide  # watch versions march node-by-node: # CP 1.29 while workers still 1.28 — HEALTHY SKEW (expected!)
💡
Workloads ride through untouched: the upgrade moves the platform. Your Pods keep running — drain just asks them to walk across the street (Book 04). Only two things interrupt workloads: API removals (fix manifests first) and drain windows (spread workers, one at a time).
⚠️
On managed clusters (CH 05–06): the vendor performs the CP upgrade — you still own node-pool upgrades and API-deprecation readiness. "Managed" moves the choreography, it doesn't delete it.
🔑
One sentence: upgrades are a fixed choreography — snapshot, CP first (kubeadm apply), then workers one-by-one (drain → upgrade node → uncordon), one minor at a time, API Server never behind kubelets — and the skill is boring repetition, not improvisation. Lab 2 rehearses it.

CH 05

🤝 Managed vs Self-Hosted

🟢 5 MIN

The industry's default answer to CH 04's workload: buy the control plane. But "managed" is a spectrum — knowing exactly which responsibilities transfer is the interview-grade question.

ResponsibilitySelf-hosted (kubeadm)Managed (GKE/EKS/AKS)
etcd — backup, quorum, encryptionyou (CH 02–03)vendor — invisible, SLA-backed
API Server / CP upgradeyou (CH 04's dance)vendor performs CP; you upgrade node pools
CP availability (multi-master, LB)you (Book 01 · CH 08's 3-node math)vendor — regionally replicated
Cert rotation, security patching (CP)youvendor
Nodes, kubelets, node poolsyouyou — still your drain/upgrade cycle
CNI, CSI, admission policy, workloadsYOU — Books 01–08, unchanged
💡
The one-line division: managed = "we run the brain" (CP + etcd). The body is still yours — nodes, networking policy, RBAC, workloads, observability. Everything from Books 01–08 except CH 02–03's etcd drills transfers over; and even there, you own the data-residency and RBAC-around-etcd questions in regulated environments.
✅ Go managed when…

your team is small; Kubernetes isn't your product; you want SLA-backed CP + integrated cloud IAM/storage (CH 06's payoff); ops headcount beats hardware budget.

✅ Go self-hosted when…

edge/air-gapped/data-residency; cost at large scale (CP bill × 50 clusters); deep customization; or Kubernetes IS your product (you need kubeadm fluency — hence CKA).

🔑
One sentence: the managed question is really "who owns the control plane's pager?" — vendor takes etcd + CP availability + CP upgrades; you keep every Books-01–08 responsibility on the node and workload side, plus node-pool upgrades, which is why Book 04's drain skill survives every architecture choice.

CH 06

☁️ GKE · EKS · AKS — The Big Three

🔵 OVERVIEW

Same Kubernetes, different clouds — the differences that actually bite live in three places: networking model, IAM integration, node pools.

🟦 GKE (Google)🟧 EKS (AWS)🟦 AKS (Azure)
Default networkingVPC-native — Pod IPs are real VPC alias-IPsAWS VPC CNI — Pod IPs drawn from the subnet (ENI limits!)Azure CNI or kubenet — same IP-from-VPC tradeoff
IAM integrationGoogle IAM + Workload IdentityIRSA (IAM Roles for Service Accounts)Entra ID + Workload Identity
StandoutAutopilot (Pod-level billing, no nodes to manage)largest ecosystem; ALB controller pairs with Book 03's Ingresssmoothest Entra/AD enterprise fit
💡
Why the IAM piece matters to YOU: it's Book 02's ServiceAccount story, cloud edition. A Pod that needs S3 access shouldn't hold static keys in a Secret (Book 02 · CH 07's risk) — it should assume a cloud role via its ServiceAccount (IRSA/Workload Identity). Workload identity = the SA token exchanged for short-lived cloud credentials. Same principle: identity for workloads, scoped tight.
  • 🌐 Networking consequence: VPC-native models mean Pod IPs are routable cloud resources — beautiful (no overlay) but subnet-sized: ENI/IP exhaustion is the classic EKS scaling failure; plan CIDRs like Book 03 taught you to plan Services
  • 🧮 Node pools everywhere: the Book 04 toolkit (taints, labels, drain) applies per pool — GPU pool tainted (Book 04 · CH 03), spot pool for batch (Book 06 · CH 09's CA loves spot)
  • 🎯 Portability discipline: everything in this series — vanilla YAML, Helm, Kustomize, GitOps — runs identically on all three. Avoid vendor CRDs in your core manifests; keep cloud-specific bits in overlays (Book 08 · CH 04's structure earns its keep)
🔑
One sentence: the big three differ mainly in how Pod IPs meet the cloud network, how ServiceAccounts meet cloud IAM, and how node pools are priced and shaped — learn the mapping (CNI model · workload identity · pools) and you can move between all three; your Books-01–08 skills carry over unchanged.

CH 07

🌐 Multi-Cluster & Fleet Thinking

🔵 OVERVIEW

A single cluster is a blast radius. Bad deploys, bad upgrades (CH 04), regional outages — one control plane means one shared fate. Multi-cluster splits it. Honest framing: true "federation" (one API over many clusters) never won; today's practice is independent clusters + shared tooling.

💥 Blast radius
prod-canary cluster takes the upgrade first (CH 04); a bad release never touches everything at once

🌍 Regions & residency
latency (route to nearest), data laws (EU data stays EU — a hard wall, not a preference)

🔀 Environments
the Book 08 overlay story, per-cluster instead of per-namespace

ChallengeToday's answer (concept level)
Deploy to manyGitOps fleet: ArgoCD ApplicationSets / Flux multi-cluster — one Git commit, N clusters reconcile (Book 08's pull model, fleet edition)
One DNS across clustersglobal load balancing / multi-cluster Ingress (cloud LB + health checks steering between cluster edges — Book 03's LB at fleet level)
Trust between clustersshared/mirrored CA or service-mesh identity — cross-cluster Service calls are an advanced, opt-in pattern, not default
ConsistencyGit as the single spec (Book 08) + Book 09's snapshot discipline per cluster
⚠️
The rule of thumb before going multi: don't — until a concrete driver exists (residency law, region-outage SLA, upgrade blast radius). Multi-cluster multiplies everything: N × upgrades, N × observability, N × etcd discipline. One well-run cluster beats five shaky ones; Book 07's dashboards and Book 08's GitOps are what make N survivable.
🔑
One sentence: multi-cluster today = many independent clusters + GitOps fleet deployment + global traffic steering — no magic single API — justified only by blast radius, residency, or reach, and affordable only because Books 07–08 made N clusters observable and declarative.

🔬 etcd Snapshot & Restore Drill

🟠 15 MIN · HANDS-ON
STEP 1 · Reach etcd inside minikube (docker driver)
$ minikube ssh $ docker exec -it etcd-minikube sh # you're inside the etcd static-pod's container — # its certs are mounted at /etc/kubernetes/pki/etcd/
STEP 2 · Take + verify the snapshot
$ ETCDCTL_API=3 etcdctl \   --endpoints=https://127.0.0.1:2379 \   --cacert=/etc/kubernetes/pki/etcd/ca.crt \   --cert=/etc/kubernetes/pki/etcd/server.crt \   --key=/etc/kubernetes/pki/etcd/server.key \   snapshot save /backup/snap1.db Snapshot saved at /backup/snap1.db $ ETCDCTL_API=3 etcdctl --cacert=… --cert=… --key=… \   snapshot status /backup/snap1.db --write-table TOTAL KEYS  TOTAL SIZE ~1800       ~6 MB  # keys = every object you've ever applied!
👀 PROVE IT'S REAL STATE
# exit container; from host kubectl: $ kubectl create ns snapshot-proof $ kubectl get ns | grep proof snapshot-proof  Active # this ns exists NOW but not in # the snapshot taken a moment ago — # a restore would erase it. that's # "point-in-time," felt firsthand
⚠️ RESTORE — THE HONEST PART
# full restore on minikube = rebuild # (single-node CP, static pods). # the DRILL to know cold: 1 · mv manifests out (CP dies) 2 · etcdctl snapshot restore \     --data-dir=/var/lib/etcd-new \     snap1.db 3 · point etcd pod at new data-dir 4 · manifests back → boot # memorize the ORDER; the exam # runs it on a 3-node CP where it # works exactly like CH 03

Proved: mTLS access, snapshot+status, and point-in-time semantics. Cleanup: kubectl delete ns snapshot-proof.

$ # LAB 1's snapshot command, rerun — labeled for the upgrade: # /backup/pre-upgrade-$(date +%F).db # rule: no snapshot, no upgrade. ever.

GLOSS

📚 Glossary

🔵 REFERENCE
kubeadm — official bootstrap tool: generates PKI, writes static-pod manifests, prints join tokens.
Join token / CA hash — trust-on-first-use credentials letting a worker's kubelet register securely.
etcd — the cluster's key-value source of truth; quorum-based (odd members); holds every object incl. Helm receipts.
etcdctl — etcd client; v3 API required for snapshots; mTLS flags mandatory.
snapshot save / status / restore — consistent backup → verify → rebuild data-dir (new identity, API Server down during).
Version skew — supported mixing during upgrades; kubelet ≤ API Server, adjacent minors only.
kubeadm upgrade apply / node — CP-side / worker-side upgrade commands; one minor per hop.
Managed Kubernetes — vendor runs CP + etcd (GKE/EKS/AKS); you own nodes, CNI/CSI choices, workloads.
Node pool — a group of like nodes (per taints/labels/size) managed as a unit — the drain/upgrade unit in clouds.
Workload Identity / IRSA — ServiceAccount-assumed cloud roles; short-lived creds instead of static keys.
VPC-native / VPC CNI / Azure CNI — Pod IPs drawn from the cloud network (no overlay) — routable but subnet-bound.
Multi-cluster — many independent clusters; fleet GitOps (ApplicationSets) + global LB steering; no unified API.
Blast radius — how much one failure touches; the reason clusters (and upgrades) are split.
CKA / CKAD / CKS — CNCF hands-on certs: operate / build / harden — mapped in CH 08.

🧠 Facts worth a job offer
  • kubeadm = PKI + static-pod manifests + join tokens; the kubelet boots the control plane from files
  • etcd snapshots = cluster state only (never PV data); restore is cold — API Server down, new data-dir, same snapshot on all members
  • Upgrades: snapshot → CP first → workers one-by-one; one minor per hop; kubelet may lag, never lead
  • Managed = vendor owns CP pager; you keep node pools, drain discipline, CNI policy, and every Books-01–08 duty
  • Cloud trio differs by CNI model + workload identity (SA→cloud role, no static keys) + node pools
  • Multi-cluster = independent clusters + GitOps fleet + global steering — justified by blast radius/residency only
